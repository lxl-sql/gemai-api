# 2026-07-31 生产事故问题与修复总结

日期：2026-08-01
适用范围：API Key 鉴权、Redis 限流、PostgreSQL 连接与预扣费、Nginx 上游超时
事故影响：大量请求 Pending，间歇性 500/504，部分有额度用户收到 403

## 1. 结论

本次不是单一故障，至少有两条已确认的故障链，以及三条需要分别处置的启动、
额度和登录兼容问题：

1. API Key 查询的 `OR + ORDER BY id` 触发 PostgreSQL 大范围主键扫描，单次鉴权已实测耗时 1.1～2.5 秒，并发后持续占用数据库连接。
2. Redis 限流旧实现一次请求执行 3～4 条串行 Redis 命令；连接池默认过小或 Redis 变慢时，排队时间会叠加，并把 Redis 错误直接转成 HTTP 500。
3. PostgreSQL 未达到服务端 `max_connections`，但慢鉴权、Redis 等待和计费短事务叠加，导致应用侧连接排队；Nginx 的 504 和 `connection reset by peer` 是上游应用超时、退出或重启的结果。
4. `user quota is not enough` 403 对大量有余额用户出现，不应按正常余额不足处理。当前最符合代码路径的原因是历史用户的充值额度桶为负数、赠送额度为正数，总额度仍为正数，但 PostgreSQL 原子扣费要求两个额度桶分别非负而误拒绝。该点必须先用本文 SQL 确认，不能直接批量改余额。
5. 事故版本的 master 每次启动都会进入 `migrateDB()`，同步执行 Token Key 元数据和
   `token_usage_source_meta` 回填。现场 `[rows:200]` 慢 SQL 来自后者，不是普通查询；
   它按 200 条循环并在应用对外服务前完成，会显著延长大表实例的启动窗口。
6. 登录接口返回 root 用户 `role=100`，紧接着 `/api/user/self` 却返回“权限不足”。
   这证明数据库登录校验成功，但后续鉴权读取到了低于普通用户的角色。代码允许
   Redis 中字段不完整的 `user:<id>` Hash 以默认 `Role=0` 通过缓存角色合法性检查，
   能精确产生该响应；生产 `HGETALL user:1` 和定点清缓存后的复测结果仍需留档。

`TRUSTED_PROXIES`、是否使用 CDN 和本次 504 没有因果关系。`TRUSTED_PROXIES` 只决定哪些反向代理有权提供可信的转发 IP 头。

## 2. 生产证据

### 2.1 API Key 查询扫描

生产慢查询反复出现：

```sql
SELECT *
FROM tokens
WHERE (key_hash = $1 OR key = $2)
  AND deleted_at IS NULL
ORDER BY id
LIMIT 1;
```

现场证据：

- 生产单次耗时约 `1094ms～2486ms`，且多个会话并发执行。
- `EXPLAIN (ANALYZE, BUFFERS)` 选择 `tokens_pkey` 扫描，过滤 369206 行，`shared hit=293155`，单次执行 874.559ms。
- 表上虽然存在 `idx_tokens_key_hash` 和 `idx_tokens_key`，但 `OR` 叠加 `ORDER BY id LIMIT 1` 使规划器选择了主键有序扫描。

这条慢查询可以直接解释鉴权阶段的 Pending、数据库连接占用和后续 500/504。

### 2.2 PostgreSQL 连接与事务

现场统计：

- PostgreSQL `max_connections=500`，已使用 71，剩余 429；不是 PostgreSQL 服务端连接上限被全部用完。
- 应用来源 `172.20.0.1` 曾有 62 个会话，其中出现 15～18 个 `idle in transaction`。
- 现场大部分计费事务的 `transaction_age` 小于 1 秒，主要在执行 `billing_reservations`、`users`和 `tokens` 的预扣、结算与回滚。
- PostgreSQL 集中记录了 `terminating connection due to idle-in-transaction timeout`，说明 60 秒护栏在清理异常长事务。这是保护动作，不是根因本身。
- 一条只读 `log_stat_rollup_states` 查询在 10 秒后 `context deadline exceeded`。小表单行查询不应该执行 10 秒，这更符合连接获取或数据库整体排队。

当时应用连接池配置为：

```text
SQL_MAX_OPEN_CONNS=20
SQL_MAX_IDLE_CONNS=5
SQL_MAX_LIFETIME=60
SQL_PG_LOCK_TIMEOUT_MS=10000
SQL_PG_IDLE_IN_TX_TIMEOUT_MS=60000
```

这些值是现场运行边界，不是本次性能根因。不应通过盲目增大 `SQL_MAX_OPEN_CONNS` 掩盖慢查询和 Redis 排队。

### 2.3 Nginx 504

Nginx 在同一时间对 `/api/status`、`/api/user/self`、`/v1/chat/completions`、`/api/token/` 等多类路由记录：

```text
recv() failed (104: Connection reset by peer) while reading response header from upstream
upstream prematurely closed connection while reading response header from upstream
```

这证明 `127.0.0.1:22360` 上的应用主动断开、崩溃或重启，而不是域名解析、CDN 或客户端直连问题。

### 2.4 有额度用户收到 403

正常余额不足会返回带数值的错误：

```text
user quota is not enough, user quota: <current>, need quota: <required>
```

现场截图只有通用错误：

```text
user quota is not enough
```

这更符合总额度检查已通过，但 PostgreSQL 原子 `UPDATE` 的分桶非负守卫未通过。先执行：

```sql
SELECT
    COUNT(*) FILTER (
        WHERE quota::bigint + gift_quota::bigint > 0
    ) AS positive_total_users,
    COUNT(*) FILTER (
        WHERE quota < 0
          AND quota::bigint + gift_quota::bigint > 0
    ) AS affected_users
FROM users
WHERE deleted_at IS NULL;

SELECT id, username, quota, gift_quota,
       quota::bigint + gift_quota::bigint AS total_quota
FROM users
WHERE deleted_at IS NULL
  AND quota < 0
  AND quota::bigint + gift_quota::bigint > 0
ORDER BY id DESC
LIMIT 50;
```

只有 `affected_users > 0` 才能确认该根因。确认前不批量改 `users.quota` 或 `users.gift_quota`，不把清空 Redis 当成账务修复。

### 2.5 日志泄露 API Key

PostgreSQL 慢查询的 `DETAIL: parameters` 记录了完整的明文 API Key。这是独立的 P1 凭证泄露事件。

- 立即作废并重新生成已出现在日志和事故沟通中的 Key。
- 同步清理可下载、可检索和外部集中的日志副本。
- PostgreSQL 慢查询日志不再记录绑定参数原文；生产验收以日志中不出现完整 Key 为准。

### 2.6 master 启动重复执行 Token 元数据回填

事故版本启动链路为：

```text
InitDB（仅 master）
  -> migrateDB
     -> AutoMigrate
     -> BackfillTokenKeyMetadata
     -> BackfillTokenUsageSourceMeta
```

`BackfillTokenUsageSourceMeta` 没有版本迁移标记，每次 master 进程启动都会从游标 0
开始检查。它只回填不存在于 `token_usage_source_meta` 的 Token，因此数据层面幂等；
但即使历史回填已经完成，每次启动仍会执行缺失检查。现场日志持续出现：

```sql
SELECT *
FROM tokens
WHERE tokens.id > $cursor
  AND NOT EXISTS (
    SELECT 1
    FROM token_usage_source_meta
    WHERE token_usage_source_meta.token_id = tokens.id
  )
ORDER BY tokens.id
LIMIT 200;
```

以及事务内对同一批 ID 的二次确认查询。附件只截取到回填中段，没有最终
`rows:0`，所以能够确认本次启动确实在回填，不能仅凭该片段确认任务最终完成。
如果后续启动反复回填相同 ID，需要检查上次启动是否中断、事务是否提交，以及
`token_usage_source_meta` 是否被清理。

当前工作区已将同步 `BackfillTokenUsageSourceMeta()` 从 `migrateDB()` 移除。存量
Token 的元数据收敛由现有 `token_usage_source_reconcile` 系统任务按游标、小批次、
每分钟有限批数执行；新建 Token 仍在创建事务中同步写入对应 meta。该改动在生产
验收前只能标记为“本地已调整”，不能宣称线上启动阻塞已经消失。

### 2.7 PostgreSQL 超时与现场恢复采样

PostgreSQL 日志曾集中出现：

```text
FATAL: terminating connection due to idle-in-transaction timeout
ERROR: canceling statement due to lock timeout
```

同一窗口存在 `users.access_token/security_version` 更新和 Token 额度更新的行锁等待，
部分等待者在持锁会话被 60 秒护栏终止后才继续。因此 `FATAL` 是 PostgreSQL 对单个
异常会话的强制回滚，不代表 PostgreSQL 主进程崩溃；被终止事务对应的业务请求仍会
失败，不能把护栏触发当成系统健康。

后续恢复采样为：

| state | connections | longest transaction |
|---|---:|---:|
| `active` | 1 | 0s |
| `idle` | 30 | - |
| `idle in transaction` | 16 | 1.523729s |

明细中事务年龄约 0.04～1.69 秒，`idle_age` 多数低于 0.25 秒，SQL 为
`billing_reservations`、用户额度、Token 额度和数据库时钟等计费事务步骤，所有
`blocking_pids` 均为空。该采样说明当时 PostgreSQL 已不存在锁阻塞链，不能继续通过
重启 PostgreSQL 或批量终止短事务处理故障。后续应转向比较容器直连 `/healthz` 与
生产域名 `/healthz`，区分 API、反向代理和外部入口问题。

应急操作边界：

1. 若再次出现分钟级 `idle in transaction` 且存在阻塞，先从负载均衡摘除或暂停
   API 写入，阻止新事务继续进入；
2. 保存 `pg_stat_activity` 和 `pg_blocking_pids()` 证据后，只终止确认的长空闲事务；
3. 不重启 PostgreSQL，不关闭 `idle_in_transaction_session_timeout`，不在事故中执行
   `VACUUM FULL`；
4. 确认无阻塞后只恢复一个 API 实例，完成 `/healthz`、登录和一次计费闭环再扩容。

### 2.8 登录成功但 `/api/user/self` 权限不足

现场接口结果：

```json
// POST /api/user/login?turnstile=
{"data":{"id":1,"username":"root","role":100,"status":1},"success":true}

// GET /api/user/self
{"message":"无权进行此操作，权限不足","success":false}
```

`/api/user/self` 经过 `UserAuth()`，该文案只会在鉴权角色低于
`RoleCommonUser=1` 时返回。登录响应已经证明 PostgreSQL 中本次登录读取到
`role=100`；因此问题不在密码校验或 root 数据本身，而在后续会话鉴权读取链路。

当前 `GetUserCache()` 从 Redis 读取 `user:<id>` 后，只校验 `Role` 是否属于
`0/1/10/100`。Redis Hash 缺失 `Role` 时 Go 零值为 `0`，而 `0` 又被定义为合法
Guest 角色，于是字段不完整的缓存不会回源 PostgreSQL，最终被 `UserAuth()` 以
“权限不足”拒绝。该代码缺口是已确认的可达路径；是否就是本次线上唯一触发原因，
仍需以下生产证据闭环：

```redis
HGETALL user:1
```

紧急恢复只允许定点执行：

```redis
DEL user:1
```

删除的是可重建用户缓存，不修改 PostgreSQL 用户、额度或账单。若定点删除后 root
恢复，并确认普通用户存在相同的残缺 Hash，才可使用 `SCAN user:*` 分批清理用户
缓存；禁止 `FLUSHALL`，避免删除限流窗口、系统任务锁、Token 安全状态和其他共享
Redis 数据。

代码侧最小修复应在接受缓存前校验完整性，至少要求缓存 `Id` 与请求用户一致、
`Username` 非空、角色和状态字段存在且合法；不完整时删除该 Key 并从 PostgreSQL
重建完整 Hash。回归测试必须覆盖“Hash 存在但缺少 `Role`/`Id`/`Username`”，不能
只覆盖 Key 完全不存在的缓存未命中。

多实例还必须确认全部实例使用同一 Redis 和完全相同、长期稳定的
`SESSION_SECRET`。不过密钥不一致通常会表现为会话无法解码或未登录，不能在没有
证据时用它解释本次精确的“权限不足”文案。

## 4. 与本次故障无关或不能单独定性的现象

- `idle` 连接数较多不等于连接池被打满；需同时看应用 `DB.Stats()` 的 `OpenConnections`/`InUse`/`WaitCount`/`WaitDuration`。
- 几百毫秒以内的 `idle in transaction` 是计费事务两次 SQL 之间的短暂状态；只有持续增长或触发 60 秒终止的会话才是异常长事务。
- `ClientRead` 表示 PostgreSQL 正等待客户端下一条命令，不能直接统计为数据库锁等待；锁阻塞必须以 `wait_event_type='Lock'` 和 `pg_blocking_pids()` 为准。
- `504 Gateway Time-out` 是 Nginx 等不到或失去上游响应，不是 `TRUSTED_PROXIES` 验证失败。
- Redis 故障能解释部分 500 和 Pending，但不能解释已确认的 Key SQL 扫描，也不能解释通用文案的额度 403。
- `checkins` 唯一索引冲突是并发签到的业务冲突，与本次全站故障链无直接证据关联。

## 5. 生产发布门禁

本次修复不应直接全量重启。生产发布前必须满足：

1. 确认有额度用户的 403 根因，并修复 Redis 残缺用户缓存导致的登录后权限不足；
   两项均完成对应回归测试前不发布。
2. 对新镜像执行 Go 全仓测试、`go vet`、Docker 构建和容器健康检查。
3. 先在一个低风险实例灰度，其他实例保留已知可回滚镜像。
4. 灰度日志不得再出现旧 Key SQL 特征：

   ```text
   key_hash = $1 OR "key" = $2
   ORDER BY "tokens"."id" LIMIT 1
   ```

5. 灰度期间 Key 查询必须分别命中 `idx_tokens_key_hash` 或 `idx_tokens_key`，不得扫描 `tokens_pkey`。
6. 对 Redis 执行正常、慢响应、连接拒绝三种验收：慢响应和断连时不返回 500，请求最多等待 500ms 后进入内存限流。
7. 观察 PostgreSQL `active`、`idle in transaction`、等锁数、慢查询和应用连接池 `WaitCount/WaitDuration`，与故障时间段对比。
8. 观察 Nginx 500/502/504 和 `connection reset by peer`，灰度稳定后再逐台更新其余实例。
9. 已暴露 Key 必须完成轮换，新日志不再输出完整 Key。
10. 使用真实浏览器完成登录闭环：登录响应必须写入有效 session cookie，随后
    `/api/user/self` 返回 root/普通用户的真实角色；删除或构造残缺 `user:<id>`
    缓存后必须自动回源重建，不能返回“权限不足”。
11. master 启动日志不得再同步循环输出 `BackfillTokenUsageSourceMeta` 的
    `[rows:200]`；reconcile 任务必须有可观察的游标推进、完成状态和失败重试。

## 6. 回滚原则

1. 灰度实例出现 403 增长、Redis 降级风暴、Key 查询仍扫描主键、连接池等待增长或 5xx 上升时，立即将该实例摘流并回滚镜像。
2. 不在故障中执行批量余额改写、全表 Key 回填、删除索引、清空 Redis 或扩大所有实例的数据库连接池。
3. 普通应用回滚不做 DDL 回退；只回滚应用镜像，保留新增的兼容列和索引。

## 7. 验证边界

之前的本地审计已执行 Go 测试、`go vet`、Docker 镜像构建和容器健康检查。这些结果不能代替以下生产验收：

- 真实 PostgreSQL 表规模下的 Key 查询计划。
- 真实 Redis 延迟、断连和连接池竞争。
- 多实例灰度与回滚。
- 额度分桶历史数据的账务审计。
- Nginx 与应用超时、重启时序。
- Redis 用户缓存残缺场景和跨实例登录会话一致性。
- 历史 Token 使用来源 meta 的后台 reconcile 收敛与页面可用性。

在额度 403、登录后权限不足两个阻塞项未关闭、已暴露 Key 未轮换、灰度未通过前，
不得标记为可全量发布。

## 8. 2026-08-01 恢复现场复核与补充修复

### 8.1 本轮生产故障时序

本轮发布和恢复过程还出现了以下相互叠加的现象：

1. master 升级并执行 Token Key 元数据迁移后，继续更新了全部 slave；存量有效
   Token 的 `key_hash` 从约 36 万条缺失逐步回填到接近 0。
2. 回填及新版本切换期间，生产页面出现无法打开、接口 429/403、原 Key 调用失败、
   用户签到返回“更新额度出错”等现象。
3. PostgreSQL 日志出现 `idle-in-transaction timeout`、`users`/`channels` 行更新
   等锁，以及 `billing_reservations ... FOR UPDATE` 等计费事务排队。
4. 浏览器中 `/api/status`、`/api/notice`、日志统计和日志列表同时长期
   `pending`；`/api/log` 到 `/api/log/` 的 301 是路由规范化跳转，不是故障根因。
5. 随着迁移结束、超时事务被 PostgreSQL 护栏清理、连接重新建立以及积压请求
   排空，生产在没有重启 PostgreSQL 和 Redis 的情况下自行恢复。

这说明事故恢复不是“数据库或 Redis 自动修复了数据”，而是异常长事务、应用连接
等待和进程内排队逐步消退。恢复后的正常快照不能反向否定事故窗口内已经出现的
Redis pool timeout 和数据库排队证据。

### 8.2 恢复后的只读现场数据

恢复后再次执行只读检查，结果如下：

| 检查项 | 恢复后结果 | 判定 |
| --- | --- | --- |
| PostgreSQL 连接 | `active=2`、`idle=13`、`idle in transaction=3` | 连接总量很低 |
| 最长空闲事务 | 约 5ms | 属于事务两条 SQL 之间的瞬时状态 |
| 数据库阻塞者 | 查询结果为空 | 当前没有锁阻塞 |
| 超过 30 秒事务 | 查询结果为空 | 当前没有异常长事务 |
| 超过 5 秒 SQL | 查询结果为空 | 当前没有持续慢查询 |
| Redis | `PING=true`、`blocked_clients=0`、`rejected_connections=0`、`evicted_keys=0` | 当前服务端健康 |
| Redis 运行时间 | 约 302343 秒 | 恢复不是 Redis 重启造成 |
| `/api/status` | 连续 16 次 HTTP 200，约 0.73～1.49 秒 | 当前公开状态接口可用 |

`idle` 行显示的 `longest_query` 是空闲连接上一次查询开始至今的时间，不代表该 SQL
持续执行同样长的时间。几毫秒的 `idle in transaction` 也不是僵尸事务；只有持续增长、
分钟级不结束或形成阻塞时才属于异常。

恢复后没有证据支持继续重启 PostgreSQL、重启 Redis、清空 Redis 或批量终止所有
数据库连接。此类操作会制造新的连接风暴和请求失败。

### 8.3 生产数据规模与日志接口复核

生产 `logs` 表约 290826500 行、282GB，远大于本地和测试环境。这解释了为什么相同
代码只有在生产并发和真实数据规模下才容易暴露排队问题，但不能据此直接认定每个
`pending` 都是日志全表扫描。

恢复后对截图对应的管理端查询执行只读计划检查：

- 有界日志计数取前 10001 个 ID：约 9.573ms；
- 日志第一页 100 条：约 1.043ms；
- 一天的分钟汇总统计：约 0.736ms。

当前查询均使用现有索引或分钟汇总表，没有证据要求紧急新增索引、重建 282GB 日志表
或重启数据库。后续仍应以事故窗口的慢查询、连接池等待和锁快照为准，而不是只看表大小。

### 8.4 本轮补充的最小代码修复

除本文第 3 节已有修复外，工作区补充了以下最小改动：

| 问题 | 最小修复 | 边界 |
| --- | --- | --- |
| 启动时重复执行大批 Token Key 回填 | 默认不在启动阶段执行；仅显式设置 `TOKEN_KEY_METADATA_BACKFILL_ON_STARTUP=true` 时允许启动回填 | 存量回填应作为受控维护任务分批执行 |
| 用量来源元数据阻塞启动 | 移除启动时全量回填，交给有界 reconcile 任务逐步收敛 | 不在实例启动路径扫描生产大表 |
| Playground 没有真实 Token 仍进入安全预算 | `TokenId=0` 时不执行 Token 安全预算预留 | 不影响真实 API Key 请求的安全策略 |
| Token 安全策略查询故障误报 429 | 数据库/内部查询错误统一映射为安全服务暂不可用 503 | 真实限流或策略拒绝仍返回原有业务状态 |
| `/api/status`、`/api/notice` 等配置接口排队 | 只在复制所需配置值时持有读锁，JSON 序列化和网络发送前释放 | 不改变接口字段和配置内容 |
| 每 60 秒配置同步反复抢写锁 | 数据库值与内存值一致时跳过重复解析和写锁 | 配置发生变化时仍正常同步 |

配置锁问题在生产更容易触发：慢客户端可以延长响应写入时间；此时定时配置同步等待
写锁，后续新的配置读取又会排在写锁后面，最终表现为多个无关接口同时 `pending`。
本地和测试环境请求少、响应快，通常无法覆盖这种读写锁竞争时序。

上述补充修复已通过 `controller` 与 `model` 包测试和 `git diff --check`，但测试只证明
代码级回归。是否已经进入生产必须以正在运行的镜像 digest/提交、实例启动时间和灰度
实测为准，不能因为生产暂时自行恢复就标记为“已上线修复”。

### 8.5 后续发布与观察要求

1. 本轮补充修复不包含数据库迁移，不需要重启 PostgreSQL 或 Redis。
2. 先灰度一个可摘流实例，至少观察两个 `SYNC_FREQUENCY` 周期，再逐台扩大。

## 9. 2026-08-01 凌晨停摆 12 小时的恢复实战与 int32 额度边界回归

### 9.1 故障一：迁移锁超时导致启动崩溃循环（全站不可用的直接原因）

现象：页面无法打开、模型无法调用约 12 小时。本地与生产启动日志一致：

```text
[SYS] database migration started
[FATAL] failed to initialize database: ERROR: canceling statement due to lock timeout (SQLSTATE 55P03)
```

根因链：

1. 本次 key 升级需要对 `tokens` 表执行 `ALTER TABLE`（key_hash/key_hint 列）与建索引，
   对 `token_usage_sources` 增加 6 个计数列，均需 ACCESS EXCLUSIVE 锁；
2. 新加的角色级 `lock_timeout=5s` 在迁移之前生效，DDL 等锁 5 秒即被取消，且没有重试，
   `InitDB` 失败直接 `FatalLog` 退出，形成"启动→拿不到锁→崩溃"循环；
3. 旧实例仍在服务流量、另有一个新版本实例在崩溃循环中反复发起自己的迁移 DDL，
   多方在锁队列里互相撞 5 秒超时，谁都完不成；
4. `validateTokenKeyMetadataSchema()` 报错信息要求"先执行文档化的在线 DDL"，
   但仓库中不存在这份 DDL 文档。

处置过程（已验证有效）：

1. 通过 `pg_stat_activity` 按 `client_addr` 分组定位三个连接来源：生产实例（19 连接）、
   另一应用节点（3 连接）、以及一个反复执行 GORM 迁移探测语句
   （`SELECT c.conkey FROM pg_constraint ...`）的崩溃循环实例；
2. 停止全部 API 实例，`pg_terminate_backend` 清残留会话，确认应用连接数为 0；
3. 手工执行在线 DDL（即 validate 所要求、此前缺失的文档化 DDL）：

```sql
ALTER TABLE tokens ADD COLUMN IF NOT EXISTS key_hash char(64);
ALTER TABLE tokens ADD COLUMN IF NOT EXISTS key_hint varchar(32);
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_tokens_key_hash ON tokens (key_hash);
-- CONCURRENTLY 必须单独执行，失败会留 INVALID 索引，DROP 后重建

ALTER TABLE token_usage_sources ADD COLUMN IF NOT EXISTS success_count BIGINT NOT NULL DEFAULT 0;
ALTER TABLE token_usage_sources ADD COLUMN IF NOT EXISTS error_count BIGINT NOT NULL DEFAULT 0;
ALTER TABLE token_usage_sources ADD COLUMN IF NOT EXISTS forward_counted_through BIGINT NOT NULL DEFAULT 0;
ALTER TABLE token_usage_sources ADD COLUMN IF NOT EXISTS backfill_counted_from BIGINT NOT NULL DEFAULT 0;
ALTER TABLE token_usage_sources ADD COLUMN IF NOT EXISTS backfill_counted BIGINT NOT NULL DEFAULT 0;
ALTER TABLE token_usage_sources ADD COLUMN IF NOT EXISTS count_generation BIGINT NOT NULL DEFAULT 1;
```

4. DDL 就绪后启动新版本，迁移检测到 schema 已存在即跳过，服务恢复。

事故期间同时执行了 Redis `FLUSHDB`（服务已停摆、状态数据价值低于恢复速度的权衡决策）。
会话为 cookie 存储不受影响；副作用是任务锁、限流窗口、Token 风控挂起状态清零，
恢复后需按第 9.4 节观察。

### 9.2 故障二：int32 额度边界回归（服务起来后高余额用户仍不可用）

现象：余额充足的用户调用模型返回不带数字的 `user quota is not enough`；
管理后台调整其额度返回 `quota change exceeds database limit`。

根因：本次计费重构按"额度列是 32 位整数"的错误假设加入了一批 int32 边界校验，
但生产 PostgreSQL 额度列全部是 bigint，且本站充值比例下用户余额天然超过 int32
（显示额度 ×500000，百万级显示额度对应 5×10^11 内部额度）：

| 报错 | 位置 | 引入提交 |
| --- | --- | --- |
| 扣费守卫 `quota::bigint + ? BETWEEN 0 AND 2147483647` 恒不成立 | `tryApplyQuotaDeltaAtomicPG` | 816ba40ea |
| 单次变更量/余额上限按 int32 预检 | `createQuotaTransactionTx`、`applyQuotaDeltaPGTx`、`applyQuotaDeltaNoLedgerTx` | 816ba40ea / c1b5aafa4 |
| 令牌累计用量守卫 `used_quota <= MaxInt32-delta` | `adjustBillingReservationTokenTx` | 816ba40ea |

判别特征：总额度不足的正常报错带具体数字（`user quota: X, need quota: Y`）；
**不带数字**的通用文案即命中本回归。root（quota≈4.8 万亿）为首个确认案例。

应急处置（root 账户，已留底 `users_quota_backup_20260801`）：

```sql
UPDATE users SET quota = 2000000000 WHERE id = 1;  -- 临时降到 int32 内
-- 代码修复上线后可从备份表恢复原值
```

代码修复（本地已完成，共 3 文件）：

1. `model/quota_transaction.go`：五条余额路径的 int32 边界统一放宽为 int64 防溢出
   （新增 `quotaTransactionDeltaOverflows` 辅助函数）；原子扣费守卫改为仅要求扣后非负；
   扣费非负守卫（防超扣）原样保留，未削弱任何安全校验；
2. `model/quota_transaction.go`：流水表 7 个金额列 gorm tag `type:int` → `type:bigint`，
   与生产实际列型对齐（已用 information_schema 确认生产无 int4 额度列，无需 DDL）；
3. `model/billing_reservation.go`：令牌 `used_quota`/`remain_quota` 两处结算守卫
   同步放宽到 int64（长期使用的令牌累计用量合法超过 int32）；
4. 测试：2 个断言旧行为的测试改写 + 新增高余额扣费、大额调整、溢出边界等 4 个测试。

刻意保留（不是遗漏）：`common/quota_math.go` 的单笔请求结算钳制（MaxQuota=MaxInt32）、
`billing_reservations` 的单笔金额校验、限流配置与 max_tokens 上限——均为单请求维度
防溢出设计，单次请求不可能合法达到 21.47 亿 quota。

验证：`go vet`、`go build ./...` 干净；`model`、`service`、`pkg/billingexpr` 全部测试通过。
注意 SQLite 的 INTEGER 是 64 位，此类 int32 回归本地测试无法暴露，必须以生产 PG 验收。

### 9.3 本轮暴露的流程问题

1. 缺失的在线 DDL 文档：`validateTokenKeyMetadataSchema` 报错所引用的文档此前不存在，
   本节 9.1 的 SQL 即该文档内容，后续版本升级前置 DDL 一律先行文档化；
2. 迁移 DDL 无重试：等锁失败一次即 Fatal，需要加有限重试或迁移会话临时放宽 lock_timeout；
3. 角色级 `ALTER ROLE ... SET lock_timeout` 是持久的全局副作用，影响该角色所有连接
   （含运维 psql 会话），建议改为连接级设置；
4. 开发机 `.env` 直连生产 PostgreSQL/Redis，且 `SQL_MAX_OPEN_CONNS` 默认 1000
   （生产 max_connections=500），事故期间本地实例长时间占用生产连接并参与抢锁，
   必须切回本地环境；
5. 聊天/截图/日志中已暴露数据库、Redis 密码与 SSH 凭证，恢复稳定后统一轮换；
   `CRYPTO_SECRET` 是 key_hash 的 HMAC 密钥，所有实例必须一致且永不变更，
   当前仅 8 位强度不足，需在移除明文 key 列之前完成强密钥轮换与重回填。
