# 2026-07-31 生产事故问题与修复总结

日期：2026-08-01
适用范围：API Key 鉴权、Redis 限流、PostgreSQL 连接与预扣费、Nginx 上游超时
事故影响：大量请求 Pending，间歇性 500/504，部分有额度用户收到 403

## 1. 结论

本次不是单一故障，至少有两条已确认的故障链，以及三条需要分别处置的启动、
额度和登录兼容问题：

1. API Key 查询的 `OR + ORDER BY id` 触发 PostgreSQL 大范围主键扫描，单次鉴权已实测耗时 1.1～2.5 秒，并发后持续占用数据库连接。
2. Redis 限流旧实现一次请求执行 3～4 条串行 Redis 命令；连接池默认过小或 Redis 变慢时，排队时间会叠加，并把 Redis 错误直接转成 HTTP 500。
3. PostgreSQL 未达到服务端 `max_connections`，但慢鉴权、Redis 等待和计费短事务叠加，导致应用侧连接排队；Nginx 的 504 和 `connection reset by peer` 是上游应用超时、退出或重启的结果。
4. `user quota is not enough` 403 对大量有余额用户出现，不应按正常余额不足处理。当前最符合代码路径的原因是历史用户的充值额度桶为负数、赠送额度为正数，总额度仍为正数，但 PostgreSQL 原子扣费要求两个额度桶分别非负而误拒绝。该点必须先用本文 SQL 确认，不能直接批量改余额。
5. 事故版本的 master 每次启动都会进入 `migrateDB()`，同步执行 Token Key 元数据和
   `token_usage_source_meta` 回填。现场 `[rows:200]` 慢 SQL 来自后者，不是普通查询；
   它按 200 条循环并在应用对外服务前完成，会显著延长大表实例的启动窗口。
6. 登录接口返回 root 用户 `role=100`，紧接着 `/api/user/self` 却返回“权限不足”。
   这证明数据库登录校验成功，但后续鉴权读取到了低于普通用户的角色。代码允许
   Redis 中字段不完整的 `user:<id>` Hash 以默认 `Role=0` 通过缓存角色合法性检查，
   能精确产生该响应；生产 `HGETALL user:1` 和定点清缓存后的复测结果仍需留档。

`TRUSTED_PROXIES`、是否使用 CDN 和本次 504 没有因果关系。`TRUSTED_PROXIES` 只决定哪些反向代理有权提供可信的转发 IP 头。

## 2. 生产证据

### 2.1 API Key 查询扫描

生产慢查询反复出现：

```sql
SELECT *
FROM tokens
WHERE (key_hash = $1 OR key = $2)
  AND deleted_at IS NULL
ORDER BY id
LIMIT 1;
```

现场证据：

- 生产单次耗时约 `1094ms～2486ms`，且多个会话并发执行。
- `EXPLAIN (ANALYZE, BUFFERS)` 选择 `tokens_pkey` 扫描，过滤 369206 行，`shared hit=293155`，单次执行 874.559ms。
- 表上虽然存在 `idx_tokens_key_hash` 和 `idx_tokens_key`，但 `OR` 叠加 `ORDER BY id LIMIT 1` 使规划器选择了主键有序扫描。

这条慢查询可以直接解释鉴权阶段的 Pending、数据库连接占用和后续 500/504。

### 2.2 PostgreSQL 连接与事务

现场统计：

- PostgreSQL `max_connections=500`，已使用 71，剩余 429；不是 PostgreSQL 服务端连接上限被全部用完。
- 应用来源 `172.20.0.1` 曾有 62 个会话，其中出现 15～18 个 `idle in transaction`。
- 现场大部分计费事务的 `transaction_age` 小于 1 秒，主要在执行 `billing_reservations`、`users`和 `tokens` 的预扣、结算与回滚。
- PostgreSQL 集中记录了 `terminating connection due to idle-in-transaction timeout`，说明 60 秒护栏在清理异常长事务。这是保护动作，不是根因本身。
- 一条只读 `log_stat_rollup_states` 查询在 10 秒后 `context deadline exceeded`。小表单行查询不应该执行 10 秒，这更符合连接获取或数据库整体排队。

当时应用连接池配置为：

```text
SQL_MAX_OPEN_CONNS=20
SQL_MAX_IDLE_CONNS=5
SQL_MAX_LIFETIME=60
SQL_PG_LOCK_TIMEOUT_MS=10000
SQL_PG_IDLE_IN_TX_TIMEOUT_MS=60000
```

这些值是现场运行边界，不是本次性能根因。不应通过盲目增大 `SQL_MAX_OPEN_CONNS` 掩盖慢查询和 Redis 排队。

### 2.3 Nginx 504

Nginx 在同一时间对 `/api/status`、`/api/user/self`、`/v1/chat/completions`、`/api/token/` 等多类路由记录：

```text
recv() failed (104: Connection reset by peer) while reading response header from upstream
upstream prematurely closed connection while reading response header from upstream
```

这证明 `127.0.0.1:22360` 上的应用主动断开、崩溃或重启，而不是域名解析、CDN 或客户端直连问题。

### 2.4 有额度用户收到 403

正常余额不足会返回带数值的错误：

```text
user quota is not enough, user quota: <current>, need quota: <required>
```

现场截图只有通用错误：

```text
user quota is not enough
```

这更符合总额度检查已通过，但 PostgreSQL 原子 `UPDATE` 的分桶非负守卫未通过。先执行：

```sql
SELECT
    COUNT(*) FILTER (
        WHERE quota::bigint + gift_quota::bigint > 0
    ) AS positive_total_users,
    COUNT(*) FILTER (
        WHERE quota < 0
          AND quota::bigint + gift_quota::bigint > 0
    ) AS affected_users
FROM users
WHERE deleted_at IS NULL;

SELECT id, username, quota, gift_quota,
       quota::bigint + gift_quota::bigint AS total_quota
FROM users
WHERE deleted_at IS NULL
  AND quota < 0
  AND quota::bigint + gift_quota::bigint > 0
ORDER BY id DESC
LIMIT 50;
```

只有 `affected_users > 0` 才能确认该根因。确认前不批量改 `users.quota` 或 `users.gift_quota`，不把清空 Redis 当成账务修复。

### 2.5 日志泄露 API Key

PostgreSQL 慢查询的 `DETAIL: parameters` 记录了完整的明文 API Key。这是独立的 P1 凭证泄露事件。

- 立即作废并重新生成已出现在日志和事故沟通中的 Key。
- 同步清理可下载、可检索和外部集中的日志副本。
- PostgreSQL 慢查询日志不再记录绑定参数原文；生产验收以日志中不出现完整 Key 为准。

### 2.6 master 启动重复执行 Token 元数据回填

事故版本启动链路为：

```text
InitDB（仅 master）
  -> migrateDB
     -> AutoMigrate
     -> BackfillTokenKeyMetadata
     -> BackfillTokenUsageSourceMeta
```

`BackfillTokenUsageSourceMeta` 没有版本迁移标记，每次 master 进程启动都会从游标 0
开始检查。它只回填不存在于 `token_usage_source_meta` 的 Token，因此数据层面幂等；
但即使历史回填已经完成，每次启动仍会执行缺失检查。现场日志持续出现：

```sql
SELECT *
FROM tokens
WHERE tokens.id > $cursor
  AND NOT EXISTS (
    SELECT 1
    FROM token_usage_source_meta
    WHERE token_usage_source_meta.token_id = tokens.id
  )
ORDER BY tokens.id
LIMIT 200;
```

以及事务内对同一批 ID 的二次确认查询。附件只截取到回填中段，没有最终
`rows:0`，所以能够确认本次启动确实在回填，不能仅凭该片段确认任务最终完成。
如果后续启动反复回填相同 ID，需要检查上次启动是否中断、事务是否提交，以及
`token_usage_source_meta` 是否被清理。

当前工作区已将同步 `BackfillTokenUsageSourceMeta()` 从 `migrateDB()` 移除。存量
Token 的元数据收敛由现有 `token_usage_source_reconcile` 系统任务按游标、小批次、
每分钟有限批数执行；新建 Token 仍在创建事务中同步写入对应 meta。该改动在生产
验收前只能标记为“本地已调整”，不能宣称线上启动阻塞已经消失。

### 2.7 PostgreSQL 超时与现场恢复采样

PostgreSQL 日志曾集中出现：

```text
FATAL: terminating connection due to idle-in-transaction timeout
ERROR: canceling statement due to lock timeout
```

同一窗口存在 `users.access_token/security_version` 更新和 Token 额度更新的行锁等待，
部分等待者在持锁会话被 60 秒护栏终止后才继续。因此 `FATAL` 是 PostgreSQL 对单个
异常会话的强制回滚，不代表 PostgreSQL 主进程崩溃；被终止事务对应的业务请求仍会
失败，不能把护栏触发当成系统健康。

后续恢复采样为：

| state | connections | longest transaction |
|---|---:|---:|
| `active` | 1 | 0s |
| `idle` | 30 | - |
| `idle in transaction` | 16 | 1.523729s |

明细中事务年龄约 0.04～1.69 秒，`idle_age` 多数低于 0.25 秒，SQL 为
`billing_reservations`、用户额度、Token 额度和数据库时钟等计费事务步骤，所有
`blocking_pids` 均为空。该采样说明当时 PostgreSQL 已不存在锁阻塞链，不能继续通过
重启 PostgreSQL 或批量终止短事务处理故障。后续应转向比较容器直连 `/healthz` 与
生产域名 `/healthz`，区分 API、反向代理和外部入口问题。

应急操作边界：

1. 若再次出现分钟级 `idle in transaction` 且存在阻塞，先从负载均衡摘除或暂停
   API 写入，阻止新事务继续进入；
2. 保存 `pg_stat_activity` 和 `pg_blocking_pids()` 证据后，只终止确认的长空闲事务；
3. 不重启 PostgreSQL，不关闭 `idle_in_transaction_session_timeout`，不在事故中执行
   `VACUUM FULL`；
4. 确认无阻塞后只恢复一个 API 实例，完成 `/healthz`、登录和一次计费闭环再扩容。

### 2.8 登录成功但 `/api/user/self` 权限不足

现场接口结果：

```json
// POST /api/user/login?turnstile=
{"data":{"id":1,"username":"root","role":100,"status":1},"success":true}

// GET /api/user/self
{"message":"无权进行此操作，权限不足","success":false}
```

`/api/user/self` 经过 `UserAuth()`，该文案只会在鉴权角色低于
`RoleCommonUser=1` 时返回。登录响应已经证明 PostgreSQL 中本次登录读取到
`role=100`；因此问题不在密码校验或 root 数据本身，而在后续会话鉴权读取链路。

当前 `GetUserCache()` 从 Redis 读取 `user:<id>` 后，只校验 `Role` 是否属于
`0/1/10/100`。Redis Hash 缺失 `Role` 时 Go 零值为 `0`，而 `0` 又被定义为合法
Guest 角色，于是字段不完整的缓存不会回源 PostgreSQL，最终被 `UserAuth()` 以
“权限不足”拒绝。该代码缺口是已确认的可达路径；是否就是本次线上唯一触发原因，
仍需以下生产证据闭环：

```redis
HGETALL user:1
```

紧急恢复只允许定点执行：

```redis
DEL user:1
```

删除的是可重建用户缓存，不修改 PostgreSQL 用户、额度或账单。若定点删除后 root
恢复，并确认普通用户存在相同的残缺 Hash，才可使用 `SCAN user:*` 分批清理用户
缓存；禁止 `FLUSHALL`，避免删除限流窗口、系统任务锁、Token 安全状态和其他共享
Redis 数据。

代码侧最小修复应在接受缓存前校验完整性，至少要求缓存 `Id` 与请求用户一致、
`Username` 非空、角色和状态字段存在且合法；不完整时删除该 Key 并从 PostgreSQL
重建完整 Hash。回归测试必须覆盖“Hash 存在但缺少 `Role`/`Id`/`Username`”，不能
只覆盖 Key 完全不存在的缓存未命中。

多实例还必须确认全部实例使用同一 Redis 和完全相同、长期稳定的
`SESSION_SECRET`。不过密钥不一致通常会表现为会话无法解码或未登录，不能在没有
证据时用它解释本次精确的“权限不足”文案。

## 4. 与本次故障无关或不能单独定性的现象

- `idle` 连接数较多不等于连接池被打满；需同时看应用 `DB.Stats()` 的 `OpenConnections`/`InUse`/`WaitCount`/`WaitDuration`。
- 几百毫秒以内的 `idle in transaction` 是计费事务两次 SQL 之间的短暂状态；只有持续增长或触发 60 秒终止的会话才是异常长事务。
- `ClientRead` 表示 PostgreSQL 正等待客户端下一条命令，不能直接统计为数据库锁等待；锁阻塞必须以 `wait_event_type='Lock'` 和 `pg_blocking_pids()` 为准。
- `504 Gateway Time-out` 是 Nginx 等不到或失去上游响应，不是 `TRUSTED_PROXIES` 验证失败。
- Redis 故障能解释部分 500 和 Pending，但不能解释已确认的 Key SQL 扫描，也不能解释通用文案的额度 403。
- `checkins` 唯一索引冲突是并发签到的业务冲突，与本次全站故障链无直接证据关联。

## 5. 生产发布门禁

本次修复不应直接全量重启。生产发布前必须满足：

1. 确认有额度用户的 403 根因，并修复 Redis 残缺用户缓存导致的登录后权限不足；
   两项均完成对应回归测试前不发布。
2. 对新镜像执行 Go 全仓测试、`go vet`、Docker 构建和容器健康检查。
3. 先在一个低风险实例灰度，其他实例保留已知可回滚镜像。
4. 灰度日志不得再出现旧 Key SQL 特征：

   ```text
   key_hash = $1 OR "key" = $2
   ORDER BY "tokens"."id" LIMIT 1
   ```

5. 灰度期间 Key 查询必须分别命中 `idx_tokens_key_hash` 或 `idx_tokens_key`，不得扫描 `tokens_pkey`。
6. 对 Redis 执行正常、慢响应、连接拒绝三种验收：慢响应和断连时不返回 500，请求最多等待 500ms 后进入内存限流。
7. 观察 PostgreSQL `active`、`idle in transaction`、等锁数、慢查询和应用连接池 `WaitCount/WaitDuration`，与故障时间段对比。
8. 观察 Nginx 500/502/504 和 `connection reset by peer`，灰度稳定后再逐台更新其余实例。
9. 已暴露 Key 必须完成轮换，新日志不再输出完整 Key。
10. 使用真实浏览器完成登录闭环：登录响应必须写入有效 session cookie，随后
    `/api/user/self` 返回 root/普通用户的真实角色；删除或构造残缺 `user:<id>`
    缓存后必须自动回源重建，不能返回“权限不足”。
11. master 启动日志不得再同步循环输出 `BackfillTokenUsageSourceMeta` 的
    `[rows:200]`；reconcile 任务必须有可观察的游标推进、完成状态和失败重试。

## 6. 回滚原则

1. 灰度实例出现 403 增长、Redis 降级风暴、Key 查询仍扫描主键、连接池等待增长或 5xx 上升时，立即将该实例摘流并回滚镜像。
2. 不在故障中执行批量余额改写、全表 Key 回填、删除索引、清空 Redis 或扩大所有实例的数据库连接池。
3. 普通应用回滚不做 DDL 回退；只回滚应用镜像，保留新增的兼容列和索引。

## 7. 验证边界

之前的本地审计已执行 Go 测试、`go vet`、Docker 镜像构建和容器健康检查。这些结果不能代替以下生产验收：

- 真实 PostgreSQL 表规模下的 Key 查询计划。
- 真实 Redis 延迟、断连和连接池竞争。
- 多实例灰度与回滚。
- 额度分桶历史数据的账务审计。
- Nginx 与应用超时、重启时序。
- Redis 用户缓存残缺场景和跨实例登录会话一致性。
- 历史 Token 使用来源 meta 的后台 reconcile 收敛与页面可用性。

在额度 403、登录后权限不足两个阻塞项未关闭、已暴露 Key 未轮换、灰度未通过前，
不得标记为可全量发布。

## 8. 2026-08-01 恢复现场复核与补充修复

### 8.1 本轮生产故障时序

本轮发布和恢复过程还出现了以下相互叠加的现象：

1. master 升级并执行 Token Key 元数据迁移后，继续更新了全部 slave；存量有效
   Token 的 `key_hash` 从约 36 万条缺失逐步回填到接近 0。
2. 回填及新版本切换期间，生产页面出现无法打开、接口 429/403、原 Key 调用失败、
   用户签到返回“更新额度出错”等现象。
3. PostgreSQL 日志出现 `idle-in-transaction timeout`、`users`/`channels` 行更新
   等锁，以及 `billing_reservations ... FOR UPDATE` 等计费事务排队。
4. 浏览器中 `/api/status`、`/api/notice`、日志统计和日志列表同时长期
   `pending`；`/api/log` 到 `/api/log/` 的 301 是路由规范化跳转，不是故障根因。
5. 随着迁移结束、超时事务被 PostgreSQL 护栏清理、连接重新建立以及积压请求
   排空，生产在没有重启 PostgreSQL 和 Redis 的情况下自行恢复。

这说明事故恢复不是“数据库或 Redis 自动修复了数据”，而是异常长事务、应用连接
等待和进程内排队逐步消退。恢复后的正常快照不能反向否定事故窗口内已经出现的
Redis pool timeout 和数据库排队证据。

| 检查项 | 恢复后结果 | 判定 |

## 9. 2026-08-01 凌晨停摆 12 小时的恢复实战与 int32 额度边界回归

### 9.1 故障一：迁移锁超时导致启动崩溃循环（全站不可用的直接原因）

现象：页面无法打开、模型无法调用约 12 小时。本地与生产启动日志一致：

```text
[SYS] database migration started
[FATAL] failed to initialize database: ERROR: canceling statement due to lock timeout (SQLSTATE 55P03)
```

根因链：

1. 本次 key 升级需要对 `tokens` 表执行 `ALTER TABLE`（key_hash/key_hint 列）与建索引，
   对 `token_usage_sources` 增加 6 个计数列，均需 ACCESS EXCLUSIVE 锁；
2. 新加的角色级 `lock_timeout=5s` 在迁移之前生效，DDL 等锁 5 秒即被取消，且没有重试，
   `InitDB` 失败直接 `FatalLog` 退出，形成"启动→拿不到锁→崩溃"循环；
3. 旧实例仍在服务流量、另有一个新版本实例在崩溃循环中反复发起自己的迁移 DDL，
   多方在锁队列里互相撞 5 秒超时，谁都完不成；
4. `validateTokenKeyMetadataSchema()` 报错信息要求"先执行文档化的在线 DDL"，
   但仓库中不存在这份 DDL 文档。

处置过程（已验证有效）：

1. 通过 `pg_stat_activity` 按 `client_addr` 分组定位三个连接来源：生产实例（19 连接）、
   另一应用节点（3 连接）、以及一个反复执行 GORM 迁移探测语句
   （`SELECT c.conkey FROM pg_constraint ...`）的崩溃循环实例；
2. 停止全部 API 实例，`pg_terminate_backend` 清残留会话，确认应用连接数为 0；
3. 手工执行在线 DDL（即 validate 所要求、此前缺失的文档化 DDL）：

```sql
ALTER TABLE tokens ADD COLUMN IF NOT EXISTS key_hash char(64);
ALTER TABLE tokens ADD COLUMN IF NOT EXISTS key_hint varchar(32);
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_tokens_key_hash ON tokens (key_hash);
-- CONCURRENTLY 必须单独执行，失败会留 INVALID 索引，DROP 后重建

ALTER TABLE token_usage_sources ADD COLUMN IF NOT EXISTS success_count BIGINT NOT NULL DEFAULT 0;
ALTER TABLE token_usage_sources ADD COLUMN IF NOT EXISTS error_count BIGINT NOT NULL DEFAULT 0;
ALTER TABLE token_usage_sources ADD COLUMN IF NOT EXISTS forward_counted_through BIGINT NOT NULL DEFAULT 0;
ALTER TABLE token_usage_sources ADD COLUMN IF NOT EXISTS backfill_counted_from BIGINT NOT NULL DEFAULT 0;
ALTER TABLE token_usage_sources ADD COLUMN IF NOT EXISTS backfill_counted BIGINT NOT NULL DEFAULT 0;
ALTER TABLE token_usage_sources ADD COLUMN IF NOT EXISTS count_generation BIGINT NOT NULL DEFAULT 1;
```

4. DDL 就绪后启动新版本，迁移检测到 schema 已存在即跳过，服务恢复。

事故期间同时执行了 Redis `FLUSHDB`（服务已停摆、状态数据价值低于恢复速度的权衡决策）。
会话为 cookie 存储不受影响；副作用是任务锁、限流窗口、Token 风控挂起状态清零，
恢复后需按第 9.4 节观察。

### 9.2 故障二：int32 额度边界回归（服务起来后高余额用户仍不可用）

现象：余额充足的用户调用模型返回不带数字的 `user quota is not enough`；

判别特征：总额度不足的正常报错带具体数字（`user quota: X, need quota: Y`）；

## 10. 2026-08-01 夜间计费积压事故（reservation 只进不出）

时间一律为 UTC，本地时间 +8。

### 10.1 结论

本次是**两个互相独立的问题叠加**，排查中长时间把二者当成一个，导致方向反复。

**问题一：积压清不掉** —— 修复机制在四处同时失效（详见 10.3），
`billing_reservations` 只进不出。

**问题二：失败持续产生** —— 12 个异地容灾实例到数据库的 RTT 为
**115–371ms（均值 224ms）**，而一次结算需要约 18 次往返，仅网络就消耗
4–6.7 秒，撞穿 15 秒的事务预算（详见 10.10）。

两条决定性证据：

1. `idx_logs_user_id_created_at` 建成后查询成本从 6294 降到 4.27（约 1400 倍），
   但积压**仍从 1714 涨到 3010** —— 慢查询不是积压增长的原因；
2. **关闭全部远程 slave、只留同机房的 master 后，
   `billing_settlement_failures.pending` 立即停止增长** —— 失败源就是那条高延迟链路。

慢查询（`logs` 缺 `(user_id, created_at)` 索引）是真实存在的问题，也确实拖慢了
整体，但它既不是积压增长的原因，也不是失败产生的原因。修它是必要的，
不足以解决本次事故。

### 10.3 根因

**第一层：数据库饱和（导火索）**

`logs` 表 2.92 亿行、283 GB、17 个索引，缺少 `(user_id, created_at)` 复合索引。
日志页面查询走 `BitmapAnd`，需先对时间窗口内约 54 万行建位图，单条 10–14s；
同时每个请求写一条日志要维护 17 个索引。读写两头挤压使计费事务撞上
`quotaTransactionTimeout`（15s），每次超时留下一条卡住的 reservation 与一条失败记录。

**第二层：修复机制全线失效（主因）**

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | 退避表达式在 PG 上被推导为 jsonb | 修复 worker 一条待重试记录都取不到，210 条 `attempts=0` 从未被重试 |
| 2 | `FindDueBillingReservations` 无宽限期，而 `persistBillingReservationIntent` 把 `expires_at` 写成 `now` | 在途结算立刻"到期"，修复 worker 与请求路径争抢同一行 |
| 3 | `FinishSystemTask` 租约丢失时不清 status/active_key，且回收逻辑以锁行为遍历起点 | 无锁行的 running 任务无法被任何路径回收，`active_key` 永久占用 |
| 4 | 失败记录阶段吃光整轮预算 | `reservations_scanned` 长期为 0，**reservation 修复路径一次都没执行过** |

第 4 条是积压单调上涨的直接原因。

**第三层：混版本放大**

1 master + 12 slave 共同抢占同一个 `billing_settlement_repair` 任务
（`active_key` 唯一索引保证全局单任务），而 slave 仍为旧版本，
约 12/13 的轮次执行了带缺陷的逻辑。这解释了同一条 SQL 时而报 jsonb 错、
时而正常的现象。

### 10.4 本轮代码修复

1. `model/billing_settlement_failure.go`：退避表达式在 PG 分支加 `CAST(? AS BIGINT)`
   （该修复此前已在工作区但**从未发布**，生产跑的是带 CASE 不带 CAST 的中间版本）；

### 10.8 新增检查项

1. **删除 `logs` 任何索引前，必须先确认 GORM 模型中没有对应的 `index` 标签**，
   否则下次重启 AutoMigrate 会以非 CONCURRENTLY 方式重建并导致启动 FATAL；
2. 超大表上的 `ALTER TABLE ... SET DEFAULT` 虽只改系统目录，仍需
   ACCESS EXCLUSIVE 锁；表上存在 autovacuum 或长事务时，5s `lock_timeout`
   必然失败并使启动崩溃。必要时对该次启动临时放宽 `SQL_PG_LOCK_TIMEOUT_MS`，
   成功后立即恢复；
3. `CREATE INDEX CONCURRENTLY` 期间 `indisvalid=f` 是**正常状态**，
   完成判据是 `pg_stat_progress_create_index` 返回空；该期间不得执行
   同名 `DROP INDEX`，也不得关闭发起会话；长任务应使用 `docker exec -d` 脱离终端；
4. 修复类系统任务为全局单任务（`active_key` 唯一索引），**增加实例不会加快清理**，
   且多实例高并发只会加剧行锁竞争；扩容的意义在于版本一致性而非吞吐；
5. 所有实例的 `BILLING_SETTLEMENT_REPAIR_*` 环境变量必须一致，
   否则哪个实例抢到任务就用哪份配置，行为随机。

### 10.10 网络拓扑根因：异地实例的 224ms RTT

修复机制全部修好、索引建成、pgbouncer 池子放开之后，
`billing_settlement_failures.pending` 仍以每 15 分钟约 165 条的速度增长。
沿以下顺序逐一排除后定位到网络：

| 测量 | 结果 | 结论 |
|---|---|---|
| `pg_stat_activity` | total 47 / active **1** / idle in tx 32，`max_connections=500` | PostgreSQL 几乎空闲，不是数据库慢 |
| `idle in transaction` 明细 | `xact_age` 1–7s，但 `idle_for` 均 < 1s | 不是泄漏事务，是正常事务在等下一条语句跨网络到达 |
| pgbouncer `SHOW POOLS` | `cl_waiting=0`、`maxwait=0`、`sv_idle=7` | 池子放开后不再是瓶颈 |
| `ping` 异地实例 → 数据库 | **min 115 / avg 224 / max 371 ms** | 根因 |

一次 `FinalizeBillingReservation` 的往返构成：

```
findBillingReservationUserId                                          1
事务一  BEGIN + SET LOCAL×2 + SELECT FOR UPDATE + UPDATE + COMMIT      6
事务二  BEGIN + SET LOCAL×2 + SELECT FOR UPDATE + 扣款/退款
        + UPDATE tokens + UPDATE billing_reservations + COMMIT       ~10
缓存失效查询                                                           1
                                                                  ─────
                                                                  约 18 次
```

`18 × 224ms ≈ 4.0s`，抖动到 371ms 时 `≈ 6.7s`，而 `quotaTransactionTimeout`
写死 15 秒。余量经不起任何行锁等待或连接排队，因此热点用户与高并发场景必然超时。

这也解释了此前所有反直觉的观测：`active=1` 却大量超时；建完索引失败率不降；
master（与数据库同机）的修复 worker 却能稳定修好 813 条。

**决定性实验**：关闭全部远程 slave、只保留 master，`pending` 立即停止增长。

前提约束：12 个异地实例是**多地容灾**的刻意设计，不能简单迁到同机房。

### 10.11 高延迟拓扑下的收敛方案

**认识前提**：持久化 reservation 本就是为最终一致设计的，结算失败不等于丢钱，
只是延后结算且幂等可修。因此目标不是"零失败"，而是：

```
异地实例的失败产生速率  <  同机房 master 的修复处理速率
```

不等式成立即自行收敛，用户仅承受数分钟的结算延迟（其间按预扣多扣，结算后退回）。

**处置顺序**

1. 保持异地实例下线，先让 master 把存量清空；
2. **逐台**恢复异地实例，每台观察 10 分钟 `pending` 是否稳定，
   得出"可支撑的异地实例数量"这一容量上限；
3. 给异地实例单独放宽事务预算（环境变量按实例生效，master 保持默认）：

```bash
SQL_QUOTA_TX_TIMEOUT_SECONDS=40
```

**中期方案（按性价比排序）**

- **A. 压缩每次结算的往返次数**：两条 `SET LOCAL` 改为连接级设置（省 4 次）、
  `findBillingReservationUserId` 重复调用合并（省 1 次）、
  两个事务在多数场景下合并（省 6 次）。压到 6–8 次后，224ms 链路上
  单次结算由 4s 降至约 1.5s，异地失败率将大幅下降。**不改架构，收益最大**；
- **B. 计费走同机房服务**：异地实例不直连数据库做计费，改为调用部署在数据库
  同机房的计费接口，异地只付 1 次 RTT，18 次往返在机房内完成。改动大但最彻底，
  可同时满足多地容灾与计费性能；
- **C. 区域只读副本**：对本问题**无效**，计费是写路径，不要在此投入。

### 10.13 pgbouncer 配置修正

事故中发现的配置问题（`pgbouncer-write`）：

| 参数 | 原值 | 修正值 | 说明 |
|---|---|---|---|
| `DEFAULT_POOL_SIZE` | 48 | 160 | 原按「3×CPU」定，该经验法则假设连接消耗 CPU；实测 `active=1`，连接全在等待，应按在途并发定 |
| `MAX_DB_CONNECTIONS` | 56 | 200 | 未同步放开时会架空 `DEFAULT_POOL_SIZE` |
| `MIN_POOL_SIZE` | 200 | 20 | 曾误设为大于 `DEFAULT_POOL_SIZE`，逻辑矛盾 |
| `MAX_CLIENT_CONN` | 600 | 1000 | 13 实例 × `SQL_MAX_OPEN_CONNS=48` = 624 已超限，是 `server refused TLS connection` 的来源 |

应用侧同步调整：`SQL_MAX_OPEN_CONNS=30`、`SQL_MAX_IDLE_CONNS=30`、
`SQL_MAX_LIFETIME=1800`。原 `MAX_IDLE=8 / MAX_OPEN=48` 意味着多达 40 条连接
反复建立关闭，而在 224ms 链路上每次 TCP+TLS 握手约需 0.7–1.1 秒，纯属浪费。

注意 edoburu 镜像在启动时由环境变量生成配置，改动必须
`docker compose up -d --force-recreate`，仅 `restart` 不生效。

### 10.14 待验证：224ms 可能是 Tailscale 中转而非地理距离

**状态：假设，尚未验证，不要据此下结论。**

在 `serFLpJzqt74hXO` 上 ping 数据库主机的公网地址 `154.9.232.11`：

```
rtt min/avg/max/mdev = 2.368/6.738/25.319/5.539 ms
```

而在 `ser454596305472` 上 ping 其 Tailscale 地址 `100.103.175.16` 为
`115.5/224.1/370.8 ms`。两者相差约 33 倍。

**但这两次测量来自不同主机，不能直接比较** —— 也可能只是后者物理距离更近。

若同机对比成立，则说明 224ms 来自 Tailscale 走 DERP 中转而非直连，
与本项目此前记录过的「Tailscale 默认端口被运营商限速、改用 UDP 443 后延迟
相差数十倍」是同一类问题。

**验证方法**（必须在同一台异地主机上执行）：

```bash
ping -c 20 -i 0.3 100.103.175.16 | tail -3
ping -c 20 -i 0.3 154.9.232.11   | tail -3
tailscale ping 100.103.175.16
tailscale status
```

`tailscale ping` 输出 `via DERP` 即为中转，`direct` 为直连；
`tailscale status` 中节点标注 `relay "xxx"` 同样表示中转。

**若确认是中转**，则 10.10 的定性需要再次修正：延迟不是多地容灾的固有代价，
而是隧道未打通直连。修好后单次结算的网络成本由 4s 降至约 0.12s，
异地实例可全部恢复，10.11 的中期方案 A/B 均无需实施。

修复优先级：

1. 打通 Tailscale 直连（强制 UDP 443、检查 NAT 与防火墙放行），
   保留既有加密与访问控制，为首选；
2. 仅在直连确实打不通时，才考虑公网 IP + 源地址白名单 + TLS，
   该方案需重新设计安全模型，不作为优先项。

**流程教训**：本次排查中，网络延迟是最后才测量的，而它恰恰是根因所在。
此前依次怀疑并投入了慢查询、连接池、并发度、代码逻辑四个方向，
其中三个方向的改动虽有价值但均未触及根因。
**今后凡出现「数据库 `active` 连接数极低却大面积超时」的现象，
应第一时间测量应用到数据库的 RTT**，该组合几乎必然指向链路而非数据库。

### 10.16 运维基线：billing_reservations 各状态的健康区间

| 状态 | 健康值 | 说明 |
|---|---|---|
| `reserved` | total 几到几十，**due = 0** | 已预扣未发出。`due > 0` 表示预扣后卡住 |
| `dispatched` | total = **当前并发请求数**（数十至数百皆正常），**due = 0** | total 随流量波动，**只有 `due` 有诊断意义** |
| `settling` | < 10，**due ≈ 0** | 瞬时状态，正常情况毫秒级流转 |
| `refunding` | < 10，**due ≈ 0** | 同上 |
| `completed` | **< 100，理想接近 0** | 正常请求写完日志即删除自身回执；堆积表示审计未跟上 |
| `auditing` | **< 50，due = 0** | 瞬时认领状态；`due > 0` 表示认领租约过期，属异常 |

**单一监控指标**（告警应挂在这一条上）：

```sql
SELECT count(*) FROM billing_reservations
WHERE status IN ('reserved','dispatched','settling','refunding')
  AND expires_at <= extract(epoch from now());
```

健康区间 **0–20**；持续超过 100 且上涨才需要介入。
不要监控 `total`，它随流量波动，没有诊断价值。

### 10.17 后续优化排期（按投入产出比排序，取代 10.9 的平铺列表）

**P0 — 修复链路（唯一能一次消除四个症状的动作）**

**P1 — 发布审计并发化版本**

- 内存扩容，使 `shared_buffers` + 页缓存能覆盖热索引。

由 18 次压缩至 6–8 次：两条 `SET LOCAL` 改为连接级设置（−4）、
`findBillingReservationUserId` 重复调用合并（−1）、
多数场景下合并两个事务（−6）。即便链路修复，减少往返对高并发同样有益。

**P4 — 收尾清理**

1. 积压清空后，从全部实例移除临时环境变量
   （`BILLING_SETTLEMENT_REPAIR_CONCURRENCY`、`BILLING_SETTLEMENT_REPAIR_RUN_LIMIT_SECONDS`、
   `BILLING_AUDIT_REPAIR_BATCH_SIZE`），回归默认值；
2. 人工核销 7 条「用户余额不足」的历史失败记录，
   否则 `Enabled()` 门禁恒为真、修复任务永久空转；
3. 核查数据库主机上的 `BT-Task` 高 CPU 占用。

**P5 — 可观测性补强（低峰期维护窗口执行）**

启用 `pg_stat_statements`（需重启 PostgreSQL，**不可在事故中做**），
补齐「数据库时间花在哪」的实测依据；
为 10.16 的单一监控指标配置告警。

## 11. 2026-08-02 带宽枯竭事故（双 slave 无法分担压力 + 启动崩溃循环）

### 11.1 结论

rc.19 计费修复发布当天，双 slave 上线后延迟不降反升，一度全站不可访问。
两个独立故障叠加，主因是**带宽**：

- **故障 A（不可访问的直接原因）——启动崩溃循环**：
  `SQL_PG_STATEMENT_TIMEOUT_MS=15000` 曾以 `ALTER ROLE` 持久写入数据库角色
  （集群级生效、删除环境变量不会自动回收），叠加新版 `main.go` 将
  `InitChannelCache` 失败从「容忍重试」改为 `FatalLog` 退出。启动时全量拉取
  channels/abilities 在拥塞链路上超过 15s 被掐 → 进程退出 → `restart: always`
  → 无限崩溃循环。
- **故障 B（根因）——数据库主机公网入口带宽枯竭**：
  154.9.232.11 公网入口的实测单流吞吐 **< 0.42 Mbit/s**（疑似被异常流量挤占）。
  所有节点的 PG + Redis 流量汇聚于同一入口：单 slave（约 0.8 Mbit/s）勉强
  容纳，双 slave 顶穿上限 → 驻留队列 → 每条 SQL 往返被加征 25–55ms 排队税
  → 结算超时、补单风暴、全面变慢。

### 11.2 证据链（全部为现场实测）

| 测量 | 结果 | 推论 |
|---|---|---|
| 空闲时 slave→DB ping | ≈ 1ms | 物理路径近且干净 |
| 业务运行时 ping | 25–55ms，尖峰 180ms | 随流量出现的驻留队列 |
| iftop（单 slave 全部 5432+6379 流量） | 合计 < 1 Mbit/s，重传 0 | 单机流量本身极小 |
| psql 拉取 5MB（slave 走公网） | 120s 未完成，被全局 statement_timeout 掐死 | 有效带宽 < 0.42 Mbit/s |
| psql 拉取 5MB（master 走公网，同机房） | 同样约 2 分钟 | 瓶颈在 DB 主机公网入口，与地理距离无关 |
| 同一 slave 对其他方向吞吐 | 峰值 74 Mbit/s | 非 slave 侧出口限速 |
| 单 slave 运行时 ping 曲线 | 突发数秒抖动后回落 1ms | 拥塞纯由自身流量导致，单机在容量内 |

### 11.3 故障时序（摘要）

| 时间 | 事件 |
|---|---|
| 7/31 17:00 起 | 服务波动开始（后续补偿窗口起点） |
| 8/2 白天 | 三节点滚动更新 rc.19 镜像；slave 进入崩溃循环，全站不可访问 |
| 8/2 下午 | `docker logs` 定位 `InitChannelCache failed` FATAL；`pg_roles` 发现角色级 `statement_timeout=15000ms` 残留 |

| 8/2 傍晚 | 测速链完成，定性带宽枯竭；切换为 1 master + 1 slave 运行 |
| 同期 | tool 站批量补单风暴（15s 超时 + 429 重试环）持续放大拥塞，已要求限速退避 |

### 11.4 与 10.15「带宽打满被否定」的关系（避免误读）

10.15 以「全部网卡合计 < 0.5 MB/s」否定带宽假设，该测量在当时的低负载窗口
成立。本次实测表明：**该入口可用带宽本身仅 1–2 Mbit/s 量级**，0.5 MB/s
（= 4 Mbit/s）的历史观测值实际上已在上限附近。两次结论不矛盾——
问题不是流量太大，而是上限太低。

### 11.5 本轮处置（已全部执行并验证）

1. 数据库：`ALTER ROLE root RESET statement_timeout`（保留 `idle_in_transaction_session_timeout=60s`、`lock_timeout=5s`，已用 `pg_roles.rolconfig` 复核）。
2. slave 配置基线（两台统一）：`SQL_MAX_OPEN_CONNS=15`、`SQL_MAX_IDLE_CONNS=15`、`SYNC_FREQUENCY=300`、`LOG_STAT_ROLLUP_ENABLED=false`、`LOG_STAT_BACKFILL_ENABLED=false`、`REDIS_POOL_SIZE=50`、`BILLING_SETTLEMENT_REPAIR_ENABLED=false`（已验证日志无 `system task runner started`）、移除 `SQL_PG_STATEMENT_TIMEOUT_MS`。
3. 运行拓扑：1 master + 1 slave；**第二台 slave 在带宽问题解决前禁止上线**（双 slave 必顶穿入口，已被数据证明）。
4. rc.19 计费修复的生产验证：`settled` 6626 → 7915，`pending` 回落至 7（全部为历史坏账）；请求路径新产生的超时失败均被 repair 及时兜底，不再积压。

### 11.6 复盘要点（流程失误，必须记录）

1. `ALTER ROLE` 是**集群级持久副作用**：单节点环境变量引入，全部节点受影响，且删除变量不会自动回收。此类角色级 guard 今后只允许 master 设置，引入时必须在文档同时记录回收命令。
2. 新镜像将 `InitChannelCache` 失败改为 fatal，在高延迟链路上被放大为全站不可用。任何「启动步骤 fatal 化」的改动必须评估该步骤是否依赖网络。
3. 发布时未按止血方案调低连接数（仍为 30），发布清单必须逐项核对而非凭记忆。
4. 数据库密码在运维沟通中明文暴露，待轮换。
