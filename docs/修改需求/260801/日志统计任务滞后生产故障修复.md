# 日志统计任务滞后生产故障修复

> 故障时间：2026-07-31  
> 记录日期：2026-08-01  
> 影响接口：`/api/log/stat`  
> 当前状态：已确认直接原因为 master 实时统计 runner 停止；底层进程/容器原因仍需结合 master 日志确认。

## 1. 故障现象与影响

管理员查询当日日志统计时，页面持续显示：

```text
统计任务暂时滞后，请稍后重试
```

已复现的请求区间：

```text
start_timestamp=1785427200  # 2026-07-31 00:00:00 +08:00
end_timestamp=1785504779    # 2026-07-31 21:32:59 +08:00
end_timestamp=1785505167    # 2026-07-31 21:39:27 +08:00
```

受影响的是需要查询最新数据的统计。日志列表和已被 watermark 完整覆盖的
纯历史区间不一定同时失效。

## 2. 生产证据与时间线

### 2.1 聚合状态

首次检查时，两个实时聚合状态一致停留在 `19:56`：

| 状态 | coverage_start | backfill_cursor | watermark |
|---|---:|---:|---|
| `minute` | 1784869200 | 1784869200 | 2026-07-31 19:56:00 |
| `minute_total_v1` | 1784869200 | 1784869200 | 2026-07-31 19:56:00 |

`backfill_cursor = coverage_start` 说明历史回填已完成，故障不是历史回填不足，而是实时
watermark 不再推进。

### 2.2 系统任务

| 任务 ID | 状态 | 关键证据 |
|---:|---|---|
| 28114 | failed | `task lease expired`，说明更早已出现 master 进程、容器或租约心跳中断 |
| 28132 | succeeded | 在 19:57 完成，watermark 推进至 19:56 |
| 28133 | pending | 19:59:04 创建后长时间没有 `locked_by`，证明没有 runner 领取 |
| 28133 | succeeded | master 恢复后在 20:35 处理积压任务，但旧 payload 只把 watermark 推进到 19:58 |
| 28135 | succeeded | 修复区间 `[19:58, 20:36)`，watermark 推进到 20:36 |
| 28136 | succeeded | watermark 正常推进到 20:37，此后再次停止 |

runner ID 在故障期间多次变化，与 master 进程或容器多次重启/替换的现象一致。
第二次查询时，`minute` 与 `minute_total_v1` 仍一致停留在 `20:37`，
距请求结束时间 `21:39:27` 约 62 分钟。

## 3. 原因结论

### 3.1 已确认的直接原因

1. 无维度筛选的管理员统计使用 `minute_total_v1` 分钟总计。
2. 查询只允许从 watermark 之后补查有界的原始日志尾部，默认上限为 10 分钟。
3. master 的 `log_stat_rollup` runner 停止后，watermark 超过 10 分钟未推进，因此需要最新
   数据的请求必然返回“统计任务暂时滞后”。
4. 任务 28133 长时间为 `pending` 且没有 `locked_by`，证明不是任务正在慢速执行，
   而是当时没有可用 master runner 领取它。
5. pending 任务是同类型活跃任务，调度器不会再创建新的 `log_stat_rollup`；必须先恢复
   master runner 并领取已存在的 pending 任务。
6. 直接请求 master 的 HTTP 端口仍能获得业务响应，只能证明 HTTP 服务存活，不能证明
   后台系统任务 runner 正常。本次故障实际上出现了两者健康状态分离。

### 3.2 尚未确认的底层原因

现有数据尚不足以在以下原因中做唯一选择，必须保留 master 当时的容器与应用日志：

- master 容器/进程退出、健康检查重启或 OOM；
- 滚动发布后指定 master 被误设为 `NODE_TYPE=slave`，或最终只剩 slave 实例；
- runner goroutine 因 panic 退出，但 HTTP 服务继续存活；
- runner 卡在没有超时保护的数据库调度/领取查询上；
- master 与其他节点的镜像、数据库入口或运行配置不一致。

未获得对应日志前，不应把某一项写成已确认根因。

## 4. 应急处置

1. 确认全集群只有一个指定 master，且该实例的 `NODE_TYPE` 不是 `slave`。
2. 确认 master 使用与 slave 相同的最新镜像、PostgreSQL 主库入口和配置。
3. 恢复、重启或重新创建正确配置的 master。runner 启动后应先领取已有 pending 任务。
4. 不手工修改 `system_tasks.status`、`active_key` 或两个 watermark；让聚合任务从已确认的
   连续水位自动补算。
5. 旧 pending 任务的 `target_end` 也是旧的：它成功只代表处理了该时点的积压，不代表统计
   立即恢复。必须继续观察后续任务，直到 watermark 进入当前时间前 10 分钟以内。

master 节点建议采集以下信息：

```bash
docker inspect --format \
'status={{.State.Status}} started={{.State.StartedAt}} restarts={{.RestartCount}} oom={{.State.OOMKilled}} exit={{.State.ExitCode}} error={{.State.Error}}' \
<master-container>

docker exec <master-container> sh -lc \
'printf "NODE_TYPE=%s\nNODE_NAME=%s\n" "$NODE_TYPE" "$NODE_NAME"'

docker logs --since "2026-07-31T19:00:00+08:00" <master-container> 2>&1 \
  | grep -E "system task runner started|system task runner query failed|system task scheduler|panic|fatal|OOM|database"
```

## 5. 生产诊断 SQL

### 5.1 聚合水位

```sql
SELECT name,
       coverage_start,
       backfill_cursor,
       watermark,
       to_timestamp(watermark) AT TIME ZONE 'Asia/Shanghai' AS watermark_time,
       EXTRACT(EPOCH FROM NOW())::bigint - watermark AS lag_seconds,
       cleanup_pending,
       cleanup_target,
       to_timestamp(updated_at) AT TIME ZONE 'Asia/Shanghai' AS updated_time
FROM log_stat_rollup_states
WHERE name IN ('minute', 'minute_total_v1')
ORDER BY name;
```

### 5.2 统计任务

```sql
SELECT id, type, status, locked_by,
       payload, state, result, error,
       to_timestamp(created_at) AT TIME ZONE 'Asia/Shanghai' AS created_time,
       to_timestamp(updated_at) AT TIME ZONE 'Asia/Shanghai' AS updated_time
FROM system_tasks
WHERE type IN (
  'log_cleanup',
  'log_stat_rollup',
  'log_stat_backfill',
  'log_stat_total_backfill'
)
ORDER BY id DESC
LIMIT 30;
```

重点异常：

- `log_stat_rollup` pending 超过 2 个调度周期且 `locked_by` 为空；
- 最后一个 rollup 任务的 `updated_at` 超过 10 分钟未变化；
- `task lease expired`；
- `minute` 和 `minute_total_v1` 不同步，或两者同时滞后超过 600 秒。

## 6. 恢复验收

必须同时满足：

1. master 启动日志包含 `system task runner started`。
2. 不再出现长时间无 `locked_by` 的 pending `log_stat_rollup`。
3. 每分钟持续产生新的 `log_stat_rollup` 任务，而不是只在 master 重启后成功一次。
4. `minute` 与 `minute_total_v1` watermark 同步推进。
5. `lag_seconds <= 600` 持续至少 30 分钟。
6. 当日无筛选统计、带支持维度筛选的统计和个人统计都能成功返回。
7. 重启、滚动发布或 master 切换后重复上述检查。

## 7. 待实施的生产修复项

本文档记录已确认故障和修复要求，不把未实施项写成已完成。

### P1：master runner 存活性

- 为调度循环记录最后成功运行时间，并暴露给管理健康检查/监控；
- runner goroutine 异常退出时必须有 panic 日志、自恢复或明确使 master readiness 降级；
- 为调度、pending 查询和领取查询增加有界超时，避免单次 DB 调用无限卡住整个循环；
- 启动时明确记录 master/slave 角色、runner ID 和任务 DB 连接目标的非敏感标识。

### P1：监控与告警

- `minute` 或 `minute_total_v1` 的 `lag_seconds > 600` 立即告警；
- pending `log_stat_rollup` 无 `locked_by` 超过 2 分钟告警；
- 最后成功 rollup 超过 2 分钟没有刷新告警；
- `task lease expired`、runner panic、连续调度查询失败立即告警；
- 监控必须区分“HTTP 存活”与“master 后台任务存活”。

### P2：运维可观测性

- 管理端展示当前 watermark、滞后秒数、最后成功任务和 master runner 状态；
- 保留对普通用户简洁的错误文案，详细原因仅在管理员视图和后端日志中暴露；
- 发布验收必须包含“连续观察 30 分钟”，不能以单个积压任务成功代替 runner 持续
  存活验收。
