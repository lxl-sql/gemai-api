# 通用日志统计预聚合与生产加固

> 日期：2026-07-10  
> 范围：通用日志统计接口、分钟级预聚合、历史回填、日志清理联动、PostgreSQL 生产保护、Default/Classic 前端统计状态。  
> 目标：解决 2 亿行日志库上 `/api/log/stat` 大范围实时聚合导致的长时间 `DataFileRead`、统计查询失败和数据库 IO 争用，并满足 5 万日活、多实例生产部署要求。

## 1. 背景与根因

原统计接口直接对 `LOG_DB.logs` 执行：

```sql
SELECT COALESCE(SUM(quota), 0)
FROM logs
WHERE created_at >= ?
  AND created_at <= ?
  AND type = 2;
```

RPM/TPM 另行执行最近 60 秒的 `COUNT + SUM(tokens)`。

在约 2 亿行 PostgreSQL 日志表上，16 小时时间窗的额度聚合曾持续 70 秒以上，等待状态为 `IO / DataFileRead`。日志列表却可以在约 1～2 秒返回，原因是：

- 列表只读取当前页，并将总数统计封顶为 10000。
- 统计接口没有分页或上限，`SUM(quota)` 必须遍历时间窗内所有消费日志。
- `p`、`page_size` 对统计接口无效。
- 旧实现未绑定 HTTP Context，客户端断开后慢 SQL 仍可能继续执行。
- 数据库错误被统一包装为“查询统计数据失败”，前端无法区分初始化、滞后和数据库故障。

结论：硬件影响执行速度，但根因是在线请求直接聚合海量原始日志。升级磁盘和内存只能暂时缓解，必须从软件架构改为预聚合。

## 2. 总体架构

新增分钟级聚合体系：

```text
LOG_DB.logs
  ├─ 每分钟实时任务：聚合最近窗口、推进 watermark
  ├─ 历史回填任务：由近及远补齐最近 7 天
  └─ 日志清理任务：删除原始日志后同步聚合状态
            ↓
主库 DB.log_stat_rollups
主库 DB.log_stat_minute_totals
主库 DB.log_stat_rollup_states
            ↓
/api/log/stat 与 /api/log/self/stat
  ├─ 完整分钟：查询聚合表
  ├─ 首尾不足一分钟：查询原始日志
  └─ RPM/TPM：最近 60 秒短缓存查询
```

核心原则：

- 原始日志仍写入 `LOG_DB`，不修改既有写入链路。
- 聚合结果写入主库 `DB`，兼容独立日志库和 ClickHouse 日志源。
- 不在每次消费请求中同步更新聚合表，避免请求延迟和热点行竞争。
- 后台任务按时间块读取原始日志，覆盖式写入聚合表，重复执行不会累计翻倍。
- 统计查询绝不回退到危险的原始日志大范围全表聚合。
- 无维度筛选的全站统计读取每分钟总计，避免再次扫描全部维度聚合行。

## 3. 数据模型

### 3.1 `log_stat_rollups`

涉及：

- `model/log_stat_rollup.go`
- `model/main.go`

分钟聚合维度：

- `bucket_start`：分钟起点 Unix 秒。
- `username`
- `token_name`
- `model_name`
- `channel_id`
- `group`

指标：

- `request_count`
- `quota`
- `prompt_tokens`
- `completion_tokens`

所有聚合指标使用 `int64`。

维度唯一键：

```text
SHA-256(username, token_name, model_name, channel_id, group)
```

唯一约束：

```text
(bucket_start, dimension_key)
```

查询索引：

- `(bucket_start, dimension_key)`：时间窗扫描和唯一冲突键。
- `(username, bucket_start)`：个人统计。
- `(model_name, bucket_start)`：模型筛选。

早期方案中的 token、channel、group 复合索引已移除。迁移会幂等检查并删除旧索引；删除失败仅记日志，下次启动重试，不阻塞服务启动。

### 3.2 `log_stat_minute_totals`

每个完整分钟固定一行全站总计（无消费的分钟也写入零值行），主键为
`bucket_start`，指标与维度聚合表一致。实时聚合从已经物化的维度结果在
Go 内累加生成，不会再次查询原始日志。

无 `username`、`token_name`、`model_name`、`channel`、`group` 筛选的管理员
查询使用该表，7 天最多扫描 10080 行。升级回填从现有
`log_stat_rollups` 按分钟汇总，不重新扫描大体量 `logs`。

### 3.3 `log_stat_rollup_states`

状态字段：

| 字段 | 含义 |
|---|---|
| `watermark` | 连续完整覆盖区间上界；实时任务单调推进 |
| `backfill_cursor` | 连续完整覆盖区间下界；回填由近及远逐步下降 |
| `coverage_start` | 当前保留和回填目标下界 |
| `cleanup_pending` | 日志清理进行中或等待对账 |
| `cleanup_target` | 清理目标时间戳，用于进程中断后的自愈对账 |
| `updated_at` | 状态更新时间 |

可查询的完整聚合区间：

```text
[max(backfill_cursor, coverage_start), watermark)
```

`cleanup_pending=true` 时统计接口保守拒绝查询，避免读取清理过程中的中间状态。

状态表包含两套独立覆盖状态：

- `minute`：维度聚合覆盖状态，供带维度筛选的查询使用。
- `minute_total_v1`：全站分钟总计覆盖状态，供无筛选管理员查询使用。

独立状态保证滚动升级时不会把新建但尚未回填的总计表误判为历史数据完整；
总计状态未覆盖所选范围时返回“统计数据正在初始化”，不会回退扫描维度表。

## 4. 实时聚合任务

任务类型：

```text
log_stat_rollup
```

默认每 60 秒由 master 节点调度。

正常行为：

1. 读取当前聚合状态。
2. 如果状态不存在，初始化最近 5 分钟可用区间和 7 天回填目标。
3. 聚合 `[max(旧 watermark, 目标时间-5分钟), 目标时间)`。
4. 每块最大 30 分钟，每次任务最多处理 2 块。
5. 聚合覆盖写与 watermark 推进在主库同一事务提交。
6. watermark 追上当前时间后，根据状态入队历史回填任务。
7. 整点执行过期分钟桶清理。

水位停滞修复：

- master 宕机或任务失败后，从旧 watermark 继续聚合。
- 每轮最多修复 2×30 分钟，避免恢复时持续打满日志库。
- 块间默认暂停 250 毫秒。
- 未追平时不启动历史回填，优先恢复最新数据。

任务开关：

```text
LOG_STAT_ROLLUP_ENABLED=true
```

关闭后：

- 不再创建或执行实时聚合任务。
- 统计接口明确返回“统计功能已被管理员停用”。
- 不回退到原始日志全表扫描。

## 5. 历史回填任务

任务类型：

```text
log_stat_backfill
log_stat_total_backfill
```

行为：

- 回填方向为由近及远，最近历史最先可查。
- 默认每块 30 分钟。
- 默认每次任务最多处理 2 块。
- 每块成功后，聚合覆盖写与 cursor 下压在同一 CAS 事务中完成。
- 每块重新读取状态，日志清理或 prune 改变边界后会按新状态停止或继续。
- 块间暂停不小于块本身耗时，占空比不超过约 50%。
- 本轮最后一块后不暂停，尽快释放维护锁。
- `log_stat_total_backfill` 专用于升级和补洞，从已经完整的
  `log_stat_rollups` 汇总分钟总计，不读取原始日志；其独立 cursor 只能推进到
  当前维度聚合已经覆盖的下界。

高基数保护：

- SQL 使用 `LIMIT max+1` 限制传入 Go 内存的分组结果。
- 默认最大分组数为 100000。
- 超限后自动将块大小减半重试。
- 最小缩到 1 分钟。
- 截断结果绝不写入数据库。
- 1 分钟仍超限时任务失败并告警，需要评估维度基数或提高上限。

回填开关：

```text
LOG_STAT_BACKFILL_ENABLED=true
```

关闭后：

- 实时统计继续运行。
- 未覆盖的历史范围返回“所选时间范围暂无统计数据”，不会永久显示“初始化中”。
- 整点 prune 仍执行，聚合表不会无限增长。

## 6. 共享维护锁与并发一致性

实时聚合、历史回填和日志清理共享：

```text
log_stat_maintenance
```

维护锁存放在 `system_task_locks`：

- 多 master 场景下仍全局互斥。
- TTL 60 秒，每 20 秒续租。
- 等待维护锁期间，任务自己的租约仍持续续租。
- 锁续租失败会取消任务 Context。
- 任务退出后释放维护锁。

该锁保证：

- cleanup 不会与 live/backfill 同时写聚合数据。
- backfill 不会重新写回 cleanup 已删除的分钟桶。
- prune 不会与在途回填块并发提交。

CAS 事务进一步校验：

- 当前 `backfill_cursor` 必须等于待提交块的 `chunkEnd`。
- `chunkStart` 不得早于最新 `coverage_start`。
- 状态变化时整块事务回滚，不会出现“聚合已写、cursor 未动”。

## 7. 日志清理联动与崩溃自愈

涉及：

- `service/system_task.go`
- `service/log_stat_rollup.go`
- `model/log.go`
- `model/log_stat_rollup.go`

两条清理路径：

- Default：异步 `log_cleanup` SystemTask。
- Classic：旧版同步 `DELETE /api/log/`。

清理流程：

1. 获取共享维护锁。
2. 设置 `cleanup_pending=true` 和 `cleanup_target`。
3. 分批删除 `created_at < target_timestamp` 的原始日志。
4. 清理期间统计接口返回“统计任务暂时滞后”。
5. 清理完成后：
   - 删除清理边界之前的聚合桶。
   - 从 `target_timestamp` 开始重算边界分钟。
   - 推进 `coverage_start` 和 `backfill_cursor`。
   - 清除 `cleanup_pending` 和 `cleanup_target`。

失败处理：

- 任意提前退出都会在 defer 中尝试幂等对账。
- 旧版同步接口请求断连后使用独立 1 分钟 Context 兜底对账。
- 如果进程直接崩溃，状态表保留 `cleanup_target`。
- 下一次实时聚合任务取得维护锁后自动重新对账。
- 自愈失败则保留 pending，下一分钟继续重试，不返回错误统计数据。

边界分钟重算从 `target_timestamp` 开始，而不是从整分钟起点开始，避免清理中断时将“部分删除”的污染区间重新计入。

旧版本升级边界：

- 如果存在 `cleanup_pending=true` 但 `cleanup_target=0` 的旧状态，无法恢复原目标。
- 实时任务会记录告警并清除旧标志。
- 部署前应确保没有正在执行的旧版日志清理；若发生该情况，升级后手动重新执行一次日志清理。

## 8. 过期聚合数据清理

整点触发 prune：

```text
cutoff = 当前完整分钟 - 7天 - 1小时缓冲
```

行为：

- 删除 `bucket_start < cutoff`。
- 推进 `coverage_start`。
- 必要时将 `backfill_cursor` 抬到新边界。
- 回填未完成或被停用时也照常执行，防止聚合表无限增长。
- prune 与 backfill 共享维护锁，CAS 保证不会提交跨边界旧块。

1 小时缓冲用于避免默认“最近 7 天”查询恰好踩在清理边界。

## 9. 统计查询流程

### 9.1 管理员

```text
GET /api/log/stat
```

鉴权与限流：

- `AdminAuth`
- `SearchRateLimit`

管理员不传 `username` 时统计全站；传入用户名后统计指定用户。

### 9.2 用户自己

```text
GET /api/log/self/stat
```

鉴权与限流：

- `UserAuth`
- `SearchRateLimit`

用户名来自认证上下文：

```go
username := c.GetString("username")
```

客户端不能通过 query 参数伪造其他用户名。

个人额度、RPM 和 TPM 都会强制带当前用户名过滤，不是全站值。

### 9.3 额度统计

时间归一化：

- `start_timestamp=0`：使用 `LOG_QUERY_DEFAULT_DAYS`，默认最近 7 天。
- 如果 `LOG_QUERY_DEFAULT_DAYS<=0`：收敛为当前已覆盖聚合区间，绝不扫原始日志全表。
- `end_timestamp=0` 或未来时间：钳到当前时间。

查询分段：

1. 无维度筛选的完整分钟：从 `log_stat_minute_totals` 求和。
2. 带任意维度筛选的完整分钟：从 `log_stat_rollups` 求和。
3. 首分钟碎片：从原始日志聚合。
4. 末分钟碎片或 watermark 后短尾：从原始日志聚合。
5. 原始补算总时长默认不得超过 10 分钟。

门禁：

- 状态未初始化：返回“统计数据正在初始化”。
- 清理进行中：返回“统计任务暂时滞后”。
- 查询起点早于当前覆盖下界：
  - 回填启用且尚未完成：返回“正在初始化”。
  - 回填关闭或超出保留范围：返回“所选时间范围暂无统计数据”。
- 实时聚合关闭：返回“统计功能已被管理员停用”。

查询总超时默认 10 秒，并绑定 HTTP Context。

### 9.4 RPM/TPM

RPM/TPM 语义固定为当前最近 60 秒，与页面选择的历史时间范围无关。

用户个人查询实际 SQL 语义：

```sql
WHERE type = 2
  AND username = 当前登录用户
  AND created_at >= now - 60s
  AND created_at < now + 1s
```

继续应用可选的模型、令牌、渠道和分组筛选。

缓存：

- 进程内 TTL 10 秒。
- 最大 2048 个筛选组合。
- singleflight 合并相同 key 的并发请求。
- 缓存 key 包含 `model + username + token + channel + group`，不同用户不会串数据。
- 满容量时整体清空，singleflight 仍可避免同 key 击穿。

失败降级：

- RPM/TPM 查询失败或超时，不影响已计算的 quota。
- quota 正常返回，RPM/TPM 降级为 0，并记录后端告警。

## 10. 错误、限流与国际化

后端错误使用哨兵值，并由 controller 映射为 i18n：

| 错误 | 用户语义 |
|---|---|
| `ErrLogStatInitializing` | 统计数据正在初始化 |
| `ErrLogStatRangeUnavailable` | 所选时间范围暂无统计数据 |
| `ErrLogStatLagging` | 统计任务暂时滞后 |
| `ErrLogStatInvalidRange` | 无效的统计时间范围 |
| `ErrLogStatQueryFailed` | 查询统计数据失败 |
| `ErrLogStatDisabled` | 统计功能已被管理员停用 |

后端语言：

- English
- 简体中文
- 繁体中文

前端新增文案覆盖：

- en
- zh
- zh-TW
- fr
- ja
- ru
- vi

统计接口使用用户级 `SearchRateLimit`：

- 默认 10 次 / 60 秒 / 用户。
- 超限返回 HTTP 429。
- Default 前端不自动重试 429，并显示“Too many requests”。

## 11. 前端行为

### 11.1 Default

- 统计加载时显示 skeleton。
- 业务失败、网络错误、超时不再伪装成 0。
- 非消费日志类型不发统计请求，显示“统计仅支持消费日志”。
- 筛选变化时不保留上一组统计，避免展示错误条件的数据。
- 统计请求跳过全局 toast，由组件内联展示状态。

### 11.2 Classic

- 非 `type=0/2` 时不发统计请求。
- 非消费类型、业务失败和网络错误都会隐藏旧统计面板。
- 不会继续显示与当前筛选不一致的 quota/RPM/TPM。

## 12. 数据库与跨库兼容

主库支持：

- SQLite
- MySQL 5.7.8+
- PostgreSQL 9.6+

日志源支持：

- SQLite
- MySQL
- PostgreSQL
- ClickHouse

分钟分桶表达式按日志库方言处理：

```text
SQLite      created_at - (created_at % 60)
MySQL       created_at - MOD(created_at, 60)
PostgreSQL  created_at - MOD(created_at, 60)
ClickHouse  intDiv(created_at, 60) * 60
```

独立 PostgreSQL 日志库：

- 支持 `LOG_SQL_PG_IDLE_IN_TX_TIMEOUT_MS`
- 支持 `LOG_SQL_PG_LOCK_TIMEOUT_MS`
- 支持 `LOG_SQL_PG_STATEMENT_TIMEOUT_MS`
- 优先应用数据库级角色设置。
- 不支持或权限不足时回退为角色级设置，并记录告警。

主库 PostgreSQL 对 `log_stat_rollups` 和 `log_stat_minute_totals` 设置更积极的 autovacuum，降低覆盖式 DELETE+INSERT 带来的死元组膨胀。

## 13. 生产容量评估（5 万日活）

假设：

- 5 万日活用户。
- 人均 50～100 次消费请求/天。
- 日消费日志约 250 万～500 万。
- 原始日志表约 2 亿行。

聚合表预计：

| 每分钟去重维度组合 | 7 天行数 | 含索引粗略存储 |
|---|---:|---:|
| 500 | 约 500 万 | 约 2 GB |
| 2000 | 约 2000 万 | 约 8 GB |
| 3000～10000 | 3000 万～1 亿 | 12～40 GB |

首次 7 天回填：

- 预计 6～12 小时。
- 实际取决于 7 天内日志量、维度基数、磁盘 IO 和 PostgreSQL `work_mem`。
- 回填期间最近范围优先可用。
- 日志库 IO 紧张时可关闭历史回填，实时聚合继续运行。

单用户查询：

- 主库使用 `(username, bucket_start)` 索引。
- 典型扫描量为该用户数百到数万条聚合行。
- 预期毫秒到百毫秒级。

全站管理员查询：

- 使用 `log_stat_minute_totals` 的 `bucket_start` 主键范围。
- 7 天固定最多扫描 10080 行，不随用户名、模型、令牌等维度基数增长。
- 带任意维度筛选时仍使用 `log_stat_rollups` 及对应索引。

## 14. 生产配置建议

### 14.1 必须配置

```env
# 全集群只能有一个非 slave 节点运行任务
NODE_TYPE=slave # 仅从节点设置；主节点不设或设 master

# PostgreSQL 每实例连接池
SQL_MAX_OPEN_CONNS=30
SQL_MAX_IDLE_CONNS=10
SQL_MAX_LIFETIME=60

# 多实例共享限流
REDIS_CONN_STRING=redis://...

# 独立 PostgreSQL 日志库
LOG_SQL_PG_STATEMENT_TIMEOUT_MS=180000
LOG_SQL_PG_LOCK_TIMEOUT_MS=5000
LOG_SQL_PG_IDLE_IN_TX_TIMEOUT_MS=60000
```

必须满足：

```text
实例数 × SQL_MAX_OPEN_CONNS < PostgreSQL max_connections - 运维预留
```

### 14.2 建议初始值

```env
LOG_STAT_ROLLUP_ENABLED=true
LOG_STAT_BACKFILL_ENABLED=true
LOG_STAT_BACKFILL_CHUNK_MINUTES=30
LOG_STAT_BACKFILL_MAX_CHUNKS_PER_RUN=2
LOG_STAT_BACKFILL_PAUSE_MS=250
LOG_STAT_REPAIR_MAX_CHUNKS_PER_RUN=2
LOG_STAT_REPAIR_PAUSE_MS=250
LOG_STAT_CHUNK_TIMEOUT_SECONDS=120
LOG_STAT_MAX_GROUPS_PER_CHUNK=100000
LOG_STAT_QUERY_TIMEOUT_SECONDS=10
LOG_STAT_RAW_TAIL_MAX_MINUTES=10
SEARCH_RATE_LIMIT_ENABLE=true
SEARCH_RATE_LIMIT=10
SEARCH_RATE_LIMIT_DURATION=60
```

日志库 IO 紧张时：

```env
LOG_STAT_BACKFILL_ENABLED=false
```

或降低：

```env
LOG_STAT_BACKFILL_MAX_CHUNKS_PER_RUN=1
LOG_STAT_BACKFILL_CHUNK_MINUTES=10
```

## 15. 监控与告警

### 15.1 Watermark 滞后

```sql
SELECT
  name,
  watermark,
  EXTRACT(EPOCH FROM NOW())::bigint - watermark AS lag_seconds,
  cleanup_pending,
  cleanup_target,
  updated_at
FROM log_stat_rollup_states
WHERE name = 'minute';
```

告警：

```text
lag_seconds > 600
```

超过 10 分钟后，需要最新数据的统计请求会开始返回“暂时滞后”。

### 15.2 回填进度

```sql
SELECT
  coverage_start,
  backfill_cursor,
  watermark,
  backfill_cursor - coverage_start AS remaining_seconds
FROM log_stat_rollup_states
WHERE name = 'minute';
```

`remaining_seconds > 0` 持续超过 24 小时需要告警。

### 15.3 清理状态

```sql
SELECT *
FROM log_stat_rollup_states
WHERE name = 'minute'
  AND cleanup_pending = true
  AND updated_at < EXTRACT(EPOCH FROM NOW())::bigint - 600;
```

正常情况下实时任务会在下一分钟自愈；持续 10 分钟说明自愈也失败。

### 15.4 任务失败

```sql
SELECT type, status, COUNT(*), MAX(updated_at) AS last_at
FROM system_tasks
WHERE type IN ('log_stat_rollup', 'log_stat_backfill', 'log_stat_total_backfill', 'log_cleanup')
  AND updated_at > EXTRACT(EPOCH FROM NOW())::bigint - 3600
GROUP BY type, status;
```

1 小时内出现 failed 即告警。

### 15.5 聚合表体量

```sql
SELECT
  COUNT(*) AS rows,
  COUNT(DISTINCT bucket_start) AS minute_buckets,
  pg_size_pretty(pg_total_relation_size('log_stat_rollups')) AS total_size
FROM log_stat_rollups;

SELECT
  COUNT(*) AS rows,
  MIN(bucket_start) AS first_bucket,
  MAX(bucket_start) AS last_bucket,
  pg_size_pretty(pg_total_relation_size('log_stat_minute_totals')) AS total_size
FROM log_stat_minute_totals;
```

参考告警：

- 行数超过 5000 万。
- 总体积超过 30 GB。

### 15.6 维护锁

```sql
SELECT *
FROM system_task_locks
WHERE type = 'log_stat_maintenance'
  AND locked_until > EXTRACT(EPOCH FROM NOW())::bigint;
```

持续长时间持锁说明 cleanup 或聚合块耗时异常。

### 15.7 日志关键字

建议采集：

- `log stat backfill chunk done`
- `log stat total backfill chunk done`
- `log stat chunk truncated, shrinking chunk`
- `failed to self-heal interrupted log cleanup`
- `failed to query pre-aggregated log stat`
- `failed to query raw log stat boundary`
- `failed to query rpm/tpm stat (degraded to zero)`
- `log stat maintenance lock renewal failed`

## 16. 部署步骤

1. 确认主库和日志库备份可用。
2. 确认全集群仅一个 master。
3. 下调每实例 PostgreSQL 连接池。
4. 配置共享 Redis。
5. 配置日志库 statement timeout。
6. 在低峰期滚动或蓝绿发布。
7. AutoMigrate 自动创建维度聚合、分钟总计、聚合状态三张小表和索引，不会给 2 亿行 `logs` 自动创建重索引。
8. 启动后检查：
   - `system task runner started`
   - `log_stat_rollup` 任务成功
   - watermark 每分钟推进
9. 观察 24 小时：
   - 水位滞后
   - 回填 remaining
   - 日志库 CPU/IO
   - chunk timeout/truncated
   - HTTP 429 比例
10. 回填完成后抽样对比原始日志与聚合结果。

## 17. 回滚

回滚旧二进制即可：

- 旧版本不会读取聚合表。
- 新增表可保留，不影响原日志写入。
- 回滚后统计接口会恢复旧版原始日志实时聚合，因此可能重新出现慢查询。

紧急情况下也可以仅关闭：

```env
LOG_STAT_BACKFILL_ENABLED=false
```

保留最近实时统计，暂停历史回填 IO。

## 19. 已知限制与后续优化

### 19.1 已知限制

- 统计为最终一致，通常延迟约 1 分钟。
- RPM/TPM 最多缓存约 10 秒。
- master 无自动选举，宕机后需人工提升 slave。
- 用户隔离当前基于 `username`，用户改名后旧用户名下历史统计不会自动归并。
- RPM/TPM 缓存达到 2048 个筛选组合后整体清空，singleflight 可防同 key 击穿，但命中率会下降。
- 高基数全站管理员查询成本高于个人查询。
- 无法对任何生产系统承诺绝对零 bug；本方案通过超时、限流、内存上限、租约、自愈、停用开关和可回滚设计限制故障影响。

### 19.2 后续可选优化

- 聚合维度增加 `user_id`，解决用户名修改和复用问题。
- 为 master 增加自动选举或高可用任务调度。
- RPM/TPM 缓存改为 LRU 或 Redis 滑动窗口。
- 为统计接口增加稳定 `error_code`，前端不再依赖后端 message 文本。
- 使用真实 PostgreSQL/MySQL/ClickHouse 环境执行周期性集成测试。
- 在监控系统中增加 watermark、backfill、chunk duration 和 groups/chunk 指标。
