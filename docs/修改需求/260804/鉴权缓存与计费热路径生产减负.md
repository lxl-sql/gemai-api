# 鉴权缓存与计费热路径生产减负

> 文档日期：2026-08-04  
> 适用拓扑：多个应用实例共享 PostgreSQL 与 Redis  
> 发布判定：代码可进入单 slave 灰度；多实例全量发布仍以生产观测通过为准。

> **长期架构约束：生产环境必须支持多 slave 节点集群。** 单节点仅用于灰度、
> 故障隔离和容量对照，不能作为功能设计、并发正确性或正式发布的成立前提。
> 当前生产数据库采用 PostgreSQL 直连；每个 slave 都有独立的 Go SQL/Redis
> 连接池，但共享同一套 PostgreSQL 数据和 Redis 缓存。

## 一、背景与目标

2026-07-31 更新后，数据库服务器经 Tailscale 接收的 PostgreSQL 流量出现明显抬升和抖动。现场确认 5432 流量是主要来源之一，并观察到两台以上 slave 同时接入时数据库往返延迟显著上升。

本次只处理已确认、可小范围证明安全的热路径放大器：

1. 计费会话在鉴权已读取用户余额后，又重复读取一次用户余额；
2. `MarkBillingReservationDispatched` 为一次状态更新开启完整计费事务；
3. 同一实例内，热门 token 或用户缓存同时失效时，多个请求会并发回源数据库；
4. 同一请求在预扣和最终结算后重复删除额度缓存，造成多 slave 同时回源和 5432 流量尖峰。

目标是减少重复 SQL、事务往返和缓存击穿尖峰。此次不承诺单独消除全部带宽波动：日志统计、正常业务响应体、缓存主动失效以及跨实例同时回源仍可能产生流量，必须以相同 RPM 下的生产前后数据验收。

## 多 slave 强制设计约束（长期有效）

后续涉及鉴权、额度、计费、缓存、锁、后台任务和数据库连接池的修改，必须同时满足：

1. 正确性不能依赖单进程内存锁、单进程 singleflight、固定请求顺序或“只有一台实例”；进程内合并只能用于减负，不能承担额度、幂等或缓存一致性。
2. 所有实例共享 Redis，任意实例执行缓存删除或重建都会影响其他实例；必须审计“提交、删除、并发重建、再次提交”的交错顺序。
3. PostgreSQL 是用户余额、token 额度和 reservation 状态的唯一权威来源；缓存只能用于预检查和展示，不能绕过事务内原子余额守卫。
4. 数据库连接池和 Redis 连接池按“每实例配置 × 实例数量”核算总预算；新增 slave 不得假定只增加吞吐而不增加数据库往返、连接和带宽。
5. master 负责迁移和 master-only 系统任务；公网 slave 默认不得执行 billing repair，除非被明确指定为故障接管节点并完成同地域、容量和互斥验证。
6. 发布验证必须至少包含一台灰度 slave 和两台并发 slave 两个阶段；单机测试、SQLite 测试或单 slave 低延迟不能代替多实例共享 PostgreSQL/Redis 验收。
7. 当前生产不使用 PgBouncer。后续优化不能依赖 PgBouncer 的事务池、会话复用或配置语义；若重新引入，必须作为独立变更重新验证。

## 二、修改内容

### 2.1 复用鉴权额度快照

- 钱包预检查优先复用 Gin 上下文中已经存在且足以覆盖本次预扣的 `ContextKeyUserQuota`；
- 快照为 `0` 或不足时重新读取一次最新额度，避免鉴权后发生的充值、退款或补偿被旧请求快照误判为 403；
- 二次额度确认使用请求 Context，客户端取消后不再继续等待 Redis 或 PostgreSQL；
- 非 HTTP 调用或上下文未提供额度时，保留原数据库读取兜底；
- 该快照仅用于提前拒绝提示，预扣费事务内的原子余额条件仍是唯一权威校验。

效果：正常 token 请求少一次用户额度读取，同时不改变实际扣费依据。

### 2.2 dispatched 状态改为单条条件更新

- `reserved/dispatched -> dispatched` 改为关闭 GORM 默认事务的条件 `UPDATE`；
- 复用公共的额度操作超时上下文，仍受 `SQL_QUOTA_TX_TIMEOUT_SECONDS` 约束；
- 正常路径不再执行 `BEGIN`、两条 `SET LOCAL` 和 `COMMIT`；
- 只有条件更新未命中时才补一次只读查询，继续区分“记录不存在”和“已进入结算”的原有错误；
- 数据库时间校准逻辑保留，不改租约时钟语义。
- 条件更新未命中时读取当前状态；`reserved/dispatched` 按幂等成功处理，避免 MySQL 将“匹配但值未变化”报告为 0 行后被误判为已进入结算。

效果：减少每请求 dispatched 阶段的数据库往返和连接占用时间，不改变预扣、结算、退款或 repair 状态机。

PostgreSQL 注意事项：自动提交 UPDATE 已没有事务内 `SET LOCAL lock_timeout`。代码仍有默认 15 秒的应用级总超时，因此不会无限占用连接；但生产希望维持的 5 秒行锁等待上限依赖角色级 `lock_timeout=5000ms`。该角色配置属于生产必需项，不得 `RESET` 或删除。master 启动会尝试重新写入角色默认值，slave 不会写入；写入失败也只记录日志。因此每次发布必须检查 master 启动日志，并从新建连接执行：

```sql
SHOW lock_timeout;
```

结果不是 `5s`（或部署明确配置的 `SQL_PG_LOCK_TIMEOUT_MS`）时，不得扩大灰度。若运维策略不允许持久化角色级配置，应回退此优化或另行设计同连接的语句级保护，不能假定应用 15 秒总超时等价于 5 秒锁超时。

### 2.3 token/user 缓存回源合并

- 提取公共 `coalesceAuthCacheLoad`，token 与用户使用独立命名空间；
- 同一应用进程、同一个 token 指纹或 user ID 在缓存未命中时只执行一轮数据库回源；
- 进入共享回源后再次检查 Redis，避免排队期间缓存已恢复仍重复查库；
- token 的 singleflight key 使用 HMAC 指纹，不把明文密钥放入进程级合并键；
- 外层 token/user Redis Hash 读取使用请求 Context，客户端取消可中断尚未完成的缓存读取；
- 进入 singleflight 后，取消方停止等待，但不取消其他请求仍依赖的共享回源；
- 共享结果返回前复制对象，避免请求间共享可修改的指针字段；
- 旧的 `GetTokenByKey`、`ValidateUserToken`、`GetUserCache` 接口保留，新增 Context 版本供 HTTP 鉴权链使用。

该合并只作用于单进程，不是分布式锁。不同 slave 仍可能各执行一次回源，因此不会引入跨实例锁等待，也不会改变 Redis 数据格式或 TTL。

### 2.4 预扣暂不删除，最终结算单次精确失效

- 新 reservation 预扣成功后不立即删除 user/token 缓存；请求执行期间缓存可能短暂保留预扣前快照；
- reservation 增加预扣成功后同样不立即删除，统一交给最终结算处理；
- 结算事务把“预扣已经修改过的额度”和“结算差额实际修改的额度”合并记录，事务成功提交后每类缓存最多删除一次；
- 即使 `actual_quota == reserved_quota`，最终结算仍删除一次对应缓存，因为数据库里的预扣额度已经发生变化；
- 只涉及钱包时只删除 user 缓存；playground 不删除 token 缓存；订阅请求只删除实际参与预扣的 token 缓存；
- token 在请求执行期间被删除时，最终结算不阻断钱包结算；已有的 token 缓存失效标记仍保留，避免把预扣阶段的额度变化漏掉；
- token 密钥在请求执行期间轮换时，最终失效按数据库中的当前 `key/key_hash` 处理，不只删除请求开始时的旧 key；
- 幂等复用、已完成 reservation 重放、事务错误和提交结果不确定继续保守完整失效，用于修复“数据库可能已提交、进程尚未来得及删缓存”的崩溃窗口；
- 普通请求、Task、Midjourney 和 repair 共用同一套提交后失效规则。

该修改不向 Redis 增量写额度，也不改变 PostgreSQL 的权威余额校验。请求执行期间缓存偏高只会让预检查继续进入权威预扣事务，事务内的非负余额条件仍会拒绝真正的透支；缓存 TTL 继续由现有同步频率约束。代价是余额展示在长流式请求结束前可能短暂偏旧，换取一次请求不再触发“预扣删除并重建、结算再次删除并重建”的缓存抖动。

## 三、明确未修改的安全边界

本次没有实施以下高风险优化：

- 不合并“持久化预扣意图”和“应用结算”两个阶段；
- 不修改用户或 token 的扣费 SQL、幂等键和冲突分类；
- 不用 `HINCRBY` 增量修补余额缓存；
- 不在预扣提交后发布新的缓存余额，也不让缓存承担防超扣职责；
- 不跳过最终结算失效；预扣实际修改过的额度即使最终差额为零也必须在结算后删除一次；
- 幂等重放和事务错误仍保守完整失效；
- 不改变 repair worker、system task runner 或审计链；
- 不增加数据库表、索引、迁移、Redis Key 或分布式锁。

因此，本次修改不会产生新的扣费入口，也不会把缓存余额提升为权威余额。多扣费防线仍由 reservation 幂等记录、条件更新和结算状态机承担。

## 四、并发、缓存与锁风险结论

| 风险 | 处理方式 | 结论 |
|---|---|---|
| 缓存击穿 | 单进程同键合并，回源前二次查 Redis | 降低尖峰，不改变缓存内容 |
| 共享对象被请求修改 | token 返回前深复制指针字段，用户缓存按值返回 | 请求间隔离 |
| 请求取消拖住共享任务 | 外层 Redis 读取可取消；共享加载与单个请求取消解耦 | 不扩大取消影响面 |
| 数据库锁等待 | dispatched 使用有界自动提交 UPDATE；PG 角色级 lock_timeout 保持 5 秒 | 比原完整事务持锁窗口更短 |
| 多扣或重复结算 | 未改 reservation 创建、应用、退款、repair 与幂等条件 | 计费语义不变 |
| 请求执行中缓存暂时偏高 | 预扣事务仍使用 PostgreSQL 原子非负条件；最终结算删除一次；保留 TTL | 可能多一次被事务拒绝的尝试，不会据此超扣 |
| 零差额结算 | 预扣已改变数据库额度，最终仍删除 user/token 各一次 | 不漏掉延期的预扣失效 |
| 幂等重放或提交结果不确定 | 完整失效 user/token | 保留崩溃恢复能力 |
| 多 slave 同时重建 | 每个进程只做本地 singleflight；最终单次删除减少失效轮数 | 不宣称跨进程只回源一次，仍以 PG 为权威 |
| 跨库兼容 | 使用 GORM 条件更新，未增加方言专属 SQL | SQLite/MySQL/PostgreSQL 路径保留 |

## 六、生产灰度与停止条件

### 6.1 发布前基线

在相近 RPM、相近模型和流式比例下至少记录 10 分钟：

- 数据库主机 5432/Tailscale 每秒入站和出站；
- PostgreSQL `active`、`idle in transaction`、`ClientRead`、锁等待；
- PgBouncer（如启用）的 `cl_active`、`cl_waiting`、`sv_active`、`sv_idle`；
- 接口 P50/P95/P99、401/403/5xx；
- `billing_settlement_failures` 新增速率、pending 数量；
- reservation 的 reserved/dispatched/settling 超期数量；
- 用户余额、token 余额、消费日志抽样对账。

### 6.2 灰度顺序

1. 构建不可变镜像并记录镜像 digest；不要直接用无法追溯内容的浮动 `latest` 判断回滚版本。
2. 在 Linux 构建机完成 `go test -race ./model ./service -count=1`。
3. 使用新建 PostgreSQL 连接确认 `SHOW lock_timeout` 与 `SQL_PG_LOCK_TIMEOUT_MS` 一致。
4. 只更新一台 slave，保持 master 和其余 slave 不变。
5. 导入小比例真实流量，至少观察 30 分钟；同时覆盖流式、非流式、按次计费、退款和错误请求。
6. 核对同 RPM 下 5432 流量、SQL 延迟和失败率，不只看 ICMP ping。
7. 第一台通过后逐台更新，每批完成一个完整观察窗口后再继续。
8. 最后更新 master，并确认 system task 与 repair 仍只按既有配置运行。

滚动发布期间，新 slave 创建的 reservation 若异常中断，旧 master 的 repair 可能不知道预扣失效已被延期；此时 Redis 可能保留偏高快照直到现有 TTL 到期，但 PostgreSQL 事务守卫仍会拒绝透支，不会因此多扣。不要长期混跑版本；灰度通过后应在受控窗口内完成 master/repair 节点收敛，并在混跑期间重点观察预扣失败率、锁等待和缓存 TTL。

出现任一情况立即停止扩大灰度并回滚该批：

- 余额、token 额度、消费日志或 reservation 出现无法解释的不一致；
- settlement failure 新增速率或 pending 持续高于基线；
- 403、5xx、重复扣费投诉明显增加；
- `idle in transaction`、锁等待、PgBouncer waiting 或 SQL P95 持续上升；
- 同 RPM 下 5432 带宽或连接等待持续高于旧版本，而非短时采样尖峰。

## 七、回滚

- 直接回滚到上一个已知镜像 digest；
- 本次没有数据库结构变化，不需要回滚 DDL；
- 本次没有 Redis 数据结构变化，不清空 Redis，不执行 `FLUSHALL`；

## 八、发布结论

此次是低风险减负补丁：正常请求减少重复额度查询，dispatched 阶段缩短为有界条件更新，缓存同时失效时限制单实例回源并发，并把同一 reservation 的额度缓存失效收敛到最终结算一次。它针对 7 月 31 日后出现的数据库流量放大器，预计降低 PostgreSQL 基础流量和尖峰，但不能在无生产对照数据时承诺恢复到固定 Mbps。

代码与本地回归达到单 slave 灰度条件；只有灰度对账、失败水位、锁等待和同 RPM 带宽全部通过后，才能判定多实例生产可用。

## 九、缓存修改强制审计清单

以后修改用户或 token 缓存前，必须逐项回答并写入对应测试或修改说明：

1. **为什么需要失效**：本次事务实际修改了哪个缓存字段；只改 reservation、日志或审计状态时，不得顺带删除 user/token 缓存。
2. **失效范围是否最小**：只修改用户余额时不得删除 token；只修改 token 额度时不得删除 user；两个都没有变化时不得执行额度缓存失效。
3. **失效时机是否正确**：数据库事务提交前不得发布新缓存值；提交结果不确定或事务报错时保留保守失效，不能为了性能跳过。
4. **是否可能重复失效**：预扣、dispatch、结算、退款、repair、审计和幂等复用路径要分别列出，避免同一次没有额度变化的状态转换重复删除完整 Hash。
5. **重建是否存在竞态**：必须覆盖“A 读旧数据库快照、B 提交并删除、A 随后写回旧缓存”的跨实例交错；普通 singleflight 不能解决该问题。
6. **token 轮换是否安全**：需要删除 token 缓存时必须以事务时刻或结算时刻的当前 key/key_hash 为准，不能只使用请求开始时保存的旧凭证。
7. **是否会重复应用额度差额**：未经版本号、Lua/CAS 和全字段一致性设计，不得用 `HINCRBY` 在删除/重建并存的路径中直接修补余额。
8. **失败方向是否安全**：缓存偏高只能导致权威事务再次拒绝；缓存偏低可能造成用户误 403。两种方向都要有并发回归测试和 TTL/修复策略。
9. **多实例是否验证**：至少覆盖两个独立进程共享 Redis/PG 的缓存 miss、重建、key 轮换、预扣、结算、退款和 repair，不得只验证单进程并发。

## 十、建议的下一步修复顺序

### 第一优先级：预扣延期、最终单次精确失效（已实施，待生产灰度）

该项已在代码中实施，仍须按第六节完成单 slave、双 slave 灰度后才能视为生产验证通过：

- 新预扣和后续增加预扣成功后暂不删除额度缓存；
- 在结算事务结果中同时记录预扣已经修改的额度与结算差额实际修改的额度，不在事务外凭请求参数猜测；
- 成功提交后，只有钱包参与过预扣/结算才删除 user 缓存，只有 token 参与过预扣/结算才删除 token 缓存，每类最多一次；
- `actual_quota == reserved_quota` 时仍执行最终单次失效，不能把延期的预扣失效漏掉；
- token 确实变化时继续取得结算时刻的当前 key，保留 `RotateTokenKey` 并发安全；PostgreSQL 可评估在额度 UPDATE 上使用 `RETURNING key`，其他数据库保留兼容路径；
- 事务错误、提交结果不确定或无法证明变化范围时，继续执行当前的保守全失效，不用性能优化冒资金一致性风险。

该项不修改两阶段 intent/apply、幂等键、退款或 repair 的业务语义，预期把普通钱包请求从“预扣后 user/token 各删一次，结算后再各删一次”收敛为“最终结算后 user/token 各删一次”。零差额请求的删除总数不变，但失效时机后移，避免请求执行期间先重建再被结算删除；有差额请求则直接减少一整轮删除和回源。

必须增加以下回归：

- 新预扣和增加预扣均不删除 Redis，最终结算删除一次；
- 零差额结算仍删除预扣实际修改过的 user/token 缓存；
- 仅用户变化只删除 user；仅 token 变化只删除 token；两者变化分别失效；
- token 结算期间轮换 key 时只清理正确的当前凭证缓存；
- 事务失败和模拟不确定提交仍执行保守失效；
- 两个实例交错结算同一用户/不同 request_id 不出现多扣、漏扣或错误保留缓存。

### 第二优先级：减少 PostgreSQL 固定往返

在第一项灰度稳定后，再分别实施并独立提交：

1. PostgreSQL 分支把两条事务级 `SET LOCAL` 合并为一条语句，但保留 lock/idle-in-transaction 两个保护语义；
2. token 额度发生变化时用同一条 `UPDATE ... RETURNING key` 获取当前凭证，避免提交后额外 SELECT；MySQL/SQLite 保留现有兼容路径；
3. 每项分别测量 SQL calls、5432 Mbps、事务时长和锁等待，不与缓存架构改造同时发布。

### 第三优先级：版本化额度缓存

只有第一、第二项仍不足以满足多 slave 容量时，才设计版本号 + Lua/CAS 的额度缓存。该阶段必须先写设计和多实例压测，统一用户 `Quota/GiftQuota`、token `RemainQuota/UsedQuota`、删除、重建、轮换和所有额度修改入口；在此之前不直接改成增量 `HINCRBY`，也不把缓存提升为扣费权威。

## 十一、与原生 new-api 的细致对比

对比基线为只读参考仓库 `D:\gemai\gemai-api\参考项目源码\new-api`，提交 `66ee6b8f9`（2026-07-29）。本次没有修改参考仓库。

| 维度 | 原生 new-api | 当前实现 | 结论 |
|---|---|---|---|
| 预扣原子性 | token 与钱包/订阅分步修改，后一步失败时再补偿前一步 | wallet、token、reservation 在同一数据库事务内提交，并带非负额度条件 | 当前实现 SQL 更多，但多 slave 下不会依赖进程内补偿完成原子性 |
| 结算 | funding 先结算、token 后调整；token 失败时只能记录错误并阻止错误退款 | 先持久化 intent，再在事务中应用并写完成状态 | 当前实现保留崩溃恢复边界，不能为了省 SQL 回退原生分步结算 |
| 退款与修复 | 退款走异步 goroutine，进程退出可能中断；没有持久 reservation repair 状态机 | reservation、幂等状态、失败记录和 repair 可恢复 | 当前实现更适合多实例和进程重启 |
| 幂等 | 主要依赖单个 `BillingSession` 的内存 mutex/布尔状态 | request_id、reservation 状态和条件更新由共享数据库约束 | 原生的进程内幂等不能作为多 slave 方案 |
| 额度缓存 | user/token 额度修改后异步 `HINCRBY`；TTL 检查与增量操作不是一条原子脚本 | 不对缓存增量补差；预扣暂不删，最终结算后按影响范围删除一次 | 当前方案避免“删除后其他实例重建新值，再被旧请求重复 HINCRBY”的双重应用 |
| 缓存回源 | 缓存 miss 可直接并发回源 | 同一进程同 key 用 singleflight 合并，并在共享加载内二次检查 Redis | 只能削减单实例尖峰，不承担跨实例正确性 |
| 鉴权后余额读取 | `NewBillingSession` 再调用 `GetUserQuota` | 足够时复用鉴权上下文快照，不足或缺失时重新读权威额度 | 少一次常态查询，预扣事务守卫不变 |
| dispatched | 原生没有持久 reservation dispatched 状态 | 有界自动提交条件 UPDATE，冲突时补 SELECT 分类 | 属于当前崩溃恢复模型的必要状态，但已压缩正常路径往返 |
| 带宽特征 | SQL/事务较少，缓存增量写较轻，但异常恢复和并发一致性较弱 | reservation/审计会增加固定 SQL；本次通过合并回源和单次失效减少放大 | 目标不是机械恢复原生代码，而是在保留计费安全的前提下降低 5432/6379 抖动 |

本次只借鉴了原生实现“请求执行期间不反复删除并重建额度缓存”的性能效果，没有复制其分步扣费、异步补偿或非原子 `HINCRBY`。PostgreSQL 始终是最终余额权威；缓存偏高最多让请求进入一次随后被事务拒绝的预扣，不会绕过余额条件，也不会形成新的多扣费入口。
