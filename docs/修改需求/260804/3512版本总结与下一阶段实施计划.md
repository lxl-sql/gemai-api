# 3512 版本总结与下一阶段实施计划

> 文档日期：2026-08-04  
> 对比范围：`v1.0.0-rc.19.3511` → `v1.0.0-rc.19.3512`  
> 3512 提交：`942088a78`（`Preserve request cancellation and billing reservation cache consistency`）  
> 适用拓扑：多个 slave 共享 PostgreSQL 与 Redis，当前 PostgreSQL 直连、不使用 PgBouncer  
> 当前判定：3512 可进入单 slave 小流量灰度；版本化动态额度缓存属于下一阶段长期优化，不是 3512 灰度前置条件。

## 一、3512 总结

3512 不是若干互不相关的小修补，而是围绕鉴权缓存、计费热路径、请求取消和多 slave 缓存抖动做的一次集中收口。它没有改变两阶段结算、余额权威来源和幂等语义，主要目标是在保留计费安全的前提下减少固定 SQL、重复缓存失效和并发回源。

本次提交共修改 17 个文件，统计为 `+1120/-152`。其中约 283 行是文档、约 385 行是测试，实际生产代码约为 `+452/-148`。本次没有新增数据库表或字段，没有修改 Redis Key 协议，也没有引入分布式锁，因此回滚不依赖 DDL 或缓存清空。

### 1.1 相比 3511 已解决的问题

| 问题 | 3511 行为 | 3512 行为 | 预期收益 |
|---|---|---|---|
| 鉴权后重复读取额度 | 鉴权已得到用户余额，`NewBillingSession` 再读取一次 | 鉴权快照足够时直接复用；不足或缺失时刷新 | 常态少一次 Redis/PG 读取，同时避免旧低余额误 403 |
| 同实例缓存击穿 | 热门 token/user 缓存 miss 时并发回源 | 同进程、同 key 使用 singleflight，并在共享回源内二次检查 Redis | 削减单实例 SQL 尖峰和重复 Hash 重建 |
| 预扣、结算重复删除 | 预扣后删除一次，结算后再次删除 | 新预扣和增加预扣暂不删除，最终结算按真实影响范围每类最多删除一次 | 直接减少多 slave 同时回源的放大次数 |
| `MarkDispatched` 固定事务往返 | `BEGIN`、事务设置、UPDATE、COMMIT | 有界自动提交条件 UPDATE；仅冲突时补只读分类 | 缩短连接占用和正常路径往返 |
| 请求取消未贯穿鉴权缓存 | 部分 Redis/PG 读取继续使用后台 Context | HTTP 鉴权、Redis Hash、用户/Token 回源传递请求 Context | 客户端断开后减少无效等待和连接占用 |
| singleflight 共享对象 | 请求可能共享 Token 中的可修改指针字段 | 返回前复制 `KeyHash`、`AllowIps` 等字段 | 防止请求间修改互相影响，降低竞态风险 |
| Token 凭证轮换后的失效 | 只按请求开始时凭证处理可能遗漏新凭证 | 结算时按数据库当前 `key/key_hash` 精确失效 | 避免轮换后的新凭证继续持有旧额度缓存 |
| 异常和幂等路径失效 | 成功、异常路径失效范围不够清晰 | 正常提交精确失效；重放、错误和提交不确定保守失效 | 性能优化不削弱崩溃恢复和缓存修复能力 |

### 1.2 最重要的带宽改进

3511 的普通请求可能形成：

```text
预扣成功
→ 删除 user/token
→ 多 slave 同时从 PostgreSQL 全量回源并重建 Redis Hash
→ 最终结算
→ 再次删除 user/token
→ 再次全量回源
```

3512 收敛为：

```text
预扣成功
→ 请求执行期间暂不删除
→ 最终结算
→ 根据事务真实影响，user/token 各最多删除一次
```

`actual_quota == reserved_quota` 时仍会在最终结算删除一次，因为预扣已经改变数据库余额；3512 省掉的是请求执行期间那一轮删除、回源和重建，而不是漏掉必要失效。事务错误、提交结果不确定和幂等重放仍保守失效。

### 1.3 计费安全边界保持不变

3512 没有修改以下核心不变量：

1. PostgreSQL 是用户余额、Token 额度和 reservation 状态的唯一权威来源；
2. `request_id` 和 reservation 状态机继续承担跨实例幂等；
3. 预扣、补扣、退款在数据库事务中使用非负余额守卫；
4. 持久化 settlement intent 与 apply 仍为两个阶段，不能合并；
5. settlement failure、repair、Task、Midjourney 的恢复语义保持；
6. 缓存只做预检查和展示，缓存偏高不能绕过数据库事务；
7. 不使用非原子的 Redis `HINCRBY` 修补 reservation 余额。

因此，请求执行期间缓存暂时偏高最多造成一次随后被数据库拒绝的预扣尝试，不会据此形成透支或重复扣费。

## 二、3512 灰度计划

### 2.1 灰度前硬门禁

1. 从干净 checkout/worktree 构建精确提交 `942088a78`，记录镜像 digest；不得把当前工作区其他未提交的前端修改意外打入计费灰度镜像。
2. 在 Linux 构建机运行：

   ```bash
   go test -race ./model ./service -count=1
   ```

3. 使用应用相同数据库角色的新建直连会话确认：

   ```sql
   SHOW lock_timeout;
   SHOW idle_in_transaction_session_timeout;
   ```

   预期分别与 `SQL_PG_LOCK_TIMEOUT_MS=5000`、`SQL_PG_IDLE_IN_TX_TIMEOUT_MS=60000` 一致。`MarkDispatched` 已改为自动提交 UPDATE，5 秒行锁等待上限依赖角色级 `lock_timeout`，不得 `RESET`。
4. slave 保持 `BILLING_SETTLEMENT_REPAIR_ENABLED=false`，除非该节点被明确指定为 repair 故障接管节点。
5. `token_usage_source_setting.enabled=false` 和 reconcile 继续关闭，不与本次计费灰度同时启用。
6. 不提高单实例 `SQL_MAX_OPEN_CONNS`，按实例数量核算 PostgreSQL 总连接预算。

### 2.2 灰度顺序

1. 一台 slave 导入 1%～5% 真实流量，观察至少 30～60 分钟；
2. 覆盖流式、非流式、零差额、补扣、退款、错误响应、Token 轮换；
3. 对比相同 RPM 下 5432/6379 带宽、SQL P95/P99、接口 P95/P99、403/5xx；
4. 第一台通过后增加第二台 slave，验证共享 Redis/PG 下的缓存失效和回源；
5. 每批完成一个完整观察窗口后再扩容；最后才更新 master；
6. 不长期混跑 3511/3512，灰度通过后在受控窗口内收敛全部节点。

### 2.3 立即停止条件

- 用户余额、Token 额度、消费日志或 reservation 无法对账；
- 重复扣费、漏退款或错误 403 明显增加；
- `billing_settlement_failures.pending` 或新增速率持续高于基线；
- `idle in transaction`、锁等待、连接等待或 SQL P95 持续上升；
- 同 RPM 下 5432 带宽持续高于 3511，而不是短时采样尖峰；
- master/slave 的 repair runner 发生非预期重复执行。

## 三、3512 之后仍存在的问题

3512 已减少一次请求内的重复失效，但最终结算后仍会删除完整 user/token Hash。下一次请求仍可能：

1. 全量查询用户鉴权与余额字段；
2. 全量查询 Token 静态配置与额度字段；
3. 全量 HSET 重建 Redis Hash；
4. 多个 slave 在同一失效窗口内分别回源一次；
5. Token 失效前按 ID 查询当前 `key/key_hash`；
6. 计费事务仍存在可进一步压缩的固定 PostgreSQL 往返。

所以 3512 预期明显缓解带宽尖峰，但不能承诺把生产带宽固定恢复到某个 Mbps，也不能彻底消除跨 slave 缓存抖动。

## 四、下一阶段实施顺序

后续修改必须逐项独立提交、独立灰度。不得同时叠加 PostgreSQL 往返优化、Redis 协议迁移和计费状态机修改。

### 阶段 A：先完成 3512 生产验收

在没有取得单 slave、双 slave 的同 RPM 对照前，不继续修改 reservation 主链。验收数据至少包括：

- 5432 和 6379 双向 Mbps；
- PostgreSQL active、idle in transaction、Lock 等待；
- Redis 命中率、连接池等待、错误率；
- `billing_settlement_failures` 新增速率与 pending；
- reservation 超期数量；
- 余额、Token、日志抽样对账。

只有 3512 灰度稳定，才能判断剩余流量到底来自最终全量重建、固定 SQL、日志审计还是正常业务流量。

### 阶段 B：低风险 PostgreSQL 固定往返优化

按以下顺序分别实施：

1. 审计所有计费事务中 `SET LOCAL lock_timeout` 与 `SET LOCAL idle_in_transaction_session_timeout` 的执行位置；只有在不改变事务级保护语义时，才合并为一条 PostgreSQL 语句。SQLite/MySQL 保留现有路径。
2. PostgreSQL Token 额度 UPDATE 使用 `RETURNING key, key_hash` 同时返回结算时刻凭证，移除提交后的当前凭证 SELECT；MySQL/SQLite 保留事务后兼容查询。
3. 每项单独测量 SQL calls、事务耗时、锁等待和 5432 Mbps；没有实际收益时不继续扩大改动。

以下内容暂不进入本阶段：

- 不合并 settlement intent/apply；
- 不修改 reservation 幂等冲突分类；
- 不引入新的重试；
- 不把 LOG 审计强行并入主库事务。

### 阶段 C：保留 LOG_SQL_DSN 扩展能力

后续可能配置独立 `LOG_SQL_DSN`，因此审计链必须继续支持主库与日志库分离：

1. 不实现依赖“日志库必然等于主库”的强耦合事务；
2. 若增加同库快路径，必须运行时确认 `UsingLogDatabase` 与主库为同一数据库，并保留跨库原路径；
3. 不允许配置 `LOG_SQL_DSN` 后静默丢失日志、ack 或 release；
4. 同库快路径和独立日志库路径必须分别测试。

该项优先级低于 3512 灰度和版本化额度缓存设计，不应为减少少量往返牺牲未来日志库拆分。

### 阶段 D：版本化动态额度缓存

这是长期解决“最终删除后全量重建”和跨 slave 乱序写入的方案，必须分发布阶段实施。

#### D1. 存储结构

- 用户静态缓存长期保存 ID、状态、角色、分组、安全版本、Setting；
- 用户动态缓存保存 `quota`、`gift_quota`、`quota_version`；
- Token 静态缓存保存状态、模型/IP/分组限制、无限额度配置；
- Token 动态缓存使用 `token_id` 作为 key，保存 `remain_quota`、`quota_version`；
- `used_quota` 属于统计字段，不进入热鉴权额度缓存。

建议动态 Key：

```text
quota:user:{user_id}
quota:token:{token_id}
```

#### D2. 数据库版本

- `users`、`tokens` 增加 `quota_version BIGINT`，不建立索引；
- 每次真实额度变化执行 `COALESCE(quota_version, 0) + 1`；
- PostgreSQL UPDATE 使用 `RETURNING` 返回完整最新余额和版本；
- MySQL/SQLite 在同一事务中 UPDATE 后窄查询快照；
- 差额为零、幂等重放不得增加版本；
- 充值、预扣、补扣、退款、repair、管理员改额必须全部覆盖，不能只修改 reservation 路径。

#### D3. Redis Lua/CAS

- Redis 只接受数据库返回的完整额度快照，不应用额度差额；
- Lua 仅允许更高 `quota_version` 覆盖旧版本；
- 旧提交晚到时不得覆盖新余额；
- CAS 写入失败后，只在缓存版本不高于本次版本时条件删除；禁止无条件 DEL 删除其他实例已经写入的新版本；
- 禁止使用当前非原子的 `TTL + HINCRBY` 作为新方案。

#### D4. 动态缓存 miss

- 用户动态 miss 只查询 `id, quota, gift_quota, quota_version`；
- Token 动态 miss 只查询 `id, remain_quota, quota_version`；
- 同实例继续使用 singleflight，并在进入共享回源后再次检查 Redis；
- CAS 因旧版本被拒绝时重新读取 Redis 新版本，不能返回已经过期的数据库结果；
- Redis 不可用时使用数据库结果，数据库事务仍是最终额度守卫。

#### D5. 崩溃窗口兜底

数据库 COMMIT 成功但进程在 Redis CAS 前崩溃时，旧动态缓存可能短暂存在。必须保证：

- 缓存偏高时仍由数据库非负条件拒绝透支；
- 缓存显示不足或 Token exhausted 时，在最终返回 403 前强制窄查询数据库刷新一次，避免充值/退款后旧低缓存误拒绝；
- 动态缓存使用有界 TTL，不能依赖永久缓存恢复一致性。

#### D6. 滚动发布模式

建议使用单一模式开关：

```text
VERSIONED_QUOTA_CACHE_MODE=off
VERSIONED_QUOTA_CACHE_MODE=shadow
VERSIONED_QUOTA_CACHE_MODE=active
```

发布顺序：

1. `off`：先上线字段和所有额度写入版本递增，继续使用 3512 的最终失效；
2. `shadow`：写入新动态缓存但鉴权仍读旧缓存，抽样对比 Redis 与数据库；
3. 所有 master/slave/repair 节点均具备版本写入能力后，仅一台 slave 开启 `active`；
4. 单 slave、双 slave 验证通过后逐台开启；
5. 全部节点收敛后才停止因额度变化删除完整静态鉴权缓存；
6. 稳定一个完整发布周期后再删除旧兼容字段和旧缓存路径。

旧版本实例如果仍可修改额度但不增加版本，`active` 模式就不安全。因此不得在版本写入尚未覆盖全部节点时开启动态缓存读取，也不得直接从 active 混滚回不认识新协议的旧镜像。

## 五、下一阶段测试门禁

版本化动态缓存至少覆盖：

1. version 10 后写 version 9，缓存保持 version 10；
2. version 10 后写 version 11，缓存更新为 version 11；
3. cache miss 查到旧版本时，并发新提交不能被覆盖；
4. version 10 CAS 失败后不得删除已有 version 11；
5. 预扣、补扣、退款、repair 的版本和余额精确；
6. 幂等重放不重复扣费、不增加版本；
7. 零差额不增加版本、不重复写 Redis；
8. Token 密钥轮换继续使用同一个 token ID 动态缓存；
9. Redis 全断时数据库扣费、防透支和不足刷新正常；
10. 两个独立进程共享 PostgreSQL/Redis 的乱序提交压测；
11. SQLite、MySQL、PostgreSQL 回归和 Linux `-race`；
12. 进程在 DB COMMIT 后、Redis CAS 前退出的故障注入。

## 六、明确禁止的过度优化

- 不为降低 SQL 数合并两阶段结算；
- 不用 Redis 分布式锁代替 PostgreSQL 条件更新；
- 不用普通 `HINCRBY` 对余额做增量补差；
- 不在数据库提交前发布缓存余额；
- 不把 user/token 静态缓存、动态额度和统计字段继续混为一个写入对象；
- 不同时上线数据库字段、active 读取和停止旧缓存删除；
- 不把本地单实例测试当成多 slave 生产验收；
- 不为了同库审计快路径破坏未来 `LOG_SQL_DSN` 独立部署能力。

## 七、最终路线

```text
3512 单 slave 灰度
→ 双 slave 共享 PG/Redis 验收
→ 逐项压缩低风险 PostgreSQL 固定往返
→ 版本字段覆盖所有额度写入
→ 动态额度缓存 shadow 对账
→ 单 slave active
→ 双 slave active
→ 全集群收敛
→ 最后停止额度变化导致的完整静态缓存删除
```

稳定性优先于减少少量 SQL。任何阶段只要余额、Token、日志、reservation、settlement failure 或锁等待出现无法解释的偏差，就停止扩大并回滚当前阶段，不继续叠加下一项优化。
