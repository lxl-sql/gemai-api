# API Key 管理员分层安全策略

日期：2026-07-29

## 目标

在保留用户自行收紧 API Key 安全限制的基础上，增加管理员强制边界，避免普通用户关闭关键保护，同时允许企业用户按合同配置高并发容量。

## 实施内容

### 策略层级

管理员可以在「系统设置 → 安全设置 → API Key 安全策略」维护三类完整策略：

1. 平台默认策略；
2. 用户分组策略；
3. 指定用户策略。

匹配优先级为：指定用户 > 用户分组 > 平台默认 > 内置无限制兼容策略。更具体的策略会完整替代较低层级策略，不进行字段拼接，便于管理员判断最终结果。

### 管理员与用户的权限边界

- 持续 RPS、突发容量、最大并发、五分钟不同模型数和 Redis 故障拒绝行为仅允许管理员配置；命中已保存的管理员策略后，直接采用该策略值，避免企业高并发容量被普通 Key 默认值误限流。
- 用户只能为自己的单个 API Key 配置单次、每小时、每日消费上限和风险响应，并且只能比管理员边界更严格。
- 用户消费上限填写 `0` 表示继承管理员值；非零值与管理员上限取更严格的一项作为最终生效值。
- 风险响应取管理员最低要求和用户配置中更严格的一项。
- 后端会显式拒绝用户请求中的管理员专属字段，包括传入 `0` 或 `false`，不能通过绕过前端修改。
- 管理员没有创建平台策略时，内置策略不限制历史 API Key，避免升级后改变现有业务流量。

支持的边界包括：

- 持续 RPS；
- 突发容量；
- 最大并发；
- 单请求额度；
- 每小时额度；
- 每日额度；
- 五分钟不同模型数量；
- 最低风险响应；
- Redis 不可用时是否强制拒绝。

### 后端与多实例一致性

- 新增 `token_security_profiles` 表，使用现有 GORM 自动迁移，兼容 SQLite、MySQL 和 PostgreSQL。
- 新增管理员接口：
  - `GET /api/token-security-profile/`
  - `PUT /api/token-security-profile/`
  - `DELETE /api/token-security-profile/`
- 新增用户默认策略接口：`GET /api/token/security-policy-default`。
- 单 Key 策略查询同时返回原始配置、命中的管理员策略和最终生效策略。
- 管理员策略按作用域缓存到共享 Redis；更新或删除后刷新对应作用域缓存，多台 API 实例读取同一结果。
- 每个请求只解析一次最终策略，并由限流、并发、预算和模型遍历检测共同复用。
- 管理员新增、更新和删除策略均写入操作日志。

### 前端

- `web/default` 管理员页面支持查看、创建、编辑和确认删除分层策略。
- `web/default` API Key 创建与编辑页面以只读方式展示管理员管理的容量、模型阈值和 Redis 故障策略，只开放消费上限与风险响应；`web/classic` 创建的 Key 同样受后端管理员边界约束。
- 管理员专属字段不会进入普通用户的创建或更新请求；用户伪造请求时由后端拒绝。
- 所有新增文案已同步到 `en`、`zh`、`zh-TW`、`fr`、`ja`、`ru`、`vi`。
- 未保存管理员策略时，用户页面明确显示“内置兼容策略/容量不受限”，不再把新 Key 的默认值误标为平台管理员策略；已保存策略展示管理员 Profile 的真实值。

### 兼容性说明

- 未配置任何持久化管理员策略时，历史 API Key 已保存的容量和 Redis 故障行为继续生效，避免升级后改变现有流量。
- 新建 API Key 不再隐式写入固定的 5 RPS、25 突发、20 并发和 20 模型限制；省略安全策略时保持兼容且不创建策略行，普通容量由管理员平台策略统一设置。
- 管理员创建平台、分组或用户策略后，管理员专属字段按命中的完整策略立即生效；用户原有消费上限和风险响应继续作为更严格的补充限制。
- 本次权限边界调整复用现有表结构，不新增数据库迁移。

### 后续修复

- 普通用户页面不再展示 Redis 等基础设施术语，改为说明“安全保护异常时暂停请求”；管理员配置页面保留技术字段。
- 批量创建 API Key 部分成功时，仍会展示已经签发的一次性密钥，避免完整密钥永久丢失。
- 状态更新接口拒绝夹带安全策略，避免不同更新模式的校验边界不一致。
- API Key 表单每次打开只初始化一次，异步加载用户组不会覆盖用户已经填写的内容。

## 上线建议

1. 多实例环境先只启动一个迁移实例，确认 `token_security_profiles` 自动迁移完成后，再滚动发布其余 API 实例，避免多个进程同时执行 DDL。
2. 再发布 `web/default`。
3. 按单 Key 统计峰值 RPS、峰值并发和五分钟不同模型数；先为高流量企业创建分组或用户策略并完成验证。
4. 最后配置平台默认策略；普通用户可从 1 RPS、5～10 突发、5～10 并发和 `notify` 风险响应开始，但必须以生产峰值和业务容忍度为准。
5. 生产环境启用 `fail_closed` 前，应确认 Redis 已具备高可用和故障切换能力。
6. 上线后检查管理员操作日志、429 错误码、Redis 延迟和连接池等待，并验证至少一个普通用户和一个企业用户的最终生效策略。

## 验收范围

- 后端：策略合并、作用域优先级、令牌限流/并发/预算/模型风险回归。
- 前端：类型检查、策略合并单元测试、表单单元测试、生产构建。
- 日志：RPM 使用严格的 60 个完整秒窗口；容量评估仍需按单 Key 采集峰值 RPS 和在途并发，不能只使用总 RPM。
- i18n：全部语言 `missingCount = 0`。
- 仍需在真实生产拓扑进行 Redis 故障切换、多实例一致性和企业峰值流量压测。

## 安全复审修复

- 管理员新增、修改和删除安全策略均增加敏感操作限流与二次身份验证。
- 数据库提交后重试刷新共享 Redis；刷新仍失败时接口明确返回 `cache_synchronized: false`，前端提示管理员缓存同步仍在等待，避免把降级状态误报为完全成功。
- 管理员操作日志补充记录全部数值边界、风险模式、Redis 故障策略和缓存同步状态。
- 管理页面会把 `success: false` 的业务响应作为加载失败处理，并提供重试入口，不再显示为空列表。
