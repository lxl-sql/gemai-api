# API Key 二次验证操作日志语义修复

日期：2026-07-29

## 问题

API Key 创建、编辑、删除、批量删除、轮换及安全策略变更均要求先完成一次
安全验证。安全验证与登录是两类不同事件，操作日志不能把安全验证展示成“登录”，
也不能只记录后续的 API Key 变更而缺少本次身份确认记录。

## 修改

- API Key 写操作触发安全验证时，由后端生成包含用户、安全版本、用途、过期时间和
  随机数的短期签名 challenge；前端只在本次 `/api/verify` 请求中原样回传，
  不接受前端自报操作日志类型。
- challenge 不再使用共享 Session 用途字段，多标签页同时触发不同敏感操作时互不
  覆盖；签名被修改、用户或安全版本不匹配、challenge 过期时拒绝验证。
- 密码、2FA 或 Passkey 验证成功后，新增一条
  `auth.api_key_security_verification` 操作日志。
- 操作日志仍归类为“身份验证”，操作显示为“API 密钥安全验证”，目标为当前用户；
  详情仅记录验证方式和用途，不记录密码、验证码、备份码或密钥明文。
- 其他敏感操作的二次验证使用通用“安全验证”名称，不复用“登录”。
- Default 前端补齐英文、简体中文、繁体中文、法文、日文、俄文和越南文显示；
  Classic 前端同步显示名称。
- 历史 `auth.login` 记录不迁移；修复只影响部署后的新操作日志。

## 验收

- 创建或编辑 API Key 前完成密码、2FA 或 Passkey 验证后，操作日志新增
  “API 密钥安全验证”，不新增“登录”。
- 同一次业务请求随后仍分别记录“创建 API 密钥”或“更新 API 密钥”。
- 操作详情包含 `verification_method` 和 `purpose=api_key_security`，不包含验证凭据。
- `go test ./common ./controller ./middleware ./router` 通过。
- Default 前端 TypeScript 类型检查通过，操作日志常量定向 lint 无错误。
- Default 前端 challenge 提取回归测试通过。
- i18n 同步报告中所有语言的缺失键数量均为 0。
- 多个 challenge 分别保留自身用途和随机数，篡改或过期 challenge 会被拒绝。
- 尚未执行真实浏览器、真实数据库及已部署环境验收。

## 最终审计结论

- 已修复共享 Session 用途字段在多标签页下相互覆盖、导致操作日志分类错误的问题。
- 最终审计覆盖签名 challenge、验证控制器、API Key 路由、Default/Classic 前端回传
  以及操作日志名称映射，未发现新的 P1/P2。
- 后端相关测试、Default 前端 2 个测试文件共 3 个测试、TypeScript 类型检查、
  Classic 格式检查和 `git diff --check` 均通过。
- 结论仅代表源码和自动化验证；真实浏览器多标签页、真实日志数据库及部署环境仍需
  上线前验收。
