# 渠道模型映射编辑器与定价文案修复

> 日期：2026-07-09  
> 范围：`web/default` 渠道编辑「模型映射」可视化编辑器；模型广场（`/pricing`）侧边栏定价类型筛选文案与供应商筛选项。  
> 目标：修复模型映射可视化编辑器中新增空行后删除任意一行会清空其他空行的问题；修正模型广场「按请求」筛选项的中文翻译；避免模型广场同名供应商重复展示。

## 1. 渠道编辑模型映射：删除一行清空其他空行

### 1.1 问题现象

渠道编辑抽屉的「模型映射」可视化编辑器中，如果连续点「添加映射」新增几条空行（原始模型/替换模型都未填），随后删除其中任意一行，其余尚未填写的空行会一并消失，体验不如 `web/classic` 的同类编辑器。

### 1.2 根因

组件内部把可视化行（rows）序列化成 JSON 字符串，通过 `onChange` 回传给外层表单，再由外层表单把该值作为 `value` prop 传回组件。原实现里有一个 `useEffect` 监听 `props.value`，一旦外部 `value` 变化就无条件重新执行 `parseJsonToRows` 把 JSON 解析回 rows。

由于 JSON 对象无法表达「键为空字符串」的行，序列化时空行天然被过滤掉；而组件自己发出的 `onChange` 又会作为 `props.value` 被同一个 `useEffect` 重新解析一遍，等于用「已过滤掉空行的 JSON」重建了 rows，结果是任何一次行内编辑或删除操作后，所有未填写的空行都会被这次「回显解析」清空。

### 1.3 修复方案

涉及文件：

- `web/default/src/features/channels/components/model-mapping-editor.tsx`

修改内容：

- 新增 `lastEmittedValueRef`，记录组件自己最近一次通过 `onChange` 发出的值。
- 监听 `props.value` 的 `useEffect` 改为：只有当 `props.value` 与 `lastEmittedValueRef` 不同（即真正来自外部的变更，例如渠道数据异步加载完成、表单被程序化重置）时才重新解析成 rows；组件自己发出后又原样回显的值不再重新解析，本地空行状态得以保留。
- `convertRowsToJson` 统一按「`from` 非空」过滤有效行；全部为空行时输出空字符串，不再输出 `'{}'`。
- 新增 `emitMappingValue` 包装 `onChange`，统一在发出值的同时更新 `lastEmittedValueRef`，覆盖行编辑、删除、JSON 模式输入、填入模板、可视化/JSON 模式切换等所有出口。
- `lastEmittedValueRef` 初始值为 `null`，保证组件首次挂载时（渠道数据异步加载完成后 `value` 从空变为已有映射）一定会执行一次解析，不会因为初始值判断被跳过。

### 1.4 影响范围核对

- 该组件另有一处调用方 `web/default/src/features/channels/components/dialogs/tag-batch-edit-dialog.tsx`（标签批量编辑弹窗），逻辑同样受益，行为一致。
- 全仓搜索确认除表单初始化/重置外，没有其他位置会程序化调用 `setValue('model_mapping', ...)` 之类的方式在编辑过程中改写该字段，因此「外部变更时强制重新解析」不会误伤正常编辑流程。
- 重复原始模型场景仍通过既有的哨兵值 `DUPLICATE_MAPPING_SENTINEL` 触发表单校验拦截，行为未变。
- 切换到 JSON 文本模式再切回可视化模式时，空行仍会因 JSON 语义限制而丢失，这是 JSON 格式的固有限制，与 `web/classic` 一致，非本次引入的问题。

## 2. 模型广场定价类型筛选文案修正

### 2.1 问题现象

`/pricing` 模型广场页面左侧筛选栏「定价类型」下，「按请求」筛选项的中文文案缺字，应为「按次计费」（与「按量计费」对应）。

### 2.2 修复方案

对应的 i18n key 为 `Per Request`（定义在 `web/default/src/features/pricing/constants.ts` 的 `getQuotaTypeLabels`，供 `pricing-sidebar.tsx` 使用）。按照项目 i18n 规范，通过 `add-missing-keys.mjs` 脚本更新既有 key 的翻译值，而非直接手改 locale JSON：

- `zh`：`按请求` → `按次计费`
- `zh-TW`：同步更正为 `按次計費`
- `fr` 补齐为 `Par requête`（原文案与英文源字符串重复，视为未翻译，此次一并修正）
- `en` / `ja` / `ru` / `vi` 原文案已符合语义，未改动

修改后执行 `bun run i18n:sync` 完成排序与报告刷新，临时脚本已删除。

## 3. 模型广场供应商筛选去重

### 3.1 问题现象

`/pricing` 模型广场左侧筛选栏「所有供应商」会展示大量重复供应商，例如多条 `Anthropic`、`OpenAI`、`Google`。这些重复项显示相同名称、相同计数，用户无法区分，且会造成 React 列表 key 重复风险。

### 3.2 根因

`/api/pricing` 返回的 `vendors` 来自供应商表，业务上允许存在多条同名供应商记录；前端 `pricing-sidebar.tsx` 原先直接遍历 `props.vendors` 生成筛选项，并使用 `vendor.name` 作为筛选值。

同时，实际筛选逻辑 `filterByVendor` 是按模型上的 `vendor_name` 做名称匹配，而不是按 `vendor_id` 匹配。因此同名供应商在筛选语义上本来就应视为同一类品牌/供应商展示项，但 UI 没有做名称归并，导致重复渲染。

### 3.3 修复方案

涉及文件：

- `web/default/src/features/pricing/components/pricing-sidebar.tsx`

修改内容：

- 生成供应商筛选项前，先按 `vendor.name` 构建 `uniqueVendors`，同名供应商只保留一个展示项。
- 计数改为基于模型列表聚合 `model.vendor_name`，保证多个同名供应商对应的模型数量合并展示。
- 如果重复供应商中前一条没有图标、后一条有图标，会补上图标，避免去重后丢失可用视觉信息。
- 对后端异常数据加运行时保护：
  - `model.vendor_name` 必须是字符串才参与计数。
  - `vendor.name` 必须是字符串且非空才参与归并。
  - 异常供应商数据会被跳过，不会导致筛选栏运行时报错。

### 3.4 当前行为

- 同名供应商只显示一个筛选 chip。
- 点击供应商筛选时仍按供应商名称过滤，和原有过滤逻辑保持一致。
- 桌面侧边栏和移动端筛选抽屉共用 `PricingSidebar`，两处都会同步生效。
