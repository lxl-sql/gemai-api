# API Key 安全改造灰度发布实施计划

日期：2026-07-30  
适用版本：API Key 滚动兼容桥接版本（第一阶段）  
生产拓扑：固定 1 个 master、多个 slave，实例角色由 `NODE_TYPE` 固定配置

## 1. 发布结论

当前版本可以按“master 优先、slave 分批”的方式滚动灰度发布，不需要停机。

成立条件如下：

- 所有实例使用同一个、已经固定且不会变更的 `CRYPTO_SECRET`。
- master 的 `NODE_TYPE` 固定为非 `slave`，所有 slave 的 `NODE_TYPE=slave`。
- 本次只发布兼容桥接版本，不执行 `tokens.key` 明文清理。
- 本次不同时调整平台默认安全策略、RPS、并发、额度、模型限流或风险响应策略。
- `TRUSTED_PROXIES` 已按生产反向代理链路配置并在发布前验证。

本版本启动时只回填 `key_hash` 和 `key_hint`，保留 `tokens.key` 明文。新旧实例混部期间：

- 旧实例仍按明文 `tokens.key` 认证；
- 新实例优先按 `key_hash` 认证，同时兼容明文查询；
- 新建及轮换的 Key 同时写入明文、哈希和掩码提示；
- 在最终明文清理前，可以回滚到发布前版本。

## 2. 发布目标与范围

### 2.1 本次目标

- 无停机完成数据库字段迁移和存量 Key 元数据回填。
- 保证旧 Key、新建 Key、轮换 Key 在新旧实例混部期间均可使用。
- 上线 Token 安全额度、风险响应、通知许可和操作日志相关修复。
- 验证 429 拒绝、自动暂停、额度扣减和使用日志行为符合预期。

### 2.2 本次不包含

- 不把 `tokens.key` 改写为 `h:<hash>`，不删除或清空明文 Key。
- 不启用或修改平台默认 Token 安全策略。
- 不修改现有用户、分组和单 Key 的生产限额。
- 不把数据库字段回滚、索引删除或 Redis 全量清空作为常规回滚步骤。
- 不执行第二阶段最终哈希存储迁移。

## 3. 发布前冻结与备份

发布前至少保留 30 分钟稳定基线，并冻结以下变更：

- 平台默认安全策略；
- 用户、分组和单 Key 安全策略；
- 模型倍率和固定调用费用；
- 模型请求限流配置；
- 反向代理、负载均衡和客户端 IP 转发配置；
- `CRYPTO_SECRET`、`NODE_TYPE`、`NODE_NAME`、Redis 和数据库连接配置。

必须完成：

1. 记录待发布镜像的唯一 digest、应用版本号和回滚镜像 digest。
2. 备份 `tokens` 表，并确认备份可读取。
3. 记录发布前有效 Key 数、每分钟请求量、401/403/429/5xx 比例、接口 P95/P99、数据库和 Redis 基线。
4. 确认每个实例有稳定且唯一的 `NODE_NAME`，便于系统实例列表识别版本和角色。
5. 分别从 master 和至少一个 slave 检查 `/healthz`：
   - HTTP 200；
   - `success=true`；
   - 返回当前版本；
   - 数据库和 Redis 均可访问。
6. 以不输出密钥原文的方式比较所有实例的 `CRYPTO_SECRET` 指纹，确认完全一致。
7. 确认 master 和 slave 的角色配置没有复用或漂移：
   - master：`NODE_TYPE` 不是 `slave`；
   - slave：`NODE_TYPE=slave`。
8. 确认 `TRUSTED_PROXIES` 覆盖实际反向代理地址或网段，并用真实请求验证 `ClientIP`、IP 白名单和审计 IP 正确。

建议发布前数据库核对：

```sql
SELECT COUNT(*) AS missing_key_hash
FROM tokens
WHERE deleted_at IS NULL
  AND key_hash IS NULL;
```

如果字段尚不存在，该查询失败是预期现象；字段由新 master 启动迁移自动创建。对于超大 `tokens` 表，应提前评估 `AutoMigrate` 增加字段和索引的锁等待时间，并相应放宽 master 的启动探针超时。

## 4. 自动化发布编排

发布平台应把本次更新拆成有依赖关系的阶段，不允许 master 和 slave 无序并发更新。

```text
发布前检查
  → 更新唯一 master
  → master 健康、迁移和回填验收
  → master 小流量灰度
  → slave 单台/小批次滚动
  → 确认旧版本实例全部退出
  → 检查混部期间新增 Key 的 key_hash
  → 必要时重启一次 master 补回填
  → 全量观察与发布收口
```

### 阶段 A：更新唯一 master

1. 保持所有旧 slave 在线承载流量。
2. 将 master 从普通业务流量中临时摘除；如果 master 本来不承载业务流量，则保持现状。
3. 只更新唯一 master，不同时更新任何 slave。
4. 新 master 启动时自动执行：
   - `AutoMigrate` 创建 `key_hash`、`key_hint` 和相关索引；
   - 按 200 条一批回填存量 Token 元数据；
   - 保留原有明文 `tokens.key`。
5. master 回填完成前不会进入正常可用状态。启动探针必须允许回填完成，禁止因短超时形成反复重启。
6. `/healthz` 返回 200 且版本正确后，继续观察 10 分钟。
7. 在系统实例列表确认：
   - 该节点是唯一 master；
   - 版本为本次目标版本；
   - `started_at` 已更新；
   - `last_seen_at` 持续刷新。

master 阶段放行条件：

- 无迁移或回填错误；
- 无 `key_hash`/`key_hint` 字段不存在错误；
- 有效 Key 的认证测试通过；
- 401、5xx、数据库锁等待和连接池等待没有异常上升；
- master 没有重启循环。

### 阶段 B：master 小流量灰度

如果 master 承载业务流量，将 5% 或一个最小可控流量单元导向新 master，持续 10～15 分钟。

至少验证：

- 一个发布前已存在的 Key；
- 一个在新 master 上新建的 Key；
- 一个在新 master 上轮换的 Key；
- 普通非流式请求和一个流式请求；
- 一个配置了允许 IP 的 Key；
- 一个低频、未触发任何安全限制的基准 Key。

有效 Key 出现可复现 401，或数据库出现字段缺失错误时，立即停止后续发布。

### 阶段 C：滚动更新 slave

slave 按以下策略更新：

- 默认一次只更新 1 台；
- slave 数量较多时，每批最多为总 slave 数的 10%～20%；
- 每批至少保留一台已验证可用实例；
- 上一批完成健康检查和观察窗口后，才能更新下一批；
- 第一台 slave 观察 10 分钟，后续每批观察至少 5 分钟。

每台 slave 的放行条件：

- `/healthz` 返回 200 且版本正确；
- 系统实例列表显示角色仍为 slave；
- 发布前存量 Key 可认证；
- 新建和轮换 Key 可认证；
- 无异常 401/403/429/5xx；
- 数据库和 Redis 延迟未越过停止阈值。

注意：每个新实例启动会清理共享 Redis 中的用户和 Token 缓存。滚动过程中会出现短时数据库回源增加，因此不得一次重启大量 slave，并应重点监控数据库连接池、查询延迟和 CPU。

### 阶段 D：确认旧版本完全退出

所有 slave 更新完成后：

1. 通过部署平台确认旧容器或旧进程数量为 0。
2. 通过系统实例列表确认所有在线节点均为目标版本。
3. 等待至少 90 秒，使未继续上报的旧实例进入 stale 状态。
4. 再等待一个 30 秒实例上报周期，确认所有新实例的 `last_seen_at` 正常刷新。
5. stale 记录可以在确认对应进程已经退出后清理，但清理记录不是发布成功的必要条件。

### 阶段 E：补齐混部期间创建的 Key

旧 slave 在混部期间创建或更新的 Key 可能没有 `key_hash`。全量更新完成后执行：

```sql
SELECT COUNT(*) AS missing_key_hash
FROM tokens
WHERE deleted_at IS NULL
  AND key_hash IS NULL;
```

- 结果为 0：不需要额外重启 master。
- 结果大于 0：在低峰期只重启一次新版本 master，让启动回填补齐数据；slave 继续承载流量。
- master 再次健康后重复查询，结果必须为 0。
- 如果第二次仍不为 0，停止发布收口并排查，不执行明文清理。

## 5. 业务验收用例

### 5.1 Key 兼容性

| 场景 | 旧实例 | 新实例 | 预期 |
| --- | --- | --- | --- |
| 发布前存量 Key | 验证 | 验证 | 均认证成功 |
| 混部期间由旧实例创建的 Key | 验证 | 验证 | 均认证成功；全量后补齐哈希 |
| 混部期间由新实例创建的 Key | 验证 | 验证 | 均认证成功 |
| 新实例轮换后的 Key | 验证 | 验证 | 新 Key 成功，旧 Key 失效 |
| Redis 缓存未命中 | 验证 | 验证 | 均可回源数据库认证 |

不要在生产执行 `FLUSHALL`。缓存未命中应通过测试 Key 的精确缓存项、隔离的验收环境或实例启动后的自然未命中进行验证。

### 5.2 额度与风险响应

使用专门测试用户和测试 Key，避免改变真实用户策略：

1. 单次最大额度小于模型单次固定费用：
   - 请求返回清晰的 429；
   - 上游不应被调用；
   - Token 剩余额度不应扣减；
   - 使用日志或安全审计日志应能说明拒绝原因。
2. 每小时或每日额度达到上限：
   - 达到上限后的请求返回 429；
   - 已成功请求按实际规则计费；
   - 被拒绝请求不重复扣减。
3. 风险响应配置为“自动暂停令牌”：
   - 触发单次、小时或每日安全额度后，当前 Key 变为暂停；
   - 其他 Key 不受影响；
   - 操作日志出现可读的风险事件，而不是原始 action 字符串。
4. 通知渠道模拟失败：
   - 发送失败后释放本次通知许可；
   - 恢复渠道后仍可再次发送；
   - 不因两次短暂失败永久耗尽默认通知额度。

### 5.3 前端与文档

- default 和 classic 操作日志均能显示以下动作的可读标签：
  - `auth.logout_all`
  - `token.rotate`
  - `token.risk_detected`
  - `token.security_profile_update`
  - `token.security_profile_delete`
- OAuth 委托认证文档不再声明已经移除的完整 Key 查看或批量查看接口。

## 6. 监控面板与停止阈值

以下为建议初始阈值；如果生产基线更严格，应使用更严格的现有阈值。

| 指标 | 继续条件 | 暂停扩容条件 | 立即回滚条件 |
| --- | --- | --- | --- |
| 有效 Key 认证 | 无异常 | 偶发异常，先固定到单节点复现 | 任一可复现 401 |
| 5xx 比例 | 接近发布前基线 | 连续 5 分钟高于基线 0.5 个百分点 | 持续上升或影响主要请求 |
| 403 比例 | 接近基线 | 明显上升，检查代理 IP | 已配置 IP 白名单的正常请求被拒绝 |
| 429 比例 | 与既有策略一致 | 高于基线 20%，按原因拆分 | 低频基准 Key 被错误限流 |
| API P95 | 不高于基线 1.5 倍 | 连续 10 分钟超过 1.5 倍 | 持续恶化并伴随错误 |
| 数据库连接池 | 无等待或接近基线 | 等待/占用持续超过 80% | 连接耗尽或大量超时 |
| 数据库查询 P95 | 接近基线 | 超过基线 2 倍持续 5 分钟 | 锁等待或查询超时持续增加 |
| Redis P95/错误率 | 接近基线 | 延迟超过基线 2 倍 | 大量错误且影响认证 |
| master 状态 | 单实例稳定在线 | 偶发重启，停止下一阶段 | 重启循环或迁移失败 |
| `key_hash IS NULL` | 最终为 0 | 全量后仍大于 0 | 二次 master 回填后仍不下降 |

日志重点搜索：

- `database migration started`
- `backfill token key metadata`
- `no such column` / `unknown column`
- `duplicate` / `unique constraint`
- `relay error: token security budget or risk limit exceeded`
- `token security bypassed because Redis is unavailable`
- `system instance report failed`
- Redis 超时、数据库连接池耗尽和锁等待

## 7. 回滚方案

### 7.1 master 阶段失败

1. 不更新任何 slave。
2. 保持旧 slave 继续对外服务。
3. 摘除失败的新 master。
4. 使用发布前镜像恢复 master。
5. 保留已新增的数据库字段和已经回填的 `key_hash`/`key_hint`，不要删除列或索引。
6. 验证旧版本 master 和 slave 的存量 Key 认证正常。

本版本保留明文 `tokens.key`，额外字段不会阻止旧版本继续按明文认证。

### 7.2 slave 灰度阶段失败

1. 立即停止后续批次。
2. 从负载均衡摘除出现问题的新 slave。
3. 将该批次回滚到发布前镜像。
4. 保持已经验证稳定的新 master 在线；如问题确认与新版本通用逻辑有关，再回滚 master。
5. 不恢复数据库备份，不删除新字段；只有确认发生数据损坏时才进入单独的数据恢复流程。

### 7.3 全量后的回滚边界

- 在第二阶段明文清理前，可以滚动回滚到发布前版本。
- 混部期由新版本创建或轮换的 Key 保留明文，因此旧版本仍可认证。
- 一旦未来执行明文清理，最低可回滚版本变为本兼容桥接版本，不能再回滚到仅支持明文查询的旧版本。

## 8. 发布期间禁止事项

- 禁止变更、删除或让任一实例回落到不同的 `CRYPTO_SECRET`。
- 禁止先于 master 更新 slave。
- 禁止 master 与全部 slave 同时更新。
- 禁止在本次发布中执行 `tokens.key` 明文清理。
- 禁止同时启用或调整平台默认 Token 安全策略。
- 禁止同时调整模型请求限流、倍率或固定调用费用。
- 禁止执行 Redis `FLUSHALL` 或全库删除缓存。
- 禁止在普通回滚中删除新字段、索引或恢复整个 `tokens` 表。
- 禁止仅凭容器“Running”判定成功，必须以 `/healthz`、实例版本、业务验收和监控共同放行。

## 9. 发布收口

满足以下条件后，本次第一阶段灰度发布完成：

- 所有在线实例均为目标版本；
- 系统实例列表中只有一个 master，其余均为 slave；
- 旧实例超过 90 秒未上报并已确认退出；
- 有效 Token 的 `key_hash IS NULL` 数量为 0；
- 旧 Key、新建 Key、轮换 Key 和缓存未命中验收通过；
- 429、自动暂停、余额扣减、使用日志和通知许可验收通过；
- 连续观察至少 30 分钟，无新增 401、5xx、数据库或 Redis 异常；
- 平台默认安全策略及生产限额在发布期间未发生变化；
- 发布镜像、版本、时间、各批次节点、验收结果和异常处置已记录。

## 10. 第二阶段安排

最终哈希存储迁移必须作为独立发布，不得紧接本次灰度自动执行。开始第二阶段前至少满足：

- 本兼容版本已稳定运行一个完整观察周期；
- 不存在任何旧版本实例或离线后可能重新加入的旧镜像；
- `key_hash IS NULL` 持续为 0；
- 已完成可恢复备份；
- 已明确新的回滚最低版本；
- 明文清理脚本可观察、可重复执行并经过生产同版本数据量演练。

第二阶段的具体脚本、锁影响、分批方式和回滚预案应另行评审。
