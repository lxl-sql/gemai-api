# 生产额度与多实例加固修复

> 日期：2026-07-08  
> 场景：10w 用户生产环境，多实例部署（1 master + 多 slave）  
> 目标：堵住额度超用/漏扣费窗口，降低日志库与任务轮询对数据库的冲击。

## 1. 已落地修复

### 1.1 信任额度旁路默认关闭
- `common.GetTrustQuota()` 不再默认返回 10 个额度单位，默认返回 `0`。
- `BillingSession` 与旧 `PreConsumeQuota` 路径统一：`trustQuota <= 0` 时不会跳过预扣。
- 如确需灰度恢复，可显式配置：
  - `TRUST_QUOTA=<绝对 quota 值>`
  - 或 `TRUST_QUOTA_UNITS=<额度单位数>`（会乘以 `QuotaPerUnit`）

生产建议：保持默认关闭。高余额用户也必须走 DB 原子预扣，避免多实例并发同时读到旧余额后全部打上游。

### 1.2 结算失败持久化补偿
- 新增 `billing_settlement_failures` 表，`request_id` 唯一。
- `SettleBilling` / legacy `PostConsumeQuota` 结算失败时，不再只写 error log，而是登记待补偿记录。
- 新增 system task：`billing_settlement_repair`。
- 请求发生在 slave 时只写 DB 补偿记录；真正执行由 master 的 system task runner 周期扫描并通过 DB lease 去重。
- 若失败发生在“资金已提交但 token 调整失败且资金回滚失败”的阶段，会记录 `funding_settled=true`，重试时只补 token，避免重复扣钱包/订阅。

相关环境变量：
- `BILLING_SETTLEMENT_REPAIR_ENABLED=true`：默认开启。
- `BILLING_SETTLEMENT_REPAIR_INTERVAL_SECONDS=60`：repair task 调度间隔，最低 15 秒。
- `BILLING_SETTLEMENT_REPAIR_BATCH_SIZE=100`：单轮处理条数，最大 1000。
- `BILLING_SETTLEMENT_RETRY_DELAY_SECONDS=60`：失败后延迟重试，避免欠费用户未充值前被高频扫表。

### 1.3 Midjourney 改为请求上游前扣费
- `RelayMidjourneySubmit` 和 `RelaySwapFace` 已改为上游请求前 `PostConsumeQuota` 硬扣。
- 上游未接收、HTTP 非 200、任务入库失败时立即退还预扣。
- 只有“上游已接收且任务入库成功”的任务才保留 `quota` 与钱包拆分字段。
- 轮询阶段仍通过 `UpdateWithStatus` CAS 抢状态，只有抢到失败状态更新的实例会退款，避免多实例重复退款。

### 1.4 Redis / token 额度一致性
- 修复 `GetUserCache` 回源 DB 后只写非额度字段的问题，改为完整写入 Redis user hash。
- token 额度增减改为强一致 DB 更新，不再受 `BATCH_UPDATE_ENABLED` 影响。
- `BATCH_UPDATE_ENABLED` 仍可用于 used_quota/request_count/channel_used_quota 这类统计，但不再用于 token 余额边界。

### 1.5 日志与任务轮询性能
- 管理员 `logs` 查询默认加时间窗：`LOG_QUERY_DEFAULT_DAYS=7`，可配置，最大 365 天。
- `logs` 与 `operation_logs` 管理查询使用有界计数：`LOG_SEARCH_COUNT_LIMIT=10000`，最大 100000。
- `SumUsedQuota` 无时间参数时默认只统计近期窗口，避免仪表盘全表聚合。
- `GetAllUnFinishTasks` 改为按 `id asc` + `LIMIT` 分批，默认 `MIDJOURNEY_TASK_QUERY_LIMIT=1000`，最大 10000。
- `operation_logs` 在 PostgreSQL 下删除改为子查询分批删除，兼容 PG 不支持 `DELETE ... LIMIT`。
- 独立 `LOG_SQL_DSN` 的 PostgreSQL 日志库也会应用 `logs` / `operation_logs` autovacuum 调优。

## 2. 多实例部署注意事项

- 只有 master 启动 `system_task` runner；slave 处理请求、写补偿表，不执行 repair loop。
- 即使误配多个 master，`system_tasks` + `system_task_locks` 也会按任务类型做 DB lease 去重。
- `NODE_TYPE=slave` 的节点不会执行 DB migration、日志库 migration、system task runner。
- 生产务必保证至少一台 master 存活，否则补偿任务和 MJ/异步轮询不会运行。
- `SQL_MAX_OPEN_CONNS` 仍建议单实例 20~50，所有实例总和必须小于 PG `max_connections`。

## 3. 上线后观察项

- `billing_settlement_failures`：正常应接近 0；若持续 pending，说明用户欠费、token 缺失或 DB/Redis 仍有异常。
- `system_tasks` 中 `billing_settlement_repair`：应周期性成功，`failed` 不应持续增长。
- `pg_stat_activity`：不应再出现分钟级以上 `idle in transaction`。
- `logs` / `operation_logs` 查询延迟：后台无时间筛选时应明显下降。
- MJ 失败退款：应只对有 `wallet_quota_consumed` / `wallet_gift_quota_consumed` 或历史已扣费任务退款。
