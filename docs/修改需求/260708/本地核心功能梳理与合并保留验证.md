## 2. 钱包拆分：充值额度 / 赠送额度

### 2.1 数据模型（`model/user.go`）

```go
// API contract after wallet split:
// quota is recharge quota only, not total remaining quota.
Quota           int  // 充值额度（真金白银充值所得）
GiftQuota       int  // 赠送额度（注册/签到/兑换/邀请/管理员赠送）
TotalQuotaValue int  // gorm:"-:all"，仅响应用：quota + gift_quota
```

**语义约定（重要，前后端契约）：**

- `quota` 字段在钱包拆分后**只表示充值额度**，不再是总余额；
- 总余额一律用 `TotalQuota()`（= Quota + GiftQuota）或响应中的 `total_quota`；
- 余额变更**禁止**直接 `Updates(user)` 写回——`UpdateWithTx` 已用
  `Omit("quota", "gift_quota", "used_quota", "request_count", "aff_quota", "aff_history", "aff_count")`
  强制拦截，防止请求快照覆盖并发扣费结果（丢更新）；
- 所有余额变更必须走统一钱包服务 `model/quota_transaction.go`。

### 2.2 扣费顺序：先赠送、后充值

`DebitQuotaPreferGift*` 系列实现"赠送额度优先消耗"：

```go
func debitQuotaPreferGiftSplit(giftQuota int, amount int) (rechargeDebit, giftDebit int)
```

调用入口（均已核对保留）：

| 场景 | 调用点 |
|---|---|
| 相对预扣费 | `service/pre_consume_quota.go` → `DebitQuotaPreferGiftNoLedger` |
| 结算扣费 | `service/quota.go:500` |
| 异步任务差额补扣 | `service/task_billing.go:100` |
| 资金源抽象 | `service/funding_source.go`（钱包/订阅双资金源） |
| 订阅购买 | `model/subscription.go` → `DebitQuotaPreferGiftTx` |

### 2.3 入账来源与桶归属

| 来源 | 入账桶 | 函数 | 幂等键 |
|---|---|---|---|
| 在线充值（易支付/Stripe/Creem/Waffo/WaffoPancake） | 充值额度 | `CreditRechargeQuota(Tx)` | 订单号维度 |
| 兑换码 | 按码配置拆分 `Quota` + `GiftQuota` | `CreditQuotaBreakdownTx` | `redemption:<id>:<userId>` |
| 注册赠送 | 赠送额度 | `CreditGiftQuotaTx` | `register_gift:<userId>` |
| 签到（`model/checkin.go`） | 赠送额度 | 事务内入账 | 每日一次 |
| 邀请奖励 | 赠送额度 | `IncreaseUserGiftQuota` / `inviteUser` | — |
| 管理员调整 | 可选桶（`quota_type`: recharge/gift） | `AdjustQuota(userId, bucket, mode, value, ref)` | `admin_adjust:<adminId>:<userId>:<uuid>`，前端可传自定义键 |
| 退款 | 按原扣费拆分原路退回 | `RefundQuotaByBreakdown(NoLedger)` / `RefundQuotaByTransaction` | 引用原流水 |

**管理端接口变化点**：`ManageUser`（`controller/user.go`）的 `add_quota` 动作请求体扩展了
`quota_type`（桶选择）和 `idempotency_key`（幂等）两个字段，全部走 `model.AdjustQuota`。

### 2.4 并发与一致性设计

- **进程内 per-user 互斥锁**（`lockQuotaUser`）：同一用户的额度事务先在实例内串行化，
  数据库端每个用户行的锁等待者最多为实例数个（历史上曾把 users 表行锁队列打爆并阻塞 autovacuum）；
  锁带引用计数，无等待者即从 map 删除，避免锁池无界增长；
- **PostgreSQL 快路径**：`tryApplyQuotaDeltaAtomicPG` 用单条条件 UPDATE 原子扣减（`quota >= ?` 守卫），
  失败再降级到锁行事务；
- **SQLite**：无行锁，靠 per-user 互斥锁补偿（签到、兑换等场景同理）；
- **幂等**：`idempotency_key` 唯一索引，重复提交返回原流水（`QuotaBreakdown.IdempotencyReused`）。

## 3. 钱包流水（quota_transactions）

### 3.1 流水记录内容

每笔余额变更记录（`QuotaTransactionRecord`）包含：

- 双桶增量：`quota_delta` / `gift_quota_delta`（正入负出）；
- **变更前后快照**：`balance_before/after`、`gift_balance_before/after`（可对账、可审计）；
- 分类：`type`（见下）、`source`（system/admin/legacy）、`direction`；
- 关联：`reference_type` + `reference_id`（如 `redemption:123`、`user:45`）、`idempotency_key`、`operator_id`；
- 元数据：`metadata` JSON（如 mode/value/quota_type）。

流水类型常量（`model/quota_transaction.go`）：

```
topup / gift / redemption / consume_pre / consume_settle /
refund / admin_adjust / aff_transfer / subscription_buy
```

> 注意：高频消费扣费走 `*NoLedger` 变体（不落流水，只保证余额原子性），
> 避免每次对话请求产生一条流水记录；充值、兑换、管理员调整等低频高价值操作才落账。

### 3.2 API 与前端

| 端点 | 权限 | 处理器 |
|---|---|---|
| `GET /api/quota-transactions/` | 管理员 | `GetAllQuotaTransactions`（支持 user/type/source/bucket/时间过滤） |
| `GET /api/quota-transactions/self` | 用户 | `GetSelfQuotaTransactions` |
| `GET /api/user/self/quota-transactions` | 用户 | 同上（selfRoute 别名） |

前端页面（default 主题，均保留）：

- `web/default/src/features/quota-transactions/` — 管理员流水列表；
- `web/default/src/features/wallet/` — 用户钱包页（余额卡片、划转、兑换、流水）。

## 4. 操作记录（OperationLog）

### 4.1 设计（`model/operation_log.go`）

独立审计表，与计费日志（`logs` 表）分离，落在 `LOG_DB`（配置 `LOG_SQL_DSN` 后进独立日志库）：

```go
type OperationLog struct {
    Id, CreatedAt, OperatorId, OperatorName, OperatorRole
    Action   string // "<category>.<action>" 稳定字符串，禁止改已发布的值
    Category string // auth/user/token/finance/channel/redemption/system
    TargetType, TargetId, Success, Ip, UserAgent
    Detail   string // JSON，写入前经 sanitize 脱敏
}
```

- **动作枚举**：`OpAction*` 共 40+ 个，覆盖登录/注册/改密/2FA/Passkey/OAuth 绑定与授权、
  用户增删改、令牌、充值/兑换/划转、渠道增删改与查看密钥、兑换码、系统配置、模型管理；
- **敏感字段脱敏**：`sensitiveDetailKeys`（password/key/secret/token/client_secret/api_key/private_key 等）
  递归遮蔽后才入库。

### 4.2 关键记录点（合并冲突中逐一保住的）

| 记录点 | 文件 | 说明 |
|---|---|---|
| 登录统一收敛 | `controller/user.go` `setupLoginWithOperationDetail` | 密码/2FA/Passkey/所有 OAuth 登录最终都调它，OAuth 登录带 provider 明细 |
| 配置修改 | `controller/option.go` | 只记 Key 不记 Value（防泄密） |
| 渠道操作 | `controller/channel.go` | 创建/更新/删除/查看密钥（含失败尝试） |
| 用户管理 | `controller/user.go` | 创建/更新/删除/manage 动作，额度调整带 transaction_id |
| 2FA 强制禁用 | `controller/twofa.go` | 管理员身份经 admin_info 传递，不在普通用户可见内容中泄露 |
| Passkey | `controller/passkey.go` | 注册/删除/管理员重置 |
| 兑换码 | `controller/redemption.go` | 批量创建（含 gift_quota 明细）、兑换成功 |

### 4.3 API 与运维

- 路由：`GET /api/operation-log/`（管理员查询）；
- 前端：`web/default/src/features/operation-logs/`；
- 清理：系统设置 → 日志维护，本地保留了**用量日志/操作日志分开清理**
  （`deleteLogsBefore` / `deleteOperationLogsBefore`，合并时已把上游删掉的前端 API 补回）；
- 迁移：`migrateLOGDB` 保留 `&OperationLog{}` 的 AutoMigrate（ClickHouse 日志库模式下不建此表，
  操作日志功能依赖关系型日志库）。

## 5. OAuth 体系

### 5.1 OAuth 登录（作为客户端）

- **Provider 抽象**（`oauth/` 包）：`provider.go` + `registry.go` 统一注册，
  内置 GitHub / Discord / LinuxDO / OIDC / generic 五种（`oauth/*.go`）；
- **统一入口**：`controller/oauth.go` `HandleOAuth` → `findOrCreateOAuthUser`，
  登录失败记 `recordOAuthLoginFailed`，邮箱冲突返回 i18n 错误（合并时叠加了上游的
  `ErrEmailAlreadyTaken` 处理）；
- **自定义 OAuth 提供商**：`model/custom_oauth_provider.go` + `controller/custom_oauth.go`，
  管理员可动态配置任意 OAuth2 源；绑定关系存 `model/user_oauth_binding.go`；
- **OAuth 流程中的 2FA**：OAuth 登录命中已开启 2FA 的账号时要求二次验证后才 `setupLogin`。

### 5.2 OAuth 授权服务器（对外提供 OAuth，本站作为身份源）

完整的 OAuth2 Authorization Server 实现，全部保留：

| 组件 | 文件 | 说明 |
|---|---|---|
| 应用管理 | `model/oauth_app.go` + `controller/oauth_app.go` | 用户自助创建应用、redirect_uri 白名单校验（强制 HTTPS/回环 HTTP）、client_secret 重置 |

| 授权关系 | `model/oauth_grant.go` | user×client 唯一、refresh token 轮换、可撤销 |
| 端点 | `controller/oauth_server.go` | `/api/oauth_server/authorize`、`/token`（限流）、`/userinfo`、`/grants`；支持 PKCE（S256）、refresh_token grant、委托 access token 签发 |

（`PageLayout.jsx` 的 `/oauth/authorize` fullscreen 分支，合并时已保住）。

### 5.3 邮箱策略（与 OAuth/注册联动）

- 本地 `common/email_policy.go`：`ValidateEmailPolicy` 统一校验
  （域名白名单、别名限制、**按域名的 local-part 正则规则** `EmailLocalPartRules`）；

  绑定落库用上游的 `model.BindEmailToUser`（`withNormalizedEmailLock` 邮箱级锁，防并发绑定同邮箱）。

## 6. 合并期间的适配改动（行为等价，实现有变）

### 6.1 注册赠送入账时机

原：`Insert` 成功后调 `CreditGiftQuota`（独立事务）。
现：随上游 `Insert` 重构（`withNormalizedEmailLock` 包裹事务），赠送入账改为**同事务内**
`CreditGiftQuotaTx`，幂等键不变（`register_gift:<userId>`）。原子性更强：用户创建与赠送要么都成功要么都回滚。
`InsertWithTx`（OAuth 注册路径）同理。`user.Quota = 0; user.GiftQuota = 0` 起始语义不变。

### 6.2 AffCode 生成

`GenerateAffCode` 原来在事务内用全局 `DB` 查重，上游把 Insert 包进事务后会在 SQLite 上**自死锁**
（测试卡死 4 分钟定位）。已拆出 `generateAffCodeTx(tx)`，事务内传 tx；对外函数签名不变。

### 6.3 兑换码 Redeem

保留本地实现（CAS 状态翻转 + `CreditQuotaBreakdownTx` 拆桶入账 + 幂等），
叠加上游的 `lockForUpdate` 行锁（MySQL/PG 下减少无效竞争，SQLite 自动跳过）。
返回结构仍是本地的 `*RedemptionRedeemResult`（含 redemption_id/transaction_id/quota/gift_quota）。

### 6.4 数据库类型判断 API

上游删除了 `common.UsingSQLite/UsingPostgreSQL/UsingMySQL` 布尔变量，
本地 `quota_transaction.go`、`utils.go`、`main.go`、`log.go` 中的引用已替换为
`common.UsingMainDatabase(common.DatabaseTypeXxx)` / `UsingLogDatabase(...)`，逻辑不变。

### 6.5 任务计费

本地的 `persistTaskBillingState`（quota + private_data 一并回写）、`RecalculateTaskQuota`、
钱包感知退款 `RefundQuotaByBreakdownNoLedger`（Midjourney/视频任务）全部保留；
rc.20 的 `PriceData.OtherRatios` 字段→方法重构已适配。

## 7. 已知行为差异（需要知晓/决策）

### 7.1 Codex OAuth 引导流程被上游方案替换

原 `main` 有 `controller/codex_oauth.go`：后台向导式发起 Codex OAuth
（`POST /api/channel/codex/oauth/start|complete`），拿授权码自动换 key 写入渠道。
上游 `chore: update Codex channel (#5461)` 重构后该文件与路由被移除，现行方式：

- 渠道 Key 直接粘贴 Codex OAuth key JSON（`relay/channel/codex/oauth_key.go` 解析）；
- **凭据自动刷新保留且更强**：`service/codex_credential_refresh.go` + 定时刷新任务，
  手动刷新 `POST /api/channel/:id/codex/refresh`、用量查询 `GET /:id/codex/usage` 都在
  （迁移到了 `router/channel-router.go` 的权限化路由）。

> 若仍需要"点按钮发起 OAuth"的引导体验，需要从原 main 把 `codex_oauth.go` 及 4 条路由
> cherry-pick 回来并适配新权限路由；日常使用上游方式可完全替代。

### 7.2 双审计体系并存

合并后存在两套审计写入：

- **本地 OperationLog**（独立 `operation_logs` 表）：登录、用户/渠道/令牌/兑换码/配置等核心操作，
  前端"操作记录"页面读这张表——**主审计源，功能完整**；
- **上游 audit**（写 `logs` 表 type=manage）：自动合并进来的新功能沿用上游风格，
  目前有 15 处调用（渠道标签批量操作、渠道复制/批量状态、上游配置应用、订阅计划重置等）。

影响：上游新功能的操作痕迹在"使用日志"（type=管理）里而非"操作记录"页。
另外上游的登录日志（`RecordLoginLog`，type=7）**未启用**（本地登录审计走 OperationLog），
因此上游前端"日志类型=登录"的筛选项查不到数据，属预期。
后续可选统一：把这 15 处 `recordManageAudit` 调用逐步改写为 `model.RecordOperationLog`。
