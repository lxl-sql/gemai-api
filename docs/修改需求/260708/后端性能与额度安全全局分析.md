## 1. 额度超用分析（最紧急）

### 1.1 正常计费链路（先理解设计）

```
请求 → TokenAuth（校验+写 user/token 到 context）
     → Distribute（仅选渠道，不扣费）
     → controller.Relay
          → 估算 QuotaToPreConsume
          → PreConsumeBilling  ← ★ 预扣（或信任跳过）
          → [上游请求]
          → PostTextConsumeQuota → SettleBilling ← ★ 结算差额
```

钱包硬扣在 DB 层有原子守卫（PostgreSQL 走 `UPDATE ... AND quota+delta >= 0`，
MySQL/SQLite 走 `SELECT ... FOR UPDATE`），**DB 余额本身一般不会变负**。
所以"超额"不是数据库层面的负数，而是**业务层面：用户已经享受了上游服务，但钱没扣到**。

### 1.2 【A1】信任额度旁路 —— 最主要的超额入口

`common/quota.go`：

```go
func GetTrustQuota() int {
    return int(10 * QuotaPerUnit)  // 10 个额度单位 = 5,000,000 quota
}
```

`service/billing_session.go:305-338` `shouldTrust`：当满足
①非异步任务 ②token 充足（unlimited 或 `token_quota > trustQuota`）③钱包余额 `UserQuota > trustQuota`，
则 `effectiveQuota = 0` —— **完全跳过预扣**，直到请求结束 `Settle` 时才一次性扣。

**超额场景**：一个余额 600 万的用户同时发起 N 个大请求，
每个都因"余额充足"跳过预扣直接打上游，N 个请求的实际总消耗可以远超 600 万。
等到逐个 `Settle` 时，DB 原子守卫会让超出部分扣费失败，但**上游服务已经全部提供了**。

**影响面**：余额越高、并发越大、单请求越贵（长上下文/大 `max_tokens`），白嫖窗口越大。
这是设计上的性能取舍（避免高余额用户每次请求都锁行扣费），但在生产被利用了。

**缓解建议**（按代价从低到高）：
1. **降低信任阈值**或按环境变量可配（当前硬编码 500 万）；
2. 高价值模型/大 `max_tokens` 请求**强制预扣**（`ForcePreConsume=true`，任务路径已经这么做了）；
3. 对同一用户的**并发在途请求数**做限制（信任旁路只在低并发下安全）。

### 1.3 【A2】结算失败只记日志，响应照常返回

`service/text_quota.go:387-389`：

```go
if err := SettleBilling(ctx, relayInfo, summary.Quota); err != nil {
    logger.LogError(ctx, "error settling billing: "+err.Error())
}
// ← 没有 return / 没有拦截，函数继续，响应已经发给用户
```

同一函数里 `UpdateUserUsedQuotaAndRequestCount`（`:383`，统计用的 `used_quota`）
和 `SettleBilling`（真正扣钱包）是**两条独立路径**。若 `SettleBilling` 失败：
`used_quota` 涨了、日志记了消费，但**钱包/令牌余额没减** → 直接白嫖。

audio、wss（实时）走同类逻辑，同样问题。

**建议**：`SettleBilling` 失败要么重试落库、要么进入补偿队列（异步兜底扣费），
至少要有告警监控。不能"只打一条 error 日志"。

### 1.4 【A3】Midjourney 后置扣费（TOCTOU）

`relay/mjproxy_handler.go:214-240`（我已核对）：

```go
userQuota, _ := model.GetUserQuota(info.UserId, false)  // ① 读余额（可能读缓存）
if userQuota - priceData.Quota < 0 { return quota_not_enough }  // ② 软检查
mjResp, _, err := service.DoMidjourneyHttpRequest(...)   // ③ 先打上游！
defer func() {
    if 成功 { service.PostConsumeQuota(info, priceData.Quota, 0, true) }  // ④ 事后扣
}()
```

②和③④之间是经典 TOCTOU 窗口：并发多个绘图请求都能通过②的软检查，
全部打上游③，然后④逐个扣费——后面的会扣失败，但图已经生成、上游算力已消耗。
Midjourney 完全没走 `BillingSession`，没有预扣保护。

**建议**：MJ 接入 `BillingSession` 预扣模型，或至少在③之前用 `DebitQuotaPreferGiftNoLedger` 硬扣。

### 1.5 【A4】信任判断依赖的余额是"快照/缓存"

`shouldTrust` 里：
- `s.relayInfo.UserQuota`（`:328`）来自 `RelayInfo` 构造时的 `ContextKeyUserQuota`，
  是 **TokenAuth 阶段**（`middleware/auth.go`）从 `GetUserCache` 读的，请求生命周期内不刷新；
- `token_quota`（`:319`）同样是 auth 时 `token.RemainQuota` 的快照（`auth.go:457`）；
- `GetUserQuota(id, false)`（`model/user.go:1088`）**优先读 Redis 缓存**，扣费后靠
  `invalidateUserCache` 删 key 再回源，不是原子递减，存在 stale read 窗口。

三者叠加：缓存/快照读到偏高的旧余额 → `shouldTrust` 误判为 true → 放大 A1。

**建议**：信任判断（尤其钱包余额）用 `GetUserQuota(id, true)` 强制读库，
或干脆收紧信任阈值让这条路径少触发。

### 1.6 令牌额度侧的次要风险

- `BATCH_UPDATE_ENABLED=true` 时，令牌扣减走内存聚合 flush（`model/utils.go` + `token.go:411`），
  **没有 `remain_quota >= ?` 下限守卫**，令牌维度余额可被打负（默认关闭，生产若开启需注意）；
- Redis 令牌缓存 `cacheDecrTokenQuota` 用 HINCRBY，但 **key 不存在/无 TTL 时静默跳过**
  （`common/redis.go`），造成 cache 与 DB 漂移。

## 2. SQL 查询与性能问题

> 完整清单见探查记录，这里列生产影响最大的。数据库需同时兼容 SQLite/MySQL/PostgreSQL。

### 2.1 高危

**【B1】管理员日志查询无界 COUNT + 无默认时间窗** — `model/log.go:535`、`controller/log.go:16-29`
`GetAllLogs` 对 `logs` 表 `Count(&total)` 没有像用户侧那样的上限（用户侧有 `logSearchCountLimit=10000`，`log.go:594-625`），
`start_timestamp/end_timestamp` 默认 0 时等于全表 COUNT。亿级日志表上每次翻页都可能触发极慢 COUNT。
→ **建议**：加 COUNT 上限 + 强制默认时间窗（7/30 天）。

**【B2】日志统计无时间窗全表聚合** — `model/log.go:650-701`
`SumUsedQuota` 在 `startTimestamp==0` 时对整表 `sum(quota)`。仪表盘不带时间参数就会触发。
→ **建议**：API 层强制 `start_timestamp`。

**【B3】Midjourney 轮询全量拉取** — `model/midjourney.go:96-104`
`GetAllUnFinishTasks()` 用 `progress != '100%'` **无 LIMIT** 全量 `Find`，每轮询周期执行一次。
对比 `task.go` 的 `GetAllUnFinishSyncTasks(limit)` 有 LIMIT，此处是缺口。
→ **建议**：分批 + LIMIT 轮询。

**【B4】订阅重置遗留失效的 FOR UPDATE** — `model/subscription.go:1096-1099,1118-1121`
仍用 `tx.Set("gorm:query_option", "FOR UPDATE")`，GORM v2 下是 **NO-OP**（项目 `model/locking.go` 已说明）。
`AdminResetUserSubscriptionsByPlan` 并发下无行锁，可能重复重置。
→ **建议**：改用同文件 `:1394,:1511` 已在用的 `lockForUpdate(tx)`。

**【B5】拆分日志库时 PG 热表调优未作用于 LOG_DB** — `model/main.go:235-247`
`applyPostgresHotTableTuning` 对主库 `DB` 执行 `ALTER TABLE logs SET(...)`，但配了 `LOG_SQL_DSN` 时
`logs` 在 `LOG_DB`，调优没生效，独立日志库死元组堆积、越查越慢。
→ **建议**：对 `LOG_DB` 同样应用 logs/operation_logs 的 autovacuum 参数。

**【B6】operation_logs 清理 PG 兼容** — `model/operation_log.go:352`
`DeleteOldOperationLog` 直接 `Limit().Delete()`，而 `log.go:770-775` 对 PG 专门用了子查询 DELETE
（PG 不支持 `DELETE ... LIMIT`）。PG + 独立日志库下清理可能失败，operation_logs 无限增长。
→ **建议**：复用 log.go 的 PG 分批删除模式。

### 2.2 中危（索引与长事务）

| 问题 | 位置 | 建议 |
|---|---|---|
| 日志 `LIKE '%ip%'`/`content LIKE '%…%'` 前缀通配无法走索引 | `log.go:521-533` | 强制带 `created_at` 窄窗；IP 结构化建列 |
| `user_agent`/`upstream_request_id` 过滤无索引（合并中刻意移除） | `log.go:78-83,507-528` | 低峰 `CREATE INDEX CONCURRENTLY` |
| 缺 `(user_id, created_at)`、`(channel_id, created_at)` 复合索引 | `log.go:60-67` | 按 EXPLAIN 补复合索引 |
| 充值表 `create_time` 无索引 | `topup.go:16-22` | 加 `(user_id, create_time DESC)` |
| 按套餐重置一次锁全部 active 订阅（无 LIMIT） | `subscription.go:1113-1128` | 分批重置 |
| 订阅过期/周期重置按 userId 循环开事务（N 事务） | `subscription.go:1203-1274,1503-1524` | 批量/合并事务，预载 plan |
| Channel 缓存刷新双表全量 Find + 全量解密 key | `channel_cache.go:33-43` | 只加载 enabled；降低 Init 频率 |
| quota_data 刷盘逐行 SELECT+UPDATE（N+1） | `usedata.go:108-121` | `INSERT ... ON CONFLICT` 批量 upsert |
| `LOWER(email)=?` 无法走 email 索引 | `user.go:1010` | 持久化 `email_normalized` 列 + unique |
| 用户/渠道搜索前后通配 LIKE、role/status/type 无索引 | `user.go:377-404`、`channel.go:379-405` | 前缀搜索或加索引 |

### 2.3 低危

分页普遍 COUNT+SELECT 双查询、只读列表包无意义事务、部分 `Count` 吞错返回 0（`task.go:523`、`midjourney.go:217`）、
批量插入固定 chunk=50、兑换码批量创建无分批（超大批次单事务过大）等。详见探查记录。

## 3. 接口安全与健壮性

### 3.1 高危

**【C1】Midjourney 图片代理无鉴权** — `router/relay-router.go:204-205`、`relay/mjproxy_handler.go:29-69`
`GET /mj/image/:id` 注册在 `TokenAuth` **之前**，凭 task ID 即可拉任意用户的生成图，可批量扫描刷上游带宽。
→ **建议**：移到鉴权之后，或校验 task 归属 + signed URL。

**【C2】Relay `/v1/*` 无全局限流** — `router/relay-router.go`（对比 `api-router.go:20` 有 `GlobalAPIRateLimit`）
relay 只有可选的 `ModelRequestRateLimit`（默认关闭）。有效 token 可无限并发打满后端和上游——这也直接放大第 1 节的额度超用。
→ **建议**：relay 加 token/user 级 QPS 限流，默认开启 model rate limit。

**【C3】管理员补单入账无二次确认** — `router/api-router.go:134`、`controller/topup.go:565-605`
`POST /api/user/topup/complete` 仅 `AdminAuth`，任意管理员（或被盗会话）可把 pending 订单标记成功并入账。
→ **建议**：改 `RootAuth` 或加 `SecureVerificationRequired` + 强审计告警。

**【C4】操作审计日志可被 Admin 删除** — `router/api-router.go:355`、`controller/operation_log.go:82`
`DELETE /api/operation-log/` 仅 `AdminAuth`，可清除登录/充值/管理痕迹妨碍取证。
→ **建议**：改 `RootAuth` 或禁止 HTTP 删除。

**【C5】setup 初始化接口无鉴权无限流** — `router/api-router.go:23-24`、`controller/setup.go`
部署首次窗口内可并发抢建 Root（100M 额度）。
→ **建议**：部署后立即完成初始化；`PostSetup` 加 IP 限流。

### 3.2 中危

- **OAuth App 控制器 session/Bearer 不一致**（`controller/oauth_app.go` 用 `session.Get("id").(int)` 强制断言，
  管理员用 Access Token 调用可能 panic → DoS）— `router/api-router.go:228`；建议统一 `c.GetInt("id")`；
- **`SearchChannels` 全量加载内存分页且 page_size 无 100 上限** — `controller/channel.go:268-372`；
- **`ManageMultiKeys` pageSize 无上限** — `controller/channel.go:1501`；
- **支付/兑换 Webhook 回调无限流** — `router/api-router.go:58-78`（幂等做得好，但验签失败路径仍耗资源）；
- **`/api/user/groups` 无鉴权泄露分组倍率** — `router/api-router.go:79`；
- **签到仅 Turnstile 无 CriticalRateLimit**、**GenerateAccessToken 无限流** — `api-router.go:122,89`；
- **限流可被环境变量整体关闭**（`CRITICAL_RATE_LIMIT_ENABLE=false`）— 生产应强制开启。

### 3.3 做得好的地方（无需改）

- **越权（IDOR）**：token/topup/redemption/subscription/quota-transaction 的自助接口都正确用
  `c.GetInt("id")` 而非请求传入的 userId；
- **支付幂等**：Epay/Stripe/Waffo/Creem 回调都有验签 + `LockOrder` + 状态 CAS + idempotency key，防重放到位；
- **兑换码**：事务内 status CAS + 幂等键，并发只成功一次（有单测）；
- **主流分页**：`GetPageQuery` 已限制 page_size ≤ 100。

## 4. 与合并的关系

这些问题**基本都是上游原有设计，不是本次合并引入的**：

- 信任额度旁路（A1）、MJ 后置扣费（A3）、结算失败只记日志（A2）在 rc.19 之前就存在；
- 合并反而**吸收了上游的计费加固**（int32 饱和转换、行锁集中化 `lockForUpdate`、数量参数校验），
  是往好的方向走；
- 唯一与合并相关的：B4 的失效 `FOR UPDATE` 出现在订阅管理里，上游其他地方已改用 `lockForUpdate`，
  这两处是漏网的（可能是上游自己没改干净）。

所以修复这些问题不会和上游冲突，属于在当前分支上的独立加固。

## 5. 建议的修复优先级

**第一批（止血，直接堵白嫖）：**
1. A2 结算失败不能静默——加补偿/告警（改动小，收益最大）；
2. A1 信任阈值改为可配 + 调低，或对贵请求强制预扣；
3. C2 relay 加限流（同时缓解 A1 的并发放大）；
4. C1 MJ 图片鉴权。

**第二批（DB 稳定性）：**
5. B1/B2 日志查询加 COUNT 上限 + 默认时间窗；
6. B4 修复失效 FOR UPDATE；
7. B3 MJ 轮询加 LIMIT；
8. B5/B6 LOG_DB 的 PG 调优与清理兼容。

**第三批（纵深加固）：**
9. A3 MJ 接入 BillingSession；A4 信任判断读库；
10. C3/C4 补单和删审计改 RootAuth；
11. 索引补齐（logs 复合索引、topup、email_normalized）。
