# 接口安全：已修复项 + 需你决策的风险项

> 日期：2026-07-08
> 分支：`merge/v1.0.0-rc.19`
> 前置：本文承接《后端性能与额度安全全局分析.md》第 3 节接口安全。

## 1. 已修复（对正常用户零影响，纯 bug / 边界保护）

### 1.1 OAuth App 管理接口 Bearer 鉴权导致 panic（DoS）— 已修复
- **文件**：`controller/oauth_app.go`（6 个 handler）
- **问题**：路由用 `AdminAuth()`，它同时支持 session 和 Access Token(Bearer) 两种鉴权，
  两种都会写入 `c.Set("id", ...)`。但 handler 里用的是
  `session.Get("id").(int)` —— 管理员用 **Access Token** 调用时 session 为空，
  裸类型断言 `nil.(int)` 会 **panic**，被 recovery 中间件兜成 500（可被反复触发 DoS）。
- **修复**：统一改为 `c.GetInt("id")`（session/token 两条路径都已设置该值）。
- **为何零影响**：只影响管理员用 Bearer 调 `/api/oauth-app/*` 的场景，且是把"崩溃"
  变成"正常工作"；普通用户根本不经过这些接口。
- **顺带**：移除了不再使用的 `sessions` 导入。

### 1.2 ManageMultiKeys 分页 pageSize 无上限 — 已修复
- **文件**：`controller/channel.go`（`get_key_status` 分支）
- **问题**：管理端查询渠道多 key 状态时，`pageSize` 来自请求体且无上限，
  传入超大值会一次性返回海量 key 元数据，造成内存/序列化压力。
- **修复**：`pageSize > 200` 时截断为 200。
- **为何零影响**：管理员专用；默认 50，正常前端分页远小于 200；响应仍带 total，可翻页。

### 1.3 setup 初始化接口 — 复核后无需改
- `controller/setup.go` `PostSetup` 开头已有 `if constant.Setup { 拒绝 }`，
  初始化完成后无法再抢注 Root。对**已在运行**的生产系统不构成风险，
  故不改代码（仅提醒：首次部署时仍应尽快完成初始化）。

> 以上改动已 `go build ./...` 全绿，`go test ./controller ./middleware` 通过。

## 2. 需你决策：这些"修复"会改变用户可见行为，未擅自改

下面每一项安全上确实该做，但直接改**可能影响 10 万用户或现有管理流程**，
必须由你确认取舍。我给出每项的影响面与"安全灰度"方案。

### 2.1 Midjourney 图片代理无鉴权（`GET /mj/image/:id`）
- **位置**：`router/relay-router.go:204`（注册在 `TokenAuth()` 之前）。
- **风险点**：凭 task ID 可拉取任意用户的生成图，可被枚举扫描刷上游带宽。
- **为何不能直接加鉴权**：前端/客户端很可能用 `<img src="/mj/image/xxx">` 在浏览器里
  直接加载（无法带 Authorization 头）。**一旦加 TokenAuth，所有正在展示的 MJ 图会立刻裂图**——
  直接影响用户。
- **现有缓解**：handler 已有 SSRF 防护（不能借此打内网），危害限于"越权看图 + 刷带宽"。
- **安全方案（需你选）**：
  1. **签名 URL**：生成图时给 URL 附带短时效签名 token，`/mj/image` 校验签名而非登录态
     （对浏览器透明，不裂图）——推荐，但要改图片 URL 生成逻辑，工作量中等；
  2. **按 IP 限流**：给该路由加宽松限流（防批量扫描，正常浏览不受影响）——最快、最低风险；
  3. 维持现状。
- 我的建议：先上**方案 2（IP 限流）**止血，再排期方案 1。等你确认。

### 2.2 Relay `/v1/*` 无全局限流
- **位置**：`router/relay-router.go`（relay 组只有可选的 `ModelRequestRateLimit()`，默认不拦）。
- **风险点**：持有效 token 可高并发打满后端/上游，也放大了额度超用问题。
- **为何不能直接加全局限流**：这是 10 万用户的**核心热路径**。加一刀切 QPS 上限
  极易误伤正常高频用户（Agent/批量调用），属高风险改动。
- **安全方案（需你选）**：
  1. **用现成的 `ModelRequestRateLimit` 按模型/分组配置**上限（已内置，配置即可，改动最小）；
  2. 加**用户级**而非全局的宽松 QPS（阈值给足，只挡异常暴刷）；
  3. 维持现状，仅靠额度控制。
- 我的建议：走**方案 1**（配置化，不动代码、不误伤）。

### 2.3 `/api/user/groups` 匿名可访问，泄露分组倍率
- **位置**：`router/api-router.go:79`（无鉴权）。
- **风险点**：匿名可探测计费分组结构与倍率（商业信息）。
- **为何不能直接加鉴权**：这个接口很可能给**登录前的定价/注册页**用，加 `UserAuth`
  会让未登录页面拿不到数据而报错。已有 `/self/groups`（带 UserAuth）供登录后使用。
- **安全方案（需你选）**：
  1. 匿名时**只返回分组名、隐藏 ratio 等敏感字段**（保留页面可用性，去掉泄露）；
  2. 直接改 `UserAuth`（需先确认没有匿名页面依赖它）；
  3. 维持现状。
- 我的建议：**方案 1**（脱敏），既堵泄露又不裂前端。需确认前端字段依赖。

### 2.4 管理员补单入账 / 删除审计日志仅 AdminAuth
- **位置**：`POST /api/user/topup/complete`（`api-router.go:134`）、
  `DELETE /api/operation-log/`（`api-router.go:355`）。
- **风险点**：任意管理员（或被盗管理员会话）可手动给账户充值、可清除审计痕迹。
- **为何不能直接改**：改成 `RootAuth` 会**改变现有管理权限模型**——若你有子管理员
  在日常用这些功能，会被挡。这属于运营策略决定。
- **安全方案（需你选）**：
  1. 改 `RootAuth`（若只有一个 root=admin，无影响；有子管理员则会挡）；
  2. 保持 AdminAuth 但补单加 `SecureVerificationRequired`（二次验证）+ 强审计告警；
  3. 维持现状。
- 我的建议：补单走**方案 2**（二次验证）；删审计改 **RootAuth**（审计日志本就该只有 root 能动）。

### 2.5 其他（低危，建议配置而非改码）
- **签到 / GenerateAccessToken 无 CriticalRateLimit**：可加限流，但签到若 Turnstile 已开影响有限；
  建议按需在路由加 `CriticalRateLimit()`（改动小，但会影响这两个接口的高频调用者，需确认）。
- **支付 Webhook 无限流**：幂等已做好，验签失败仍耗资源；建议在**网关/WAF**层按 IP 限流，
  比改代码更安全（不影响正常回调）。
- **限流总开关可被 env 关闭**（`CRITICAL_RATE_LIMIT_ENABLE=false`）：确保生产为开启即可，无需改码。

## 3. 已确认无需改（做得好的地方）
- **越权(IDOR)**：token/topup/redemption/subscription/quota-transaction 自助接口都用
  鉴权得到的 `c.GetInt("id")`，非请求传入 userId；
- **支付幂等**：Epay/Stripe/Waffo/Creem 回调均有验签 + 订单锁 + 状态 CAS + 幂等键；
- **兑换码**：事务内状态 CAS + 幂等键，并发只成功一次；
- **主流分页**：`common.GetPageQuery` 已限制 page_size ≤ 100。
