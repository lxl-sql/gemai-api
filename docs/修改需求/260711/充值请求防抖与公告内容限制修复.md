# 充值请求防抖与公告内容限制修复

> 日期：2026-07-11  
> 范围：Default/Classic 钱包充值页面、系统公告校验与编辑、前端国际化。  
> 目标：避免自定义充值金额输入耗尽全局 API 限流，并修复公告正文长度过短、中文字符计数错误及前后端限制不一致的问题。

## 1. 充值金额计算请求防抖

### 1.1 问题

充值页自定义金额输入原先在每次 `onChange` 时立即调用金额计算接口：

- `/api/user/amount`
- `/api/user/stripe/amount`
- `/api/user/waffo-pancake/amount`

所有 `/api` 请求共用按客户端 IP 计数的 `GlobalAPIRateLimit`。默认限制为 180 秒内 360 次，因此长按数字输入框步进按钮、滚轮或自动化输入可能耗尽限流额度，并影响同一 IP 下的其他 API。

原实现还存在并发响应乱序风险：旧金额请求可能晚于新请求返回，覆盖最新支付金额。

### 1.2 修复

Default 和 Classic 前端统一采用：

- 输入停止 400ms 后再计算支付金额。
- 输入框失焦时立即执行仍在等待的计算。
- 选择预设金额或支付方式时取消待执行的输入计算。
- 页面卸载时清理定时器。

Default 在低于最低充值金额时不请求后端，并将支付金额显示为 0；同时使用请求序号保护结果，只有最新金额计算请求可以更新金额与加载状态，避免旧响应覆盖新结果。Classic 由数字输入组件约束最低金额，空值或无效输入会取消待执行计算。

涉及文件：

- `web/default/src/features/wallet/components/recharge-form-card.tsx`
- `web/default/src/features/wallet/index.tsx`
- `web/default/src/features/wallet/hooks/use-payment.ts`
- `web/classic/src/components/topup/RechargeCard.jsx`

## 2. 公告内容长度限制

### 2.1 原问题

后端原校验为：

```go
if len(content) > 500 {
    return fmt.Errorf("第%d个公告的内容长度不能超过500字符", i+1)
}
```

Go 的 `len(string)` 统计 UTF-8 字节数，而错误提示声称统计字符数，导致实际限制约为：

- ASCII 英文：500 个字符。
- 常见中文：约 166 个字符。
- 四字节 Emoji：约 125 个。

同时存在以下不一致：

- Default 前端按 JavaScript 字符串长度限制正文 500、说明 100。
- Classic 前端正文 `maxCount` 为 500。
- 后端正文限制 500 字节、说明限制 200 字节。
- 公告支持 Markdown/HTML，格式标记还会额外占用长度。

因此较完整的维护公告会在前端或保存接口处被拒绝。

### 2.2 新限制

调整为：

- 单条公告正文：最多 10,000 个 Unicode 码点。
- 单条公告说明：最多 500 个 Unicode 码点。
- 公告数量：最多 100 条。
- 整个公告 JSON：最多 512KB。

后端使用 `utf8.RuneCountInString` 统计正文和说明，中文不再按三个字节重复计数。总大小仍按序列化后的字节数限制，避免最多 100 条长公告全部注入公共 `/api/status` 后造成响应体膨胀。

校验错误增加公告发布时间，例如：

```text
第1个公告（发布时间2026-07-11T10:32:40+08:00）的内容长度不能超过10000字符
```

发布时间用于定位具体公告，避免页面按发布时间排序后，后端数组序号与可见行顺序不一致。

### 2.3 前端同步

Default：

- Zod 校验改为 Unicode 码点计数。
- 正文上限同步为 10,000。
- 说明上限同步为 500。
- 保存前检查总 JSON 是否超过 512KB。
- 校验消息通过 `t(...)` 国际化。

Classic：

- 移除原来的 500 字符输入限制。
- 保存单条公告时按 Unicode 码点校验正文和说明。
- 编辑区域显示当前字符数和上限。
- 保存全部公告前检查 512KB 总大小。

已同步以下语言：

- English
- 简体中文
- 繁体中文
- Français
- 日本語
- Русский
- Tiếng Việt

- `setting/console_setting/validation_test.go`

## 4. 部署注意事项

后端修改不会由前端开发服务器热更新。若保存时仍看到：

```text
第1个公告的内容长度不能超过500字符
```

说明请求仍由修改前启动的旧 Go 进程或旧容器处理，需要：

1. 重新编译后端。
2. 重启当前 Go 服务或容器。
3. 确认负载均衡后的所有实例均已更新，避免部分请求仍落到旧实例。
4. 重新构建并部署前端，必要时清理浏览器和 CDN 静态资源缓存。

当前源码中已不存在上述 500 字符后端错误。

## 5. 已发现的后续问题

Default 公告保存失败时可能同时出现：

- 一条“公告保存成功”。
- 两条内容相同的后端错误。

原因不是必然发送了两次请求，而是一次 HTTP 200 业务失败可能被三个位置分别处理：

1. 全局 API 响应拦截器提示业务错误。
2. `useUpdateOption` 的 `onSuccess` 再次提示相同业务错误。
3. `AnnouncementsSection.handleSaveAll` 未检查返回值中的 `success`，仍清除修改状态并提示保存成功。

建议后续统一业务错误所有权：

- `updateSystemOption` 对该调用设置 `skipBusinessError`，由 `useUpdateOption` 统一提示；或由全局拦截器统一提示并让 Hook 跳过。
- `handleSaveAll` 必须检查 `result.success`，只有真正成功时才能清除 `hasChanges` 并显示成功提示。
- 若浏览器 Network 面板确实出现两个 `/api/option/` PUT，再增加同步提交锁，防止按钮禁用状态生效前的快速双击。
