## 1. 故障现象

生产节点使用外部 PostgreSQL 和 Redis，`gemai-api` 容器出现退出或不可访问，页面同步无法打开。

已提供的 82 行容器日志显示：

- 23:04:20，容器内部对 `/api/status` 的请求返回 HTTP 200。
- 截至 23:04:22，首页、控制台、静态资源、API 和 CORS 预检仍在正常返回。
- 日志随后突然终止，没有 Go `panic`、`fatal`、PostgreSQL 连接错误或 Redis 连接错误。

因此，当前证据不能把故障定性为应用代码崩溃。“正常处理请求后日志直接截断”更符合进程被外部终止、宿主机 OOM、Docker/主机重启或存储异常的特征。

## 2. 已确认的配置问题

### 2.1 健康检查使用了错误的接口

生产配置使用：

```text
/api/status
```

该接口主要返回前端所需的系统设置，不会对 PostgreSQL 和 Redis 执行健康检查。即使外部依赖已经不可用，它仍可能返回 HTTP 200。

仓库已有的 `/healthz` 才是生产健康检查接口：

- `model.PingDB()` 失败时返回 503。
- 启用 Redis 后，Redis `PING` 失败时返回 503。
- 依赖正常时返回 200、`success=true` 和当前版本。

相关代码：

- `controller/misc.go`
- `router/api-router.go`
- `docker-compose.yml`

### 2.2 Docker 日志限制没有覆盖应用文件日志

`logging.driver=json-file` 中的 `max-size=50m` 和 `max-file=3` 只限制 Docker 收集的 stdout/stderr 日志。

容器同时使用：

```yaml
command: --log-dir /app/logs
volumes:
  - ./logs:/app/logs
```

`logger/logger.go` 会把 Gin 日志同时写入 stdout/stderr 和 `/app/logs/oneapi-*.log`。文件日志不受 Docker `json-file` 的 150 MB 总量预算约束，而且旧文件不会被 Docker 轮换策略删除。因此 `./logs` 仍有持续占满宿主机磁盘的风险。

### 2.3 `restart: always` 不会处理单纯 `unhealthy`

`restart: always` 在容器主进程退出时尝试重启容器，但 Docker Compose 不会仅因健康检查变成 `unhealthy` 就重启容器。

因此需要分开判断：

- 主进程已退出：检查退出码、OOM 状态和重启次数。
- 容器仍在运行但不健康：由负载均衡/外部监控摘除流量，并根据组织的编排策略决定是否重建。

### 2.4 YAML 缩进必须以实际文件为准

如果生产 Compose 文件中 `ports`、`volumes` 和 `environment` 下的 `-` 确实没有缩进，则 YAML 无法通过解析。但本次已有容器运行日志，更可能是复制到聊天时丢失了缩进，不能直接认定为本次故障根因。

上线前必须执行：

```bash
docker compose config --quiet
```

## 3. 根因优先级与判定标准

| 优先级 | 候选根因 | 判定证据 |
|---|---|---|
| P1 | 宿主机或容器 OOM | `exit=137` 且 `OOMKilled=true`，或内核日志出现 `oom-kill` / `Killed process` |
| P1 | 主机、Docker 或部署流程终止容器 | `exit=143`/`exit=0`，同时 Docker/systemd/部署日志有 stop/restart 记录 |
| P1 | 宿主机磁盘或 inode 耗尽 | `df -h` 或 `df -i` 接近 100%，Docker 或应用日志出现 `no space left on device` |
| P2 | 重启后 PostgreSQL/Redis 不可达 | 启动日志出现 database initialization 或 Redis ping `fatal`，容器反复重启 |
| P2 | 进程在运行，但反向代理/防火墙/端口异常 | 容器内和宿主机本地请求成功，外部域名请求失败 |

在获得上表证据前，不将任何候选项写为已确认根因。

```bash

docker logs --timestamps --tail 500 gemai-api 2>&1

journalctl -k --since '2026-07-31 23:03:30' --until '2026-07-31 23:06:00' \
  | grep -Ei 'oom|out of memory|killed process'

journalctl -u docker --since '2026-07-31 23:03:30' --until '2026-07-31 23:06:00'

df -h
df -i
docker system df

curl -v http://127.0.0.1:22360/healthz
curl -v http://127.0.0.1:22360/api/status
```

这些命令只读，不会删除数据、重启服务或修改生产配置。

## 5. 建议修正的 Compose 片段

```yaml
services:
  gemai-api:
    restart: always
    command: --log-dir /app/logs
    logging:
      driver: json-file
      options:
        max-size: "50m"
        max-file: "3"
    ports:
      - "22360:3000"
    volumes:
      - ./data:/data
      - ./logs:/app/logs
    healthcheck:
      test:
        - CMD-SHELL
        - >-
          wget -qO- http://127.0.0.1:3000/healthz |
          grep -Eq '"success"[[:space:]]*:[[:space:]]*true'
      interval: 30s
      timeout: 10s
      retries: 3
      start_period: 30s
```

保留 `/app/logs` 时，必须在宿主机为 `./logs/oneapi-*.log` 另外设置文件大小、保留数量或保留天数，并配置磁盘使用率告警。

如果生产只需要 Docker 统一收集日志，可以在灰度节点验证后禁用应用文件日志：

```yaml
command: ["--log-dir", ""]
```

两种日志方案二选一完成生产验证，不在故障期间直接切换。
