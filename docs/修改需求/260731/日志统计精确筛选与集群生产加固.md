# 日志统计精确筛选与集群生产加固

日期：2026-07-31

## 1. 生产背景与目标

部署形态为 1 master + 多 slave，共用 PostgreSQL 与 Redis，日在线用户 2 万以上，峰值约
5000 RPM。本次只修复审计确认的权限边界、筛选口径、集群配置和热尾缓存问题，不扩充
高基数聚合维度，不改变计费日志口径，不引入新的必填环境变量。

目标：

1. `/api/log/self/stat` 不得因用户名包含 `%` 而匹配其他用户。
2. 日志表格使用原始日志专属筛选时，统计不得静默返回全站总计。
3. RPM/TPM 在界面上明确为最近 60 秒成功消费日志快照。
4. 集群运维只暴露 3 个常用系统设置，其他保护参数继续使用安全默认值。
5. 最近 60 秒缓存达到上限时平滑淘汰，避免整表清空造成并发缓存击穿。

## 2. 实施内容

### 2.1 自身统计精确用户名

- 新增结构化 `model.LogStatQuery`，集中声明统计真正支持的维度。
- 增加用户名匹配模式，并贯穿分钟维度表、首尾原始日志碎片和最近 60 秒速率查询。
- 管理员统计保留 `%` 模式匹配；自身统计强制等值匹配。
- 匹配模式进入热尾缓存键，防止 exact 与 pattern 结果互相污染。

没有新增用户名字符白名单。原因是这会改变现有账号兼容性；权限边界已在查询层闭合。

### 2.2 不支持的筛选明确拒绝

统计支持的维度保持为：时间、用户名、令牌名、模型名、渠道和分组。

以下原始日志字段不进入分钟聚合：

- `request_id`
- `upstream_request_id`
- `request_ip`
- `request_domain`
- `user_agent`
- `content`

前端检测到这些筛选后显示“当前筛选条件不支持统计”并停止统计请求；后端同时进行独立
校验，防止旧前端或直接调用绕过。不会为这些字段扩充分钟聚合表，避免在当前生产规模下
制造高基数写放大和聚合表膨胀。

### 2.3 RPM/TPM 口径

界面保持简洁的 `RPM`、`TPM` 标签。当前后端口径保持不变：

- RPM：最近 60 秒 `type=2` 成功消费日志数量。
- TPM：同一窗口 `prompt_tokens + completion_tokens`。
- 结果使用进程内 10 秒短缓存。

没有改成所选区间平均值，也没有把失败日志计入 RPM。这两项都会改变既有接口含义和监控
阈值，不属于安全修复；范围聚合列继续保留，不额外增加查询成本。

### 2.4 系统设置替代大量环境变量

新增 3 个持久化系统设置：

| 设置键 | 默认值 | 范围/说明 |
|---|---:|---|
| `log_stat_setting.enabled` | `true` | 实时分钟聚合总开关 |
| `log_stat_setting.backfill_enabled` | `true` | 历史回填开关 |
| `log_stat_setting.recent_minutes` | `5` | 5–30 分钟 |

系统设置写入共享 PostgreSQL 的 `options` 表，各节点通过现有配置同步机制读取，
`SYNC_FREQUENCY` 默认 60 秒。读取发生在进程内类型化配置上，不会为每个统计请求访问
PostgreSQL 或 Redis；相较每次解析环境变量，性能差异可以忽略，运维一致性更好。
首次运行新版本时 master 会把缺失的 3 个默认项写入 `options`，但绝不覆盖已经存在的
运维值，避免各节点因环境变量不同而长期使用不同配置。

兼容策略：

- `LOG_STAT_ROLLUP_ENABLED`
- `LOG_STAT_BACKFILL_ENABLED`
- `LOG_STAT_ROLLUP_RECENT_MINUTES`

以上变量仍可作为首次启动默认值；数据库中保存设置后以数据库设置为准。原有高级参数
（查询超时、raw tail、chunk、pause、group 上限等）保留内置默认值和环境变量应急覆盖，
不展示到日常设置界面，避免误配置。

### 2.5 热尾缓存

热尾缓存仍为单节点进程内缓存，TTL 10 秒、最多 2048 项，不引入 Redis 热路径。写入时：

1. 先删除已过期项；
2. 仍满时只淘汰过期时间最早的一项；
3. 保留现有 singleflight 合并同键并发查询。

这样不会在多用户并发下因第 2049 个键把全部热点同时清空。

## 3. 明确不实施的高风险改动

1. `log_stat_minute_totals` 未覆盖时不回退空条件扫描维度聚合表。生产维度表可能很大，
   回退会让最常用的无筛选请求变成高成本 SUM，并与实时聚合争用 PostgreSQL。
2. 不给 IP、UA、内容、请求 ID 增加分钟维度。这些字段基数高，直接加入会显著放大写入
   和存储。
3. 不改变消费日志、额度和 token 计费口径。
4. 当前生产使用 PostgreSQL 日志库，因此没有修改 ClickHouse 专属 LIKE 转义分支。

## 4. 1 master + 多 slave 部署步骤

### 4.1 部署前

1. 确认所有节点使用同一个 PostgreSQL `SQL_DSN` 和 Redis 连接。
2. 确认仅 master 未设置 `NODE_TYPE=slave`，所有 slave 明确设置
   `NODE_TYPE=slave`。
3. 所有节点启用 NTP/chrony，节点间时钟偏差建议小于 30 秒，必须小于近期重算窗口。
4. 备份 PostgreSQL；本次没有新增业务表或索引，不需要手工 DDL。
5. 使用同一提交构建一个不可变镜像，避免节点代码版本漂移。

### 4.2 滚动发布

1. 从负载均衡摘除一个 slave，升级并通过健康检查后重新加入；逐个完成所有 slave。
2. 暂停管理端日志统计操作，摘除并升级 master，确认系统任务恢复后重新加入。
3. 混合版本期间旧节点仍有旧的自身统计匹配行为，因此升级窗口应尽量短，并确保节点在
   升级时已从负载均衡摘除。
4. 在“系统设置 → 运维设置 → 日志维护”确认：
   - 启用日志统计聚合：开
   - 回填历史日志统计：开
   - 近期重算窗口：5 分钟
5. 修改后等待一个 `SYNC_FREQUENCY` 周期（默认最多约 60 秒），再检查各节点行为。

### 4.3 PostgreSQL 检查

```sql
SELECT name, coverage_start, backfill_cursor, watermark,
       cleanup_pending, cleanup_target, updated_at
FROM log_stat_rollup_states
WHERE name IN ('minute', 'minute_total_v1')
ORDER BY name;
```

验收条件：

- 两个状态均存在，`watermark` 按分钟推进。
- `cleanup_pending = false`。
- 回填期间 `backfill_cursor` 逐步下降，完成后不高于所需查询起点。
- master 日志无持续的 `failed to query/aggregate log stat`。

## 5. 生产验收清单

1. 创建测试用户名 `audit%ops`，同时创建可能被模式命中的 `auditXops`，分别产生消费日志。
   `audit%ops` 登录后自身用量只能包含自己的数据；管理员按 `audit%ops` 查询仍可执行模式
   搜索。
2. 管理员仅按 IP、UA、内容或请求 ID 筛选时，表格正常过滤，统计区域显示“不支持统计”，
   浏览器网络面板不发送统计请求。
3. 直接调用 `/api/log/stat?request_ip=203.0.113.10` 返回业务失败，不返回全站额度。
4. 支持的模型、用户名、令牌、渠道、分组和时间筛选仍能返回正确额度。
5. RPM/TPM 保持简洁标签；连续刷新不得出现统计接口自动重试 429。
6. 切换 master 或让日志延迟数分钟后，5 分钟窗口内的数据能在后续分钟重算中补入。
7. 在 2 万用户并发量下观察 PostgreSQL：统计请求不出现原始日志长区间扫描，Redis 不新增
   统计缓存大键。

## 6. 回滚

应用回滚到上一镜像即可；本次没有破坏性数据库迁移。新增 `options` 记录旧版本会忽略，
可保留。若需要紧急止损，在新版本管理端关闭 `log_stat_setting.enabled`，等待配置同步后
统计接口会明确显示不可用，不会回退扫描原始日志。

- `bun run test`：24 个测试文件、101 个测试通过。

- `bun run typecheck`：通过。
- `bun run build:check`：通过。
- 涉及文件的 `oxlint`：通过。
- `bun run i18n:sync`：7 个语言文件均无缺失键；报告中日/俄/简中各 1 个
  既有“与英文相同”项，不是本次新增文案。

全仓 `bun run lint` 仍被仓库内其他既有文件的规则错误阻断；本次没有扩大范围修改这些
无关文件，涉及文件已单独通过同一 lint 配置。

二次发布审计补充确认：

- `LogStatRollupState.CountGeneration` 由 token usage source 的代际切换、恢复和清理流程读取
  与写入，不是死字段，必须保留。
- 系统任务锁使用指定 `type` 唯一键的 `ON CONFLICT DO NOTHING` 区分正常锁竞争；
  连接失败、约束异常等非冲突错误原样返回，不再静音后误判为锁竞争。
- 日志统计配置读取与现有 `OptionMap` 更新使用同一读写锁，避免运行时读到部分更新值。
- 多项设置保存期间不逐项触发跨节点 GET；成功值直接写入 React Query 缓存，避免负载
  均衡命中尚未同步的 slave 后把界面回滚成旧值。任一保存失败时，表单只保留已收到
  成功响应的值，并把配置缓存标记为待刷新，不立即读取可能尚未同步的其他节点。
- 单项设置写入会检查数据库查询和保存错误；持久化失败时返回失败响应，且不会把未落库
  的值写入当前节点 `OptionMap`。
- 安全策略重复提示已从 7 个 locale 的错误根节点迁入 `translation`；`sync-i18n.mjs`
  现在遇到 `translation` 之外的根节点 key 会直接失败，防止相同问题再次漏过检查。
- 统计查询键只使用稳定的路由筛选条件，不包含渲染时生成的默认“当前时间”，避免无关
  重渲染额外消耗统计接口限流额度。

本地自动化不能替代共享 PostgreSQL、多节点负载均衡、NTP 和真实日志量的发布后验收；
第 5 节必须在灰度/生产发布窗口执行。
