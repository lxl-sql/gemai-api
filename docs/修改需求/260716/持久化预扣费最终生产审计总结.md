# 持久化预扣费最终生产审计总结

> 日期：2026-07-16  
> 生产规模：约 3 万日活、累计约 2 亿条日志、每日约 200 万条日志、多实例部署  
> 基础设施：多实例共享 PostgreSQL 和 Redis  
> 结论：持久化预扣费与余额一致性链路已通过代码级生产门禁，可以进入小流量灰度

完整架构设计、状态机、监控 SQL 和故障边界见同一需求的详细文档：

- `docs/修改需求/260715/PostgreSQL持久化预扣费与余额一致性修复.md`

## 1. 最终架构结论

- PostgreSQL 是钱包、订阅、Token 额度和预扣状态的唯一事实来源。
- Redis 不保存 `billing_reservations`，只继续承担鉴权和普通缓存；即使配置 AOF/RDB，也不能替代 PostgreSQL 财务事务。
- 主库新增业务表 `billing_reservations`，记录请求级预扣、上游发送状态、精确结算/退款意图、审计状态和异步任务绑定关系。
- 日志库新增小型幂等表 `billing_audit_markers`，用于保证消费日志去重；没有在约 2 亿行 `logs` 上新增阻塞式索引。
- 钱包、订阅与 Token 的预扣、补扣、退款在主库事务中原子提交。
- 多实例通过数据库行锁、数据库时钟租约、幂等 request ID、终态 CAS 和 repair task 协作，不依赖 Redis 分布式锁。
- 正常同步请求结算并完成日志审计后删除 receipt；异步任务 receipt 保留到任务终态计费和审计完成，因此新表不会按每日日志量永久增长。

## 2. 余额显示修复

原问题并不只是“余额接口不是实时的”，而是预扣生命周期、响应时序和缓存共同造成：

1. 请求先按估算额度预扣。
2. 非流式成功响应原来可能早于精确结算提交给客户端。
3. 用户立即打开钱包时，会读到仍处于预扣状态的低余额。
4. 精确结算或退款稍后完成后，页面已持有的旧快照不会自动恢复。

现在的行为：

- `/api/user/self`、兼容 billing 接口、订阅和 Token 余额接口读取主数据库。
- 余额类响应统一返回 `Cache-Control: no-store`，禁止浏览器、网关或 CDN 复用旧余额。
- 付费非流式响应在精确结算事务提交前不会向客户端暴露成功 body。
- 异步任务成功响应在“任务入库 + 提交阶段结算”事务提交前不会向客户端暴露。
- 流式请求执行期间显示预扣后的可用余额属于正确语义；流结束后同步完成差额结算，异常崩溃才进入 repair 窗口。

## 3. 最终审计修复项

### 3.1 财务一致性

- 修复上游已经成功后，本地结算失败又被通用错误清理错误退款的问题。
- 精确结算一旦开始，`finalizationStarted` 会阻止退款覆盖结算意图。
- 异步 Task/Midjourney 上游已接受但本地提交失败时，持久化精确 settlement failure，交由其他实例修复。
- `dispatched` 状态崩溃后无法确定上游结果时，保守按预扣估值结算，避免形成免费调用窗口。
- Task/Midjourney 终态 CAS、钱包/订阅、Token 和最终任务额度在一个事务内提交。
- settlement、refund、日志审计和 repair 均具备重复执行幂等性。

### 3.2 数据边界与归属

- 所有预扣、补扣和最终额度拒绝负数及超过 int32 数据库范围的值。
- Token 增减同时检查 `remain_quota`、`used_quota` 的下界和上界。
- Token 更新条件同时校验 `token_id` 与 `user_id`；归属错配会使整个事务回滚。
- Token 在请求发送前已删除时拒绝预扣；发送后被删除时允许资金结算或退款继续完成，避免用户余额永久冻结。
- PostgreSQL 不再直接执行 `quota + gift_quota` 的 `int4` 加法，改为分别读取后在 Go 中安全相加，避免表达式溢出。
- 软删除用户仍可通过 unscoped 事务完成结算或退款。

### 3.3 幂等与迁移

- `request_id` 唯一索引防止同一请求重复预扣。
- Task/Midjourney 幂等提交同时校验上游任务 ID、用户和实际额度；额度冲突时拒绝重放。
- repair 到期扫描使用 `(expires_at, id)`。
- 审计积压扫描使用 `(status, updated_at, id)`，避免日志库故障时退化为大范围扫描和排序。
- `task_id`、`midjourney_id` 索引用于异步 receipt 定位。
- 迁移保持 SQLite、MySQL 5.7.8+、PostgreSQL 9.6+ 兼容。

### 3.4 并发安全

- 活跃 reservation 使用数据库时间续租，避免多实例系统时钟偏差。
- repair 会在事务行锁内再次检查到期状态，消除扫描与心跳续租之间的 TOCTOU。
- 异步视频轮询改为私有 Task 副本计算和落库，不再并发修改调用方持有的 Task 指针。
- 日志轮转计数和工作状态改为原子计数与 CAS。
- 审计 claim 带所有权令牌和超时接管规则，旧实例不能删除新实例接管的 receipt。

## 5. 生产发布门禁

1. 备份主库并确认 PostgreSQL 主从或高可用状态正常。
2. `SQL_DSN` 必须指向可写主库或提供写后读强一致性的数据库代理；余额查询不能路由到异步只读副本。
3. 低峰期先从负载均衡中排空旧实例，避免新旧计费生命周期并存。
4. 先启动一个 master 完成 `billing_reservations`、`billing_audit_markers` 和小表索引迁移。
5. 确认迁移成功后再滚动启动其他实例。
6. 保证至少一个 master 运行 system task runner，并保持 `BILLING_SETTLEMENT_REPAIR_ENABLED=true`。
7. 灰度覆盖正常流式、正常非流式、客户端中断、上游 4xx/5xx、渠道重试、统一任务和 Midjourney。
8. 观察至少 24 小时，再决定是否全量。

## 6. 上线监控重点

- `billing_reservations` 各状态行数和最早到期时间。
- `settling`、`refunding`、`auditing` 是否持续积压。
- `billing_settlement_failures` 中 pending 数量和最大 attempts。
- `billing_settlement_repair` system task 是否持续运行。
- `billing_reservations`、`billing_audit_markers` 的死元组和 autovacuum 状态。
- 日志关键字：
  - `failed to renew billing reservation`
  - `failed to repair billing reservation`
  - `failed to record billing settlement failure`
  - `refund billing reservation failed`
  - `atomic task finalization failed`
  - `billing_dispatch_failed`

## 7. 回滚原则

不能在仍有活跃 reservation 时把全部实例直接回滚到旧版本。安全顺序：

1. 停止新请求。
2. 等待正常请求结束。
3. 确认 `billing_reservations` 为空。
4. 确认没有 pending 的 managed settlement failure。
5. 再回滚应用二进制。

紧急情况下至少保留一个新版本 master 继续执行 repair，直到 reservation 清空；回滚窗口内不要删除新增表。

## 8. 最终结论与边界

本功能没有遗留已知 P0/P1 代码问题，已满足进入生产小流量灰度的条件。

仍需明确一个无法由本地数据库完全消除的边界：请求已经发送给 provider 后进程硬崩溃，而 provider 又不提供幂等键、任务查询或账单对账接口时，本地无法严格判断上游是否成功。当前对过期 `dispatched` 记录保留预扣估值，是优先避免成功调用被免费使用的保守财务策略。若要获得逐 provider 的精确恢复，需要后续增加对应的幂等请求键与对账适配器。
